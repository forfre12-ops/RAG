KIPRA AI 영업비밀관리시스템 — Lloydk 파트 설계

문서를 업로드하면 AI가 4단계 보안등급(특급/1급/2급/3급)을 자동 분류하는 온프레미스 Docker 시스템. 한국지식재산보호원이 발주, KL과의 협업 구조로 Lloydk는 AI 코어 6개 기능을 담당.

발주처 한국지식재산보호원 담당 파트 Lloydk AI Engine (FUN-003, 004, 005, 022, 023, 024) 현 단계 PoC 설계 완료
AI / NLP RAG Korean BERT On-premise Active Learning FastAPI

2 · 풀려는 문제

Problem 1

실데이터 부재

영업비밀은 정의상 외부 공개 불가. 학습 데이터를 구할 수 없음.

Problem 2

도메인 전문성

등급 판정은 4대 평가요소(경제가치·비공지성·관리수준·유출영향) 종합. 키워드 매칭으로는 불가.

Problem 3

미탐(FNR) 위험

고등급 → 저등급 오분류 = 즉시 영업비밀 유출 사고. Accuracy가 아니라 FNR이 KPI.

해법 — 3중 전략

  1. 데이터 3중 확보 — 공개 데이터(AI Hub·공공데이터·KIPRA 가이드) + LLM 합성(Claude/Qwen3 1,500건 + 이중 검수) + 능동학습(운영 중 누적)
  2. 한국어 도메인 모델 — KF-DeBERTa(금융·법률 사전학습) + KURE-v1(한국어 retrieval fine-tuned) + RAG로 기업별 사내규정 결합
  3. FNR 3-layer 통제 — 손실함수 비대칭 가중치 + DB corrections.direction 추적 + v_active_learning_status 자동 트리거

7 · 핵심 결정 6가지

7.1 왜 BERT? LLM도 분류 잘하는데

분류는 인코더 모델이 디코더 LLM보다 빠르고·정확하고·해석 가능. 14B LLM은 1건당 수초·달러, KF-DeBERTa는 초당 수십건이며 비용 거의 0. Attention rollout으로 근거 span도 추출. 단, LLM은 합성·RAG·평가 보강에 적극 활용 (역할 분리).

7.2 왜 KF-DeBERTa?

영업비밀 문서는 90%+가 경영·기술·법무·계약. KF-DeBERTa는 카카오뱅크가 한국어 + 금융·법률 도메인으로 사전학습 — 도메인 일치도가 KLUE-BERT(뉴스), KoBERT(위키)보다 압도적.

7.3 왜 KURE-v1?

BGE-M3를 한국어 retrieval 데이터로 fine-tune한 모델 (고려대 NLP&AI Lab). 베이스가 동일하므로 dense+sparse+multi-vector 호환 유지 + 한국어 Recall@1 +1.6%p. 인덱스 재구축 없이 모델만 swap 가능 — 운영 리스크 최소.

7.4 왜 RAG를 분류에 결합?

기업마다 영업비밀 기준이 다름. 같은 매출 자료도 A기업은 1급, B기업은 2급일 수 있어 학습 모델 하나로 안 됨. 기업별 사내규정을 Qdrant에 임베딩해두고 추론 시 Top-K로 BERT 출력 보강. RAG는 선택 옵션 — 자원 부족 기업은 OFF 가능.

7.5 왜 FNR이 핵심 KPI?

보안 시스템에서 고등급 → 저등급 미탐 = 즉시 유출 사고. 저등급 → 고등급 과탐은 업무 불편 수준. 두 오류의 비용이 다르므로:

  • 손실함수 비대칭 가중치 (고등급 미탐 cost ×3~×5)
  • EarlyStop 기준을 accuracy가 아닌 val_FNR_overall
  • Confusion Matrix를 등급별로 추적, TS→S2/S3 알람

7.6 어떻게 운영 중에 좋아지나?

LangGraph 능동학습 루프:

추론 → 관리자 검수 → (오분류) 재라벨 → corrections 누적 → underclass 10건 또는 unconsumed 50건 도달 → 자동 재학습 트리거 (Celery) → MLflow 평가 → 신모델 FNR 개선 시 Staging → 관리자 승인 → Production 승격 → 가중치 MinIO 교체 (무중단)

8 · 예상 Q&A

Q1

데이터가 부족할 텐데?

공개 데이터(AI Hub·공공데이터·KIPRA 가이드) + LLM 합성 1,500건 + 능동학습 3중 전략. KF-DeBERTa는 이미 도메인 사전학습이라 4,000건이면 충분.

Q2

합성 데이터 위험은?

(1) Claude 70% + Qwen3 30% 혼합으로 스타일 편향 방지. (2) 시스템 프롬프트에 "등급명 본문 직접 표기 금지". (3) PII 정규식 + 검수자 이중 확인.

Q3

Class imbalance는?

데이터: 고등급 over-sample(TS 15/S1 25/S2 30/S3 30). 학습: class_weight=inverse frequency + 비대칭 cost. 가중치는 classification_levels.loss_weight 외부화.

Q4

GPU 부족하면?

KF-DeBERTa-base 184M은 VRAM 16GB로 batch=8 충분. 더 작으면 KoELECTRA(110M)로 전환. INT8/INT4 양자화는 추론 단계 옵션.

Q5

모델 무중단 업데이트?

모델 가중치는 이미지가 아닌 MinIO 볼륨. model_versions.is_active 플래그 swap → FastAPI lazy load. 롤백도 동일 메커니즘.

Q6

대량 요청 처리?

동기 /classify + 비동기 /classify/async·/batch. Celery worker가 Redis 큐 소비, 결과 PG 저장, KL polling/webhook 수신.

Q7

보안 / 컴플라이언스?

API Key + Actor 메타 감사 로그 (audit_log, payload SHA-256만 저장). 멀티테넌트 격리. PII 자동 필터. 영업비밀 원문은 PG 미저장(MinIO 분리).

Q8

모니터링?

Prometheus(메트릭) + Grafana(대시보드) + Loki(로그) + MLflow(실험). FNR 임계 초과 시 Alertmanager 자동 알람.
