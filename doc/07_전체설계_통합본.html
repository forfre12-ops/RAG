KOIPA AI 영업비밀관리시스템
전체 설계 통합본

한국어 문서를 받아 4단계 보안등급(특급·1급·2급·3급)을 자동 분류하는 온프레미스 시스템 — 그 설계가 왜 이렇게 굳혔는지, 전체 워크플로우와 모델별 장단점, 선택 이유를 한 문서에 펼친 근거.

KF-DeBERTa + KURE-v1 RAG FNR ≤ 5% 핵심 KPI 온프레미스 Docker PoC 4주 (P1~P5)

§1프로젝트 한눈에

무엇을 만들고, 누가 무엇을 책임지는가.

What
4단계 자동 보안 등급 분류

한국어 문서(HWP/PDF/DOCX)를 업로드하면 특급·1급·2급·3급을 AI가 자동 추론하고, 근거(evidence span)와 4대 평가요소 점수를 함께 반환합니다.

Who
KOIPA 발주, 기업 온프레미스

한국지식재산보호원이 발주한 표준 시스템. 기업이 사내 서버에 Docker Compose로 설치해 운영. 외부 송신 없는 폐쇄망도 지원.

Split
KL 18개 ↔ Lloydk 6개

KL은 웹 UI · 권한 · 보관함 · 워터마크 · 감사를, Lloydk는 AI 학습/추론/합성/평가를 REST API로 제공합니다.

2.3 능동학습 루프

M5 추론 (staging)
   → KL 관리자 검수 → /relabel
   → relabel_event INSERT (original, corrected, reason, actor)
   → ActiveLearningQueue.push (Redis)
   → if queue.size >= threshold(=100):
        RetrainTrigger.fire
          → TrainingService.start(incremental)
          → M4 재학습 (이전 가중치 + 새 데이터)
          → 새 model_version Staging 등록
          → 이전 vs 신규 FNR 비교 리포트 자동 생성
          → 관리자 승인 시 Production 승격

LangGraph로 이 루프를 상태 머신으로 명시 — idle → collecting → training → evaluating → awaiting_approval → promoted.

4.2 KF-DeBERTa 채택 이유 (3가지)

01 · 도메인 적합성

영업비밀 후보 문서(매출/원가/특허/계약서/내부지침)는 금융·법률 어휘 비중이 큼. KF-DeBERTa는 카카오뱅크가 한국어+금융+법률 텍스트로 사전학습 → 도메인 임베딩 공간이 이미 정렬되어 있음.

02 · 효율

184M 인코더는 GPU 1장(24GB)에서 batch 16으로 초당 수십 건 추론. 14B 디코더 LLM은 1건당 수 초 + 비용 큼 + 결정성·해석성 떨어짐.

03 · 해석성

attention rollout / IG로 evidence span 추출 가능. 보안 시스템은 "왜 이 등급인지" 근거를 함께 제공해야 함 (관리자 검수·감사 대비).

4.3 KoELECTRA를 동시에 유지하는 이유

자원 부족 기업(GPU 16GB 이하·CPU 추론 환경)을 위한 이중 트랙. KoELECTRA-base 110M → CPU 추론도 현실적. 분류 헤드·학습 파이프라인은 동일하므로 동일 데이터셋·동일 평가체계로 두 모델을 함께 학습 → 환경별 골라쓰기.

Conclusion

분류 코어는 BERT, LLM은 합성 데이터 생성·RAG 보강·라벨링 경계 판단에 보조 활용 — 역할 분리.

class LLMAdapter(Protocol):
    name: str

§10RAG 결합 방식과 한계

10.1 왜 RAG를 분류에도 쓰는가

기업마다 영업비밀 기준이 다르다. 같은 "매출 자료"라도 A기업은 1급, B기업은 2급일 수 있다. 학습 모델 하나로 모든 기업의 변동성을 다 잡을 수 없다. 그래서 기업별 사내규정·정책을 KURE-v1 임베딩 → Qdrant(테넌트 네임스페이스 분리)에 두고, 추론 시 Top-K로 회수 → 모델 출력을 후처리 보강.

10.2 결합 방식 — 모델 입력이 아니라 후처리 보강

BERT 청크 추론 → 청크별 등급 확률
                    │
                    ▼ ChunkAggregator
              문서 단위 등급 확률
                    │
       (RAG ON이면)  ▼
RAG Top-K 가이드 청크의 등급 분포 회수
                    │
                    ▼ 가중평균 (α·model + (1-α)·rag)
              최종 라벨 + confidence
왜 모델 입력에 안 넣는가

BERT 시퀀스 분류는 학습 시 본 적 없는 외부 컨텍스트 토큰을 입력에 결합하면 학습-추론 분포 불일치(distribution shift)가 생김. 별도 보강 레이어로 처리하면 학습은 깨끗이, 추론은 유연하게.

10.3 한계

  • RAG 적중률이 낮으면 보강 효과 없음 → KURE-v1으로 retrieval 성능 보강
  • 테넌트별 사내규정 데이터가 부족한 기업은 RAG 효과 제한 → RAG는 선택 옵션, OFF 가능

v1의 factor_scores JSONB → v2 document_factor_scores 정규화. FK 무결성·집계 쿼리 효율화.

D6 · 등급체계 스냅샷

model_versions.level_snapshot JSONB에 학습 시점 등급 체계 보존. 등급 정의 변경 후에도 과거 모델 해석 가능.

D7 · 감사 본문 미저장

audit_log.payload_hash는 SHA-256만 저장. 재현 가능하되 본문은 PG에 안 남김 → 영업비밀 정책 충돌 회피.

D8 · 가중치 합 트리거

evaluation_factors.weight 합 = 1.0 강제. DEFERRABLE CONSTRAINT TRIGGER로 트랜잭션 종료 시점 검증.

20.3 경계 규약 — 자주 깨지는 곳 6개

R1 · 멱등성

같은 doc_id + Idempotency-Key로 들어오는 중복 호출은 Lloydk가 24h 캐시로 동일 응답 반환. KL의 재시도 부담 제거.

R2 · 동시성 락

같은 doc_id에 동시 분류 요청 시 PG advisory lock으로 직렬화. 두 번째 요청은 첫 결과를 받음.

R3 · 본문 미저장 원칙

Lloydk는 원본 바이너리(HWP/PDF) 미수신·미저장. content는 텍스트만, 요청 단위 처리 후 30일 후 자동 삭제. 영구 보관은 KL만.

R4 · Evidence 노출 정책

evidence span은 원문 부분 텍스트라 영업비밀 일부일 수 있음. KL이 UI 표시 시 권한 체크 후 노출. Lloydk는 호출자에게 응답에 포함하되, 가공·마스킹 책임은 KL.

R5 · 삭제 cascade

KL이 문서를 삭제하면 DELETE /classify/{doc_id}를 명시적으로 호출. 자동 cascade는 안 함. Lloydk가 받으면 classifications/chunks/evidence cascade 삭제, audit_log는 hash만 잔존.

R6 · 에러 메시지 변환

Lloydk는 항상 RFC 7807 JSON (영문 title/detail). 사용자에게 보이는 한국어 메시지는 KL이 매핑 (예: type=https://lloydk/errors/gpu-oom → "AI 엔진 일시 과부하, 잠시 후 재시도").

21.4.2 현실 보정 — 숨은 비용 4가지

H1 · 운영 인력

OSS GPU 서버 = DevOps·MLOps 책임 추가. vLLM 버전 관리, 양자화 재실험, 모델 swap, GPU 장애 대응. 월 인건비 환산 수백~수천만원.

H2 · 신뢰성·가용성

API는 99.9% SLA + 글로벌 redundancy. 자체 GPU는 단장애점. 다운타임 시 폴백 비용 + 사용자 신뢰 비용.

H3 · 품질 손실

Q4 양자화는 평균 95% 품질이지만 경계 사례·법률 문어체에서 FNR 악화 가능. 영업비밀 시스템에선 미탐 1건이 사고로 직결.

H4 · 능동학습 부담

API는 모델 업데이트 자동(Anthropic이 함). OSS는 새 버전 평가·승격·롤백을 우리가 다 함. MLflow + 평가셋 운영 부담.

현실 손익분기점: 단순 비용은 월 45K건이지만, 위 4개 보정 시 월 100K~200K건 이상에서야 OSS가 진짜 유리해짐.
