## 1. 발주처(한국지식재산보호원) 협의 항목

### Q1. 발주처 제공 GPU 사양 확인
- 모델 학습·추론에 사용할 GPU의 **VRAM 용량**(예: 24GB / 48GB / 80GB) 및 **장수**
- CUDA 버전, NVIDIA Driver 버전, 컨테이너 런타임 사용 가능 여부
- **영향**: VRAM 24GB → KF-DeBERTa-base 학습 batch_size=8 / 48GB+ → batch_size 16 가능. Qwen3-14B 운영도 24GB 이상 권장(INT4 양자화 시).

### Q2. 합성 데이터 활용 범위
- LLM(Claude / Qwen3 등)으로 생성한 합성 문서를 다음 용도로 활용해도 되는지 확인:
  - (a) 학습 데이터로 사용 — **사업단 내부 사용**
  - (b) 다른 지원기업과 공유 — **PoC 산출물 표준 데이터셋화**
  - (c) 외부 학술 발표·논문 공개
- 운영 단계 LLM API 비용 부담 한도(월/연 상한액)

### Q3. 비밀해제(declassified) 실문서 제공 가능성
- 보호원 내부 또는 협력 기업의 비밀해제 영업비밀 문서를 PoC Test 셋용으로 제공 가능한지
- 가능 시 수량·등급 분포·제공 시점·NDA 조건
- **불가 시** 본 PoC는 공개 데이터(D1~D6) + 합성 데이터(2.2)만으로 진행 — 외부 일반화 검증 한계 명시

### Q4. KIPRA 영업비밀 등급분류 가이드 최신본 수령
- 현재 운영 중인 등급분류 가이드 최신 PDF/DOCX 일괄 수령
- 4단계 등급 정의(특급기밀·1급 비밀·2급 대외비·3급 공개)의 **각 등급별 판단 기준 상세 문서** 포함 요청
- 가이드 개정 이력(언제·왜 바뀌었는지) 확인 — FUN-002 버전 관리 설계 근거

### Q5. AI Hub / 모두의 말뭉치 데이터 신청 명의
- 학습 데이터 보강용 외부 코퍼스 신청 시 명의:
  - (a) 사업단 (보호원 명의로 일괄 신청, 향후 KL이 운영 시 양도 용이)
  - (b) 로이드케이 (개발 효율 우위, 운영 양도 시 별도 합의 필요)

### Q6. EXAONE 라이선스 검토
- LG AI Research **EXAONE 3.5 32B** 모델을 한국어 강화 옵션으로 채택 검토 중
- 공공사업·온프레미스 상용 배포에 사용 가능한지 라이선스 확인 (LG 측 별도 합의 필요 여부)

### Q7. 검수 기준 합의 (등급 경계 사례)
- PoC P3 단계에서 합성 문서 50건을 **공동 검수 워크숍** 형태로 진행 제안
  - 발주처 가이드 작성자 1~2명 + 로이드케이 AI팀 + 검수자 2명
  - 일정: 약 1일(반나절×2회)
- 목적: 등급 경계 사례에 대한 판단 기준 합의 → 라벨링 규칙 YAML(FUN-023) 확정 근거

## 2. KL 협의 항목

### K1. KL 기존 인프라 도입 현황
- 현재 KL 시스템이 사용 중이거나 도입 예정인 인프라:
  - [ ] PostgreSQL 사용 중 (버전: ___)
  - [ ] Elasticsearch / OpenSearch 사용 중 (버전: ___)
  - [ ] Redis 사용 중
  - [ ] Kafka / RabbitMQ 등 메시지 큐 사용 중
  - [ ] 인증 시스템 (LDAP/SSO/JWT 발급기)
- **영향**: ES 도입 시 Qdrant 대신 dense_vector 통합 검토 가능 / 인증 체계는 KL ↔ Lloydk API 토큰 발급 방식과 직결

### K2. 인터페이스 명세서 검토 (`03_openapi_lloydk_kl.yaml`)
다음 9개 영역 16개 엔드포인트에 대한 KL 측 검토 의견 요청:
| 영역 | 엔드포인트 수 | 검토 포커스 |
|---|---|---|
| classify | 5 | 동기·비동기·일괄 호출 패턴이 KL의 처리량과 부합하는지 |
| confirm/relabel | 2 | 관리자 확정·재라벨 워크플로우가 KL UI와 부합하는지 |
| training | 3 | 학습 트리거·진행 상태 폴링 방식 |
| synthesis | 3 | 검수 큐 UI 노출 방식 |
| guide | 2 | FUN-002 가이드 문서 동기화 방식 |
| schema | 2 | 등급체계 변경 시 재학습 트리거 응답 |
| metrics | 3 | 대시보드 데이터 표시 방식 |

회신 형식: GitHub PR 코멘트 또는 yaml 직접 편집 후 회신

### K3. 인증 방식 합의
- 현 명세는 **API Key (X-API-Key 헤더)** 기반
- KL 측이 SSO/JWT 기반을 요구하면 명세 갱신 필요
- 호출자 `Actor` 메타에 KL 관리자 user_id·역할을 전달하는 방식 확인

### K4. KL 측 통합 일정
- KL의 본 사업 개발 일정 마일스톤 공유
- 인터페이스 통합 테스트 가능 시점 (PoC E2E 시연 후 본격 통합 예정 시점)
- KL 측 담당자(개발 PM, 통합 담당) 지정 요청

### K5. 멀티 테넌트(기업별 분리) 요구 강도
- 본 시스템은 여러 지원기업이 사용 예정인지 확인
  - (a) 보호원 단일 테넌트
  - (b) 지원기업 N개사 멀티 테넌트 (각 기업 데이터 분리·권한 분리)
- **영향**: Qdrant 네임스페이스 분리·RAG 인덱스 격리·Postgres tenant_id 컬럼 인덱싱 정책
