1-2. 배포 준비 중 로컬 DB 시험으로 잡은 결함 3건

로컬에 PostgreSQL 을 실제로 띄우고 전체 시험을 돌려 찾았다. 단위 시험만으로는 셋 다 드러나지 않았다.

결함증상없었다면
alembic 리비전 번호 충돌
545b27bf		 SERIAL→IDENTITY 마이그레이션에 붙인 번호가 pg_rag_vectorstore 가 이미 쓰는 번호였다. Cycle is detected in revisions 배포 시 alembic upgrade 가 통째로 실패한다. 같은 id 가 둘이면 체인이 순환으로 보여 어떤 마이그레이션도 돌지 않는다
규약서 유령 경로 오판
545b27bf		 /metrics-prom 을 유령으로 잡았다. 규약서 기재가 맞고 시험이 틀렸다 — 코드가 include_in_schema=False 로 일부러 감춘 경로다 시험이 계속 빨간불이라 §2 판단이 서지 않는다
시험이 조용히 안 돌던 것
529c300c 0a814bd8		 DB 판정이 세 곳에 복제돼 전부 localhost:5432 하드코딩. make test-full 도 DATABASE_URL 없이 돌았다 fullstack 101 건이 계속 건너뛴다. 그 상태로 초록을 보고 배포했을 것이다
첫 번째가 결정적이다. 단위 시험 3,680 건이 전부 초록이었고 223 트랜잭션 드라이런도 통과했다 — 드라이런은 SQL 만 돌렸지 alembic 체인을 타지 않았기 때문이다. 배포해서 alembic 을 부르는 순간 터졌을 것이다.

DIRECT_SRC_TAR 를 빼고 부르면 안 된다. 그러면 스크립트가 GitHub 원격 tip 을 받아 현재 판보다 뒤로 롤백된다. 이 환경은 push 가 막혀 있어 원격이 로컬보다 뒤에 있다.

스크립트가 자동으로 처리하는 것 — uv.lock 정합 · 외부 볼륨 이름 · .env 접두 · 워커 메모리 한도 · 학습 산출물 소유권 · 6개 이미지 태그 · 되돌림 태그 생성 · 기동 후 SHA 대조.

5. 스키마 마이그레이션 (별도 · 수동)

배포 스크립트는 alembic 을 돌리지 않는다. 소스 반영과 스키마 변경을 분리해 두었다.

docker exec koipa-jjw-api-1 alembic upgrade head   # -> c9e1f2a3b4d5

대상과 검증 결과는 「DB 대리키 표준화 전환계획」에 있다. 요지 — 정수 대리키 9개를 SERIAL 에서 표준 GENERATED ALWAYS AS IDENTITY 로 바꾼다. 223 실데이터에 트랜잭션으로 걸어 보고 롤백해 검증했다(tb_audit_log 38,502행 포함).

7. 롤백과 실행 기록

되돌림 태그는 koipa-jjw-* 에 걸린다. 2026-08-29 롤백 때 실제 구동 이미지가 koipa-jjw-api 인데 koipa-poc-api 에 태그를 걸어 한 번 헛돌았다. 빌드는 koipa-poc-* 로 나오고 스크립트가 프로젝트명으로 다시 태그한다 — 되돌릴 때 보는 것은 koipa-jjw-* 쪽이다.

스크립트가 배포 전 이미지에 :rollback-YYYYMMDDHHMM 태그를 남긴다. 소스는 그 태그로 되돌리고, 스키마는 alembic downgrade -1 로 되돌린다. 순서는 스키마 먼저, 그다음 이미지다.
