오픈망 테스트서버 배포 가이드

인터넷이 되는 오픈망 테스트서버에 시스템을 올리는 실행 가이드. 결론부터: 배포 파일도 배포 메뉴얼도 이미 다 있다. 오픈망 = lite-cloud tier이고, 정본 런북 CLOUD_DEPLOY_RUNBOOK.md 그대로 따라가면 반나절 컷이다(2026-07-05 prod 경로 로컬 리허설로 검증됨). 진짜 신경 쓸 것은 배포 절차가 아니라 ① 외부 노출 앞단(리버스 프록시)+키·CORS 잠금, ② 테스트 데이터를 외부 LLM에 보내도 되는지 두 가지다.

tier: lite-cloud
GPU 불필요 · 외부 LLM API
배포 소요: 반나절
파일·문서 준비완료
가장 중요한 한 가지

오픈망 테스트서버는 안전이 느슨한 개발/스테이징 tier(lite-cloud)인데 동시에 인터넷에 노출된다. 이 조합이 이 문서의 핵심 리스크다 — 테스트서버여도 (1) API_KEY·CORS를 진짜로 잠그고, (2) 영업비밀 본문이 외부 LLM(Anthropic/OpenAI)으로 전송됨을 인지하고 합성·공개 데이터로만 테스트해야 한다. 배포 자체는 리허설로 검증된 길이니, 위험은 절차가 아니라 노출·데이터반출에 있다.

01 배포 tier 결정 — 오픈망 = lite-cloud

이 시스템은 4-tier 배포 프로파일(KOIPA_DEPLOY_PROFILE)로 이미 나뉘어 있다. "테스트서버가 어떤 종류냐"가 경로를 가르는데, 인터넷 되는 오픈망 = lite-cloud tier로 확정이다.

03 배포 절차 (반나절 컷)

CLOUD_DEPLOY_RUNBOOK 순서 요약. 전제: Docker + Compose, 인터넷(이미지 빌드·외부 LLM API) 가용, GPU 불필요.

① 환경파일 준비

cp .env.lite-cloud .env.cloud     # 실값 채우기 (§04 필수값 표)

② 기동 — override 제외 + --env-file (중요)

docker-compose.override.yml은 dev 전용(GPU·Ollama 강제)이라 자동 머지되면 GPU 없는 VM에서 실패한다. 반드시 명시 경로로 올린다. ENV_FILE=과 --env-file을 같은 파일로 줘야 dev .env 누수가 차단된다.

CF=".env.cloud"
BASE="-f docker-compose.yml -f docker-compose.prod.yml"
ENV_FILE=$CF docker compose --env-file $CF $BASE up -d postgres redis minio
# postgres 헬시 대기 후 ↓
ENV_FILE=$CF docker compose --env-file $CF $BASE run --rm api alembic upgrade head   # 마이그레이션 수동
ENV_FILE=$CF docker compose --env-file $CF $BASE up -d

③ 분류 모델 공급 (external 볼륨)

artifacts/는 이미지·git 밖(대용량)이라 external 볼륨으로 넣는다. prod compose가 prod_artifacts(external·ro)를 /app/artifacts에 마운트한다.

docker volume create koipa_prod_artifacts
docker run --rm -v koipa_prod_artifacts:/dst -v "$(pwd)/artifacts:/src:ro" alpine \
  sh -c "mkdir -p /dst/classifier_p1_retrain_v4_clean && \
         cp -r /src/classifier_p1_retrain_v4_clean/v-dd3abab9 /dst/classifier_p1_retrain_v4_clean/"
# .env.cloud 의 CLASSIFIER_MODEL_DIR 와 경로 일치 필수 (부재 시 부팅 거부)

④ 온도 보정 (미탐 방지)

active 모델 v-dd3abab9에 temperature.json이 없어 T=1.0(미보정)으로 서빙 → OOD 과신·TS/S1 무음 미탐 위험. 테스트에선 .env.cloud의 CLASSIFIER_TEMPERATURE=3.0(사전 실측 T≈3) 유지로 즉시 우회.

⑤ 워커·관측 스택

up -d에 worker·beat 포함(compose 기본). drift·outbox·partition·audit-chain 알람이 no-data를 벗어나려면 worker·beat가 떠 있어야 한다.

⑥ 스모크 검증

curl -fsS http://<host>:8000/api/v1/healthz/ready         # 200 (모델·DB·스토어 준비)
python scripts/p5_e2e_smoke.py --mode http --url http://<host>:8000 --api-key <API_KEY>
python scripts/run_acceptance.py --mode http --base-url http://<host>:8000 --api-key <API_KEY>
✓
인수 러너 판정 규율: 정확 등급일치가 아니라 (1) 파싱 성공 + (2) 고등급 미탐 없음(severity floor). UNDER!(고등급 미탐)·파싱실패가 1건이라도 있으면 FAIL — 배포 전 반드시 0이어야 한다.

04 부팅 거부(fail-fast) 실값

poc_mode=full(lite-cloud 기본)은 startup에서 자격증명·게이트를 fail-fast 검증한다. 아래를 실값으로 안 채우면 부팅이 거부된다(무음 성공 방지 설계 — 오히려 안전).

키값 / 비고
API_KEY관리자 API 키 (강한 값)
ANTHROPIC_API_KEY (또는 OPENAI_API_KEY)외부 LLM
KOIPA_AUDIT_CHAIN_SECRETopenssl rand -hex 32 (NFR-SEC-01, 미설정 = 부팅 거부)
CORS_ALLOW_ORIGINS포털/프런트 origin 명시 (["*"]은 부팅 거부)
MINIO_SECRET_KEY객체스토어 시크릿 (lite-cloud는 storage_backend=minio)
CLASSIFIER_MODEL_DIR컨테이너 내 모델 경로. 설정 후 경로 부재면 부팅 거부(무음 rule-fallback 방지)

05 오픈망 특유 리스크 3건

lite-cloud는 원래 안전이 느슨한데 서버가 인터넷에 노출되므로, 테스트서버여도 이 3가지는 반드시 짚는다.

#리스크내용 · 조치
P1 외부 접속이 안 됨
(제일 헷갈릴 지점)		 prod overlay는 api를 127.0.0.1:8000에만 바인딩한다(내부망/리버스프록시 전제). 오픈망에서 외부가 붙으려면 앞에 nginx 리버스 프록시를 두거나 바인드를 바꿔야 한다. 그냥 up만 하면 "떴는데 외부에서 안 붙는" 상황.
P1 노출 구멍
키·CORS 미잠금		 오픈망은 스캐너가 바로 긁는다. ["*"] CORS + 약한 API_KEY 조합이면 테스트서버가 그대로 노출 구멍. API_KEY 강한 값 + CORS를 실제 origin으로 잠글 것.
P1 영업비밀 외부 반출
외부 LLM 전송		 오픈망이라 외부 LLM API가 가능하지만(폐쇄망은 불가), 반대로 분류 대상 본문이 외부 LLM으로 전송됨을 의미한다. 테스트 데이터가 실 민감문서면 사전 합의 필요 — 합성·공개 데이터로만 테스트 권장.

06 리허설에서 잡힌 함정 3건

2026-07-05 prod 경로를 로컬에서 그대로 재현하며 실제로 밟은 것. 같은 함정 반복 금지.

함정 1 · compose
override 자동 머지 금지
dev override가 GPU·Ollama를 강제해 GPU 없는 VM에서 실패. 반드시 -f로 base+prod만 명시하고 --env-file·ENV_FILE=을 같은 파일로.
함정 2 · 임베더
non-root HF 캐시 경로 불일치
prod 이미지는 uid1000으로 도는데 base compose가 HF 캐시를 /root/.cache/huggingface에 마운트 → 비-root가 못 읽어 bge-m3 매 기동 재다운로드(~2.5분). HF_HOME을 쓰기가능 볼륨으로 지정하거나 모델을 볼륨에 미리.
함정 3 · 이미지
GPU torch가 CPU VM에 ~10GB
CPU 배포인데 기본 torch가 CUDA 휠(~4GB)을 끌어옴. CPU 전용 torch 휠(--index-url .../cpu)로 바꾸면 이미지·다운로드가 크게 준다(테스트엔 무영향).

07 오픈망이라 안 챙겨도 되는 것

인터넷이 되므로 폐쇄망 배포의 부담이 통째로 빠진다.

오픈망의 이점 — 해당 없음 처리
  • 오프라인 번들 Linux 실빌드 불필요 — 인터넷 있으니 이미지 직접 빌드. 유일하게 남아있던 배포 P0(airgap 번들 재빌드)가 이 케이스엔 애초에 해당 없음.
  • 온프렘 vLLM/Qwen3-14B GPU 서버 불필요 — 외부 LLM API(Anthropic/OpenAI)로 대체.
  • GPU 불필요 — 추론·임베딩은 CPU로 충분(런북 전제).
  • 저장 암호화 키 불필요 — lite-cloud는 저장암호화 OFF라 STORAGE_ENCRYPTION_KEY 불요(단 onprem-local 하드닝 배포는 필수).

09 최단 배포 & 설치 확인 (E2E)

목표 = 테스트서버에 올려 문서 업로드 → 파싱 → 분류가 되는지 확인. 최대한 무설정으로.

한 줄 배포 — 무설정

bash scripts/deploy.sh 하나면 끝. .env.cloud가 없으면 자동 생성한다 — API_KEY·감사키는 랜덤 생성, STORAGE_BACKEND=local로 minio도 제거(startup 필수값이 API_KEY·감사키 둘뿐이 됨), LLM 키는 불필요(분류 핫패스는 LLM-free). 모델 아티팩트가 있으면 볼륨에 자동 적재, 없으면 룰 기반으로라도 등급이 나온다. 끝나면 화면에 API_KEY와 E2E 확인 방법이 출력된다.

설치 확인 — 한 방 스크립트

bash scripts/verify_install.sh
# 1) /healthz/ready 200   2) /healthz/deep 컴포넌트 상태   3) 문서 올려 파싱+분류
# → "설치 확인 PASS ✓ — 파싱·분류 E2E 정상"

문서 E2E — 3가지 방법

방법어떻게
데모 콘솔(브라우저)http://<서버>:8000/demo/parse_demo.html — 문서를 드래그하면 추출 텍스트·표·PII·등급이 바로 보임(가장 직관적)
커맨드 1건아래 /documents/analyze — 파일 하나 올려 파싱+분류 한 번에
인수 샘플팩배포 스모크가 자동 실행(전 포맷 TXT/PDF/DOCX/XLSX/HWPX × 등급, severity floor)
 
curl -s -X POST http://<서버>:8000/api/v1/documents/analyze \
     -H "X-API-Key: <배포시 출력된 API_KEY>" \
     -F "file=@내문서.pdf" | jq .
# 반환: parse(추출방식·품질·char_count·표·PII) + 분류 등급(TS/S1/S2/S3)
▲
브라우저 접근 — api 는 하드닝상 127.0.0.1:8000에만 바인딩된다. 원격에서 데모 콘솔을 열려면 SSH 터널이 가장 간단·안전: ssh -L 8000:127.0.0.1:8000 <user>@<서버> 후 로컬에서 http://localhost:8000/demo/parse_demo.html. 서버에서 직접 curl localhost:8000은 터널 없이 바로 된다.
◆
판정 기준: 이 E2E의 확인 포인트는 두 가지 — (1) 파싱(추출 텍스트·char_count가 나오는가), (2) 분류(등급이 산출되는가). 모델 아티팩트가 없으면 룰 기반 등급이라 정확도는 낮지만 파이프라인 동작 자체는 확인된다. 실제 분류 품질을 보려면 분류기 아티팩트(v-dd3abab9)를 artifacts/에 두면 자동 적재된다.
