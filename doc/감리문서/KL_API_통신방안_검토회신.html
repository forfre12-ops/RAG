0. 결론 세 줄

#사안회신
1연계 방식 1안(REST 직접 연동) 채택 권고. 2안(Redis Stream)은 당사에 소비자 구현이 없어 신규 개발이 필요하고, 1안이 제공하는 신뢰 전달(재시도·DLQ)을 이미 갖추고 있습니다
2결과 반환 항목 label 만으로는 연동이 성립하지 않습니다. confidence · status · warnings 를 함께 받으셔야 합니다
3요청 절차 등록 → 분류 2단계다. 등록을 건너뛰면 200 응답을 받고도 결과가 저장되지 않습니다

1. 초안의 표기 오류 — 확인 요청

규약 문서라 먼저 짚는다. 인터페이스 목록과 상세의 메서드가 어긋나 있습니다.

IF-03POST /classify/callbackGET /api/v1/classify/callback본문 전송이므로 POST 가 맞다. 덧붙여 이 경로는 관리시스템이 여는 수신 경로이며 분류 엔진의 라우트가 아니다 — 엔진은 요청 본문의 callback_url 로 결과를 보낸다(§4)

또한 IF-01 의 경로는 당사 실제 구현과 다릅니다.

2. 요청 절차 — 2단계다

가장 중요한 조정 사항. 초안은 POST /classify 하나에 파일을 실어 보내는 1단계 구조다. 당사 엔진은 문서 등록과 분류가 분리되어 있고, 등록 없이 분류를 호출하면 HTTP 200 을 반환하면서도 분류 결과가 저장되지 않습니다. 응답만 보면 정상으로 보이므로 현장에서 발견하기 어렵다.

2-1. 실제 절차

① 문서 등록
   POST /api/v1/documents
   Content-Type: multipart/form-data
   Authorization: Bearer <토큰>          (또는 동일 오리진 세션 쿠키)

   form-data
     file          (필수) 원본 파일
     actor         (필수) Actor JSON 문자열 — 없으면 422
                   예: {"user_id":"kl-portal","role":"kl_backend"}
     external_ref  (선택) KL 문서번호. 예: KL-2026-000123
     security_marking / access_scope   (선택) 상향 게이트 입력
   → 응답에 doc_id(UUID) 발급 · 원본은 AES-256-GCM 으로 암호화 저장

② 분류 요청
   POST /api/v1/classify/async
   Content-Type: application/json
   Authorization: Bearer <토큰>

   { "doc_id": "3f2a9c14-...",              ← ①이 발급한 UUID
     "callback_url": "https://portal/…/callback" }
   ※ content 는 넣지 않습니다. 생략하면 ①에서 저장한 본문을 사용합니다.
   → job_id 즉시 반환

③ 완료 통보 (엔진 → 관리시스템)
   POST {callback_url}
   { "job_id": "...", "status": "done", "results": [ { ... 20필드 ... } ] }
인증. 화면이나 요청 본문으로 자격증명을 받지 않습니다. 서버가 같은 오리진 세션 쿠키 또는 Authorization 헤더로 신원을 확인하며, 미인증이면 401 을 반환합니다. 실제 자격증명은 본 문서를 포함한 어떤 문서에도 기재하지 않고 별도 안전 경로로 전달합니다.

doc_id 가 문서 테이블에 없으면 분류는 수행되지만 이력·조회·검수 대상 목록에 남지 않습니다. 경고 문자열 하나만 응답에 붙는다. 따라서 ①을 생략할 수 없습니다.

3. 결과 반환 항목 — 확대 요청

초안의 콜백 항목은 5개(doc_id · success · etc · file_name · label)다. 당사 응답은 20필드이며, 그중 검수 라우팅에 반드시 필요한 것이 빠져 있습니다.

우선필드없으면 무엇이 안 되는가
필수status이 건을 사람이 봐야 하는지를 알 수 없다(needs_review)
필수confidence검수 우선순위를 매길 수 없다(저신뢰 우선 정렬)
필수warnings왜 검수로 보냈는지 설명할 수 없습니다
권장evidence검수자가 근거 없이 본문 전체를 다시 읽어야 합니다
권장rule_grade · model_grade룰·모델 불일치를 화면에 표시할 수 없습니다
권장model_version어느 모델이 판정했는지 추적할 수 없다(감사 대응)
참고scores · decision_path · automation_assessment판정 근거 심층 확인용
왜 이것이 규격 문제가 아니라 설계 문제인가. 본 시스템의 목표는 정확도가 아니라 미탐 최소화이며(RFP 성능요건), 그 목표는 확신이 낮은 건을 사람에게 돌려 달성합니다. 등급만 전달되면 모든 건이 자동확정된 것과 같아지고, 검수 라우팅 설계 전체가 작동하지 않습니다.

4. 콜백 — 이미 구현되어 있습니다

초안 협의사항의 “Callback 실패 처리 · 재시도 기준”은 신규 개발 항목이 아닙니다. 현행 구현이 다음을 이미 제공합니다.

기능구현 내용
콜백 주소 지정요청 본문의 callback_url 필드
신뢰 전달Outbox 패턴 — 결과를 먼저 적재하고 별도 배송기가 발송합니다
재시도지수 백오프. 발송 주기 60초
영구 실패 처리최대 시도 소진 시 DLQ 이동 + 지표 노출(koipa_outbox_dlq_total)
SSRF 차단루프백·클라우드 메타데이터·사설 대역 주소를 콜백 대상에서 거부

따라서 귀사에서는 콜백 수신 엔드포인트만 준비하시면 됩니다.

5. Redis Stream 방식(2안)에 대한 의견

권고하지 않습니다. 기술적으로 불가능해서가 아니라, 1안이 이미 제공하는 것을 새로 만들어야 하기 때문입니다.
항목현황
Stream 소비자 구현되어 있지 않습니다. 당사 Redis 용도는 작업 큐 브로커와 Outbox 저장소이며, Stream 자료구조는 DLQ 한 곳에서만 씁니다. 요청 소비 루프는 신규 개발입니다
미소비 Timeout 감시 초안은 관리시스템 Scheduler 가 미소비 요청을 감시하는 구조인데, 1안에서는 불필요하다 — 엔진이 job 상태를 보유하고 콜백으로 통보하며, 조회 엔드포인트도 있습니다
파일 전달 Base64 는 본문을 약 33% 키우고, 공유 mount 는 원본 암호화 저장을 우회한다(§5-1)
스트림 키 이름 초안은 kopia: 접두사를 쓰는데, 당사 시스템 식별자는 전부 koipa 다(패키지·DB·컨테이너·도메인). 채택 시 koipa: 로 통일 요청
접속 비밀번호 초안 5쪽에 실값이 기재되어 있습니다. 문서에서 제거하고 별도 안전 경로로 전달하실 것을 요청드립니다

5-1. 파일 공유 mount 방식에 대한 별도 의견

초안은 “같은 환경에서 구동되므로 mount 로 읽을 수 있을 것”이라 적고 있습니다. 당사 폐쇄망 설계는 원본 문서를 AES-256-GCM 으로 암호화해 저장합니다. 관리시스템이 평문 원본 경로를 넘기고 엔진이 그 경로를 직접 읽으면 이 암호화 저장 경로를 지나치게 됩니다. 등록 API(POST /api/v1/documents)를 통해 반입하시면 암호화 저장이 보장됩니다.

공통장애·예외 처리당사 API 는 HTTP 상태코드로 분기합니다. 심볼릭 오류코드 체계는 없으므로 상태코드 기준으로 처리 로직을 세워 주시기 바랍니다

7. 당사가 제안하는 인터페이스

번호경로방향용도
IF-01GET /api/v1/healthz관리 → 엔진준비 상태 확인
IF-02POST /api/v1/documents관리 → 엔진문서 등록(multipart) → doc_id
IF-03POST /api/v1/classify/async관리 → 엔진비동기 분류 요청(callback_url 포함)
IF-04POST {callback_url}엔진 → 관리완료 통보(결과 본문 포함)
IF-05GET /api/v1/classify/jobs/{job_id}관리 → 엔진상태 조회(콜백 유실 대비 보조 수단)
IF-06GET /api/v1/classify/{doc_id}관리 → 엔진문서 단위 결과 조회 — 사람이 확정한 등급 포함
IF-06 에 대한 보충. 사람이 검수로 등급을 확정해도 label(예측 등급)은 바뀌지 않습니다. 모델이 무엇이라 했는지와 사람이 무엇으로 정했는지를 두 가지 모두 남기는 설계이기 때문입니다. 확정 등급은 별도 필드(confirmed_label · confirmed_by · confirmed_at)로 제공됩니다.
