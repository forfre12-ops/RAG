본 규약은 KL 포털과 AI 엔진 사이의 연동 방식을 확정한 것이다. 협의 대상이 아니라 확정 사항이며, KL 은 이 문서대로 구현하면 된다. 메타데이터 필드의 값 목록 정의는 KL연동_인터페이스_규약서_ICD, 엔드포인트 전체 명세는 API_정의서 에 있다. 본 규약의 절차는 시험 서버에서 실제로 실행해 확인했다(§9).

1. 확정 사항

#항목확정근거
1문서 식별자2 단계 호출. 등록으로 받은 UUID 를 판정 요청에 쓴다. KL 문서번호는 external_ref 로 보관한다 판정 결과 저장은 tb_documents 에 해당 행이 있어야 진행된다. 임의 UUID 는 저장되지 않는다
2등록 입력원본 파일(multipart). 텍스트만 있는 문서는 .txt 로 감싸 올린다 텍스트 추출·정규화·개인정보 마스킹이 FUN-022 로 AI 엔진 요건이다. 추출 방식·품질이 품질 격리 게이트의 입력이라 텍스트만 받으면 그 게이트가 동작하지 않는다
3메타데이터 3 필드등록 시점에 전달. 판정 요청에서는 생략한다 엔진이 판정 시 저장된 문서 메타데이터를 자동으로 채운다(요청값 우선, 없는 것만 보완). 문서 속성이므로 재분류마다 다시 보낼 이유가 없다
4결과 회신동기 응답이 기본. 대량은 비동기 요청 후 폴링. 웹훅 콜백은 쓰지 않는다 실측 응답 366ms 로 동기 처리에 충분하다. 콜백은 엔진에서 포털로 나가는 연결이 필요해 폐쇄망 방화벽 정책이 늘어난다. 아웃박스 구현은 있으므로 필요 시 전환한다
6중복 문서파일 내용 해시로 중복 제거. 같은 내용은 기존 doc_id 를 재사용한다 재등록으로는 메타데이터와 external_ref 가 갱신되지 않는다(실측). 변경분은 판정 요청의 metadata 로 전달한다
5검수 화면AI 엔진 콘솔을 사용한다. KL 포털은 문서 상세에서 링크로 연결한다 검수·등급확정(FUN-024)은 “등급 확정까지”의 AI 엔진 구간이다. 포털에 다시 구현하면 판정 근거·판정 경로 표시를 중복 개발해야 한다

응답의 doc_id 가 이후 모든 호출의 키다. 값을 채울 수 없는 메타데이터 필드는 빈 문자열이 아니라 전송하지 않는다.

메타데이터를 등록 시점에 주면 판정 요청에서는 생략해도 된다. 엔진이 저장된 값을 자동으로 채워 넣는다. 판정 요청에 값을 함께 보내면 그 값이 우선한다.

3-1. 같은 파일을 다시 올릴 때

문서는 파일 내용 해시로 중복을 제거한다(file_hash 유일 제약). 내용이 같은 파일을 다시 등록하면 새 문서가 만들어지지 않고 기존 doc_id 가 반환된다.

상황엔진 동작KL 처리
같은 내용을 다시 등록기존 doc_id 반환보관 중인 doc_id 를 쓰면 되므로 재등록할 필요가 없다
재등록으로 메타데이터 변경 시도저장된 값이 갱신되지 않는다 보안표시·접근범위가 바뀌었으면 판정 요청의 metadata 로 전달한다. 재업로드로는 반영되지 않는다
재등록으로 external_ref 변경 시도갱신되지 않는다 최초 등록 시 확정한다. 하나의 파일 내용에 하나의 KL 문서번호를 대응시킨다
내용이 다른 파일새 doc_id 발급정상 등록

실측 2026-08-26 — 같은 파일을 source_type=internal 로 등록한 뒤 source_type=public 으로 재등록했으나 저장된 값은 internal 로 유지되었다.

5-1. 확정은 예측을 덮어쓰지 않는다

검수자가 등급을 확정해도 분류 결과의 예측 등급은 그대로 보존된다. 사람의 판단은 별도의 교정 기록으로 남고, 이 기록이 재학습 입력이 된다. 감사 관점에서 “모델이 무엇이라고 했는지”와 “사람이 무엇으로 정했는지”를 모두 남기기 위한 설계다.

확정 시 바뀌는 것값KL 이 알아야 할 점
분류 행의 상태status → confirmed확정 여부는 여기서 확인한다
분류 행의 예측 등급변경되지 않는다label 은 예측 등급이며 확정 등급이 아니다. 확정 등급은 같은 응답의 confirmed_label 로 받는다
교정 기록원 등급 · 확정 등급 · 방향 · 검수자 · 사유확정 등급의 정본이다
검증 라벨확정만으로는 생성되지 않는다승격(POST /promotions/promote) 후에 생성되며, 이후 재분류 시 그 등급이 반환된다

따라서 KL 은 한 번의 조회로 예측 등급과 확정 등급을 모두 받는다.

확정 등급은 문서 단위로 유지된다. 교정 기록은 확정 당시의 분류 결과에 붙는데, 같은 문서를 다시 분류하면 교정이 없는 새 결과가 생긴다. 조회는 문서 기준으로 확정 등급을 찾으므로 재분류가 있어도 사람이 내린 판단은 사라지지 않는다. 이 경우 status 는 needs_review, confirmed_label 은 이전 확정값으로 함께 나온다 — “예전에 확정했고 그 뒤 다시 분류되어 아직 확정 전”이라는 뜻이다.
실측 2026-08-26 — 문서 기준으로 바꾸기 전에는 배치 재분류 직후 confirmed_label 이 null 로 떨어졌다.
GET /api/v1/classify/{doc_id} { "label": "S2", ← 모델 예측 (확정해도 바뀌지 않는다) "status": "confirmed", ← 확정 여부 "confirmed_label": "S1", ← 사람이 확정한 등급 · KL 이 반영할 값 "confirmed_by": "reviewer-01", "confirmed_at": "2026-08-26T02:24:05+00:00" }
확정 전에는 confirmed_label·confirmed_by·confirmed_at 이 null 이다. KL 은 confirmed_label 이 채워졌는지로 확정 여부를 판단해도 되고 status 를 봐도 된다.
시험 서버에 반영되어 있다(2026-08-26 배포·검증 완료).

9. 연동 시험 시나리오

#시나리오합격 기준사전 검증
1내부 문서 등록 후 판정등록 응답에 doc_id 존재. 판정 응답에 persistence skipped 경고가 없을 것통과
2공개 출처 문서 판정source_type=public 전달 시 등급이 공개(S3)로 상한 처리될 것통과
3보안표시 있는 문서 판정security_marking=top_secret 전달 시 등급이 TS 로 상향될 것통과
4검수 대기 처리status=needs_review 문서가 GET /review-queue 에 나타날 것통과
5검수 확정과 교정 기록확정 후 status 가 confirmed 가 되고 교정 기록이 남을 것. 조회 응답의 confirmed_label 이 확정 등급과 일치할 것통과
6대량 배치배치 요청이 202 를 반환하고 완료 건수를 확인할 것통과
