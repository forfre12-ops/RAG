## A. 프로젝트 전체 (5문항)

### Q1. 이 프로젝트 한 문장으로 소개해주세요
> 한국지식재산보호원이 발주한 AI 영업비밀 관리시스템에서, **문서를 자동으로 4단계 보안등급으로 분류하는 AI 엔진**을 우리 로이드케이가 담당하고 있습니다. KL이라는 협력사가 웹시스템·보관함·권한 같은 18개 기능을 만들고, 우리는 학습·추론·평가의 AI 코어 6개 기능을 만들어 REST API로 통합합니다.

### Q2. 본인의 역할은 무엇입니까?
> AI 엔진 전반의 **설계와 구현을 리드**합니다. 구체적으로는 (1) PoC 단계 기술 스택 선정·검증, (2) FastAPI 기반 6개 모듈 아키텍처 설계, (3) KL과의 16개 REST 인터페이스 명세 정의, (4) DB 스키마와 능동학습 루프 설계입니다.

### Q3. 가장 어려운 부분은 무엇이었나요?
> **실데이터 부족**입니다. 영업비밀은 정의상 외부 공개 불가라 학습 데이터를 구하기 어렵습니다. 그래서 (1) AI Hub·공공데이터 같은 공개 데이터, (2) LLM(Claude/Qwen3) 합성 데이터 1,500건, (3) 운영 중 관리자가 수정하는 능동학습 데이터 — 이 3중 전략으로 해결합니다.

### Q4. 마감/리스크가 큰 항목은 뭔가요?
> **FNR(미탐율)** 입니다. 고등급 문서를 저등급으로 잘못 분류하면 곧바로 영업비밀 유출 사고로 이어집니다. 그래서 손실함수 비대칭 가중치, Confusion Matrix 모니터링, 능동학습 루프에서 underclass(미탐) 10건 누적 시 즉시 재학습 — 세 단계로 방어합니다.

### Q5. 현재 진행 상황은?
> **PoC 단계**입니다. 설계 8종, OpenAPI 명세, DB v2 스키마, FastAPI 스캐폴드 완료. 5개 PoC(P1~P5) 일정이 짜여 있고, 첫 검증인 헬스 체크·규칙 폴백 분류는 통과한 상태입니다. 발주처 가이드 문서 수령과 GPU 확정 후 본 실행 들어갑니다.

## B. 모델 선택 (6문항)

### Q6. 왜 BERT 계열이에요? 요즘은 LLM도 분류 잘하잖아요
> 세 가지 이유입니다: **(1) 속도** — 14B LLM은 분류 1건에 수초·달러, BERT 184M은 초당 수십건이며 비용 거의 0. **(2) 정확도** — 4-class 분류는 인코더 모델이 디코더보다 SOTA. **(3) 해석성** — attention rollout으로 근거 span 추출 가능. 단, LLM은 다른 역할에 적극 활용합니다: 합성 데이터 생성과 RAG 추론 보강.

### Q7. 왜 KF-DeBERTa인가요? 그냥 KLUE-BERT나 KoBERT는요?
> **도메인 적합도** 때문입니다. KF-DeBERTa는 카카오뱅크가 한국어 + 금융·법률·경제 코퍼스로 사전학습한 모델입니다. 영업비밀 문서는 90% 이상이 경영·기술·법무·계약 텍스트라 정확히 이 도메인입니다. KLUE-BERT는 뉴스 도메인, KoBERT는 위키 도메인이라 일반화 성능은 좋지만 우리 도메인엔 약합니다. DeBERTa의 disentangled attention 구조 자체도 분류 SOTA급입니다.

### Q8. 한국어 임베딩 모델은 왜 KURE-v1?
> 고려대 NLP&AI Lab이 **BGE-M3를 한국어 retrieval 데이터로 fine-tune한 모델**입니다. 동일 아키텍처라 BGE-M3의 dense+sparse+ColBERT multi-vector 출력 호환이 유지되면서, 한국어 retrieval에서 Recall@1을 1.6%p 끌어올렸습니다. MIT 라이선스, 1024차원, 8192 토큰. 베이스가 동일하므로 인덱스 재구축 없이 모델만 swap 가능 — 운영 리스크 낮은 게 큰 장점입니다.

### Q9. OSS LLM은 왜 Qwen3? 한국어 SOTA는 EXAONE 아닌가요?
> 두 가지 이유입니다. **(1) 라이선스**: Qwen3-14B는 Apache 2.0이라 공공사업·온프레미스 배포 안전. EXAONE은 LG 별도 라이선스 확인이 필요해 채택은 검토 단계입니다. **(2) thinking 모드**: Qwen3는 `enable_thinking` 동적 전환을 지원해 합성처럼 빠른 다량 생성에는 OFF, 평가나 라벨링 경계 판단에는 ON으로 활용할 수 있습니다. vLLM 0.8.5+ 공식 지원도 운영상 큰 이점입니다.

### Q10. Claude를 상용 기본값으로 한 이유는?
> **한국어 합성 품질**입니다. GPT-4o와 Gemini도 후보였지만, 한국어 공문체·법률체 자연스러움에서 Claude Sonnet 4.6이 가장 좋다는 정성평가가 다수입니다. 200K~1M 컨텍스트라 가이드라인 전체를 한 번에 넣고 일관된 합성이 가능한 점도 큽니다. 다만 Adapter 패턴으로 추상화해서, 비용·정책 따라 GPT/Gemini로 교체 가능합니다.

### Q11. Fine-tune 안 하고 LLM zero-shot으로 분류하면 안 돼요?
> 시도해볼 수 있지만 두 가지 문제가 있습니다: **(1) 기업별 변동성** — 같은 매출 자료도 A기업은 1급, B기업은 2급일 수 있는데 zero-shot LLM은 이걸 일관성 있게 못 잡습니다. **(2) FNR 통제 불가** — 비대칭 가중치, early stop, class weight 같은 fine-tune 전용 기법으로 미탐을 줄여야 보안 시스템 요구사항을 만족합니다. 그래서 BERT fine-tune이 정답이고, LLM은 RAG 컨텍스트 보강용으로만 씁니다.

## C. RAG·임베딩 (4문항)

### Q12. RAG를 왜 분류에 쓰나요? 검색이지 분류가 아니지 않나요?
> 분류 모델 출력을 **기업 맥락으로 보강**하기 위해서입니다. 4단계 등급의 절대 기준은 KOIPA 가이드라인이지만, 운영 시에는 기업별 사내규정·정책에 따라 달라집니다. 그래서 기업별 사내규정을 Elasticsearch에 임베딩해두고, 추론 시 dense kNN + BM25 + RRF 하이브리드로 Top-K를 가져와 BERT 출력에 가중치를 줍니다. RAG는 **선택 옵션**이라 자원 부족 기업은 끌 수 있습니다.

### Q13. RAG를 BERT 모델 입력 토큰으로 넣지 않은 이유는?
> **학습-추론 불일치** 때문입니다. BERT는 시퀀스 분류로 학습되어서 외부 컨텍스트를 입력 토큰으로 결합하면 학습 시 본 분포와 달라집니다. 그래서 RAG는 **후처리 보강 레이어**로 처리합니다: BERT가 등급 확률을 내면, RAG Top-K 청크의 라벨 분포 가중평균으로 최종 등급을 보정. 이 방식이 학습 안정성과 RAG 효과 모두 잡습니다.

### Q14. 왜 Elasticsearch로 정했나요? Qdrant·Milvus·pgvector도 봤어요?
> 네 가지 모두 비교했습니다. 초기 매트릭스는 Qdrant 1순위였지만, KL 사전 인터뷰에서 ES 운영 표준화 의사를 확인하고 **Elasticsearch 8.14+로 변경**했습니다. 결정 요인은 (1) KL 기존 인프라 재사용으로 운영 단일화, (2) `dense_vector` HNSW + BM25 + RRF 하이브리드로 영업비밀 검색의 키워드+의미 동시 수용, (3) Kibana·ILM·audit log 등 컴플라이언스 도구 표준 제공. **pgvector는 자체 결정으로 제거**(어댑터 미작성 + ES와 기능 중복), Qdrant는 즉시 롤백 경로로 유지합니다. 자세한 전환 설계는 doc/13에 정리돼 있습니다.

### Q15. ColBERT 같은 late interaction은 왜 안 써요?
> KURE-v1과 BGE-M3가 **이미 dense + sparse + multi-vector(ColBERT 스타일) 출력을 동시 지원**합니다. 그래서 별도 ColBERT 인덱스 없이 하나의 모델로 하이브리드 서치를 구현할 수 있습니다. ES 8.14+ retriever API + RRF로 dense kNN과 BM25 결합이 표준 지원되므로, multi-vector 없이도 영업비밀 도메인에 충분한 검색 품질을 확보할 수 있습니다.

### Q14-1. (보강) ES로 바꾸면 추가되는 위험은 없나요?
> 세 가지를 식별했습니다. (1) ES는 JVM 기반이라 Qdrant 대비 메모리 2~3배 — 발주처 노드 사양 확인 필요(E5). (2) `retriever` API는 8.14+ 기능 — KL 버전이 미만이면 legacy `rank.rrf` 폴백(E1). (3) DLS는 Platinum 라이선스 — Basic만 가능하면 인덱스 분리로 우회(E3). 세 위험 모두 K1 회신 부록 E1~E8로 명시 질의 중이고, 각 시나리오별 대응안이 doc/13 §7·§11에 들어 있습니다.

## D. 데이터·학습 (5문항)

### Q16. 데이터 4000건이면 너무 적지 않나요?
> 맞습니다. 그래서 세 전략을 씁니다: **(1) 사전학습 모델 활용** — KF-DeBERTa는 이미 한국어 + 금융·법률 도메인 사전학습이 끝났으므로 head만 학습. 4,000건이면 충분합니다. **(2) 능동학습** — 운영 중 관리자 수정으로 데이터 누적, 임계 도달 시 자동 재학습. **(3) 합성 데이터** — LLM으로 1,500건 추가 + 검수. 데이터셋 자체는 정적이지 않고 운영하며 진화합니다.

### Q17. 합성 데이터의 위험은 없나요?
> 두 가지 위험과 대응이 있습니다: **(1) LLM 스타일 흔적** → Claude 70% + Qwen3 30% 혼합 생성으로 다양성 확보, **(2) 라벨 누설** → 시스템 프롬프트에 "등급명을 본문에 직접 표기 금지" 명시 + 검수자 재확인. 또 합성 데이터는 절대 단독으로 쓰지 않고 공개 데이터·실데이터(가능 시)와 섞어 씁니다.

### Q18. Class imbalance 어떻게 처리하나요?
> 두 단계입니다. **(1) 데이터 단계**: 등급별 분포를 의도적으로 조정 (TS 15%, S1 25%, S2 30%, S3 30%) — 운영 분포보다 고등급 over-sample. **(2) 학습 단계**: `class_weight = inverse frequency`로 CrossEntropyLoss 가중치. 추가로 고등급 미탐에 ×3~×5 비대칭 cost를 줘서 FNR 우선 최적화합니다. 손실함수 가중치는 DB의 `classification_levels.loss_weight`에 외부화돼 있어 학습 코드 변경 없이 조정 가능합니다.

### Q19. Train/Val/Test 분할 어떻게?
> **Stratified 70/15/15**, seed 고정(재현 가능). 분할은 `training_datasets` 테이블에 영구 기록해서 모델 버전과 매핑됩니다. Test셋은 절대 학습 데이터와 섞이지 않게 합성/공개/실데이터 비율을 분할 전 결정하고, 검수자 간 일치도(Cohen's Kappa ≥ 0.75)도 사전 확인합니다.

### Q20. GPU 부족하면 어떻게 해요?
> KF-DeBERTa-base는 184M이라 **VRAM 16GB(예: RTX 4080)에서 batch_size=8로 충분**합니다. 24GB+면 batch_size=16으로 가속. 더 작으면 KoELECTRA-base(110M) 경량 옵션으로 전환 가능. 양자화(INT8/INT4)도 추론 단계에 적용 가능한데, 현재는 분류 정확도 우선이라 FP16 유지 계획입니다.

## E. 운영·인프라 (5문항)

### Q21. 왜 Docker compose예요? Kubernetes 안 써요?
> **기업 환경 도입 시 부담 최소화**가 첫 번째 이유입니다. 지원기업 IT팀이 K8s를 다룰 줄 모를 수 있습니다. docker-compose는 `up -d` 하나로 6개 서비스 일괄 기동, 학습곡선 거의 없습니다. 대규모 멀티테넌트로 확장되면 K8s 마이그레이션 가능하도록 각 서비스를 stateless하게 설계했습니다(상태는 PG/MinIO/Redis로 외부화).

### Q22. 모델 업데이트는 어떻게 하나요? 무중단인가요?
> **무중단**입니다. 모델 가중치는 Docker 이미지가 아니라 **MinIO 볼륨**에 저장합니다. 새 모델 학습 완료 시 (1) MinIO에 가중치 업로드, (2) `model_versions`에 등록 (status=Staging), (3) 관리자 승인 시 `is_active` 플래그 swap, (4) FastAPI가 다음 추론 요청부터 새 가중치 lazy load. 롤백도 같은 메커니즘으로 `rolled_back_from` 컬럼 사용.

### Q23. 동시 요청 많으면 어떻게 처리해요?
> 두 패턴 구현돼 있습니다. **(1) 동기 API**: `/classify` — 8KB 이하 단일 문서, p50 800ms. **(2) 비동기 큐**: `/classify/async`, `/classify/batch` — 대용량/RAG ON/일괄 1000건. Celery worker가 Redis 큐에서 받아 처리, 결과는 Postgres에 저장하고 KL이 polling 또는 webhook으로 받습니다. 학습·합성도 같은 패턴.

### Q24. 보안은 어떻게 했어요?
> **다층 방어**입니다: **(1) API Key 인증** + 호출자 Actor 메타로 모든 행위 감사 로그 (`audit_log` 테이블, 본문은 SHA-256 해시만 저장), **(2) 멀티테넌트 격리** — `tenant_id` 기반 모든 쿼리 필터링 + Qdrant 네임스페이스 분리, **(3) PII 자동 필터링** — 합성 단계 정규식 검증 + 검수자 재확인, **(4) 영업비밀 텍스트는 PG에 직접 저장 안 함** — MinIO 볼륨 분리 + URI만 PG. 또 모든 API 호출이 request_id로 추적 가능합니다.

### Q25. 모니터링은요?
> **3축 옵저버빌리티**: **(1) Prometheus** — FastAPI 요청수/지연/에러율, 모델 추론 시간, RAG 적중률 메트릭 수집. **(2) Grafana** — 대시보드 (KL UI와 별도 운영용). **(3) Loki** — 구조화 JSON 로그. 추가로 MLflow가 모델 실험·평가지표를 별도 추적합니다. FNR 임계 초과 시 Prometheus Alertmanager로 자동 알람.

## F. 코드·아키텍처 (5문항)

### Q26. 왜 FastAPI예요? Django REST는요?
> 세 가지 이유: **(1) OpenAPI 자동 생성** — KL과 16개 엔드포인트 합의를 코드에서 자동 추출, 문서-코드 불일치 위험 제거. **(2) Pydantic 타입 검증** — 잘못된 호출을 명확한 에러로 즉시 차단. **(3) 비동기 native** — LLM API, GPU 추론, DB I/O 모두 비동기. Django는 동기 모델이라 LLM API 대기 시 worker 효율이 떨어집니다.

### Q27. LangChain 꼭 필요해요? 직접 SDK 호출하면 안 돼요?
> 두 가지 이유로 채택했습니다: **(1) 요구사항 명시** — FUN-003에 "LangChain 기반 프롬프트 체인 구성"이 명시되어 있어 사실상 강제. **(2) LLM Provider 추상화** — `ChatPromptTemplate` + `OutputParser`로 OpenAI/Anthropic/Google/vLLM 동일 인터페이스. Provider 교체할 때 프롬프트만 두고 한 줄 변경. 다만 단순 호출엔 오버엔지니어링이라 PoC 초기엔 직접 SDK 쓰고 합성 본 실행 단계에 LangChain 도입 계획입니다.

### Q28. LangGraph는 어디 써요?
> **능동학습 루프(FUN-024)** 입니다. "추론 → 관리자 검수 → 승인/재라벨 분기 → 재학습 트리거 임계 도달 판단 → 학습 → 평가 → 승격/거부" 같은 분기·대기 흐름은 if/else로 짜면 코드가 산만해집니다. LangGraph는 상태 그래프로 표현해서 가독성·디버깅·시각화 모두 좋습니다. Postgres `corrections.consumed_in_run` 상태가 그래프 노드 전이 트리거가 됩니다.

### Q29. 모듈 6개는 어떻게 나눴어요?
> **단일 책임 + FUN-ID 1:1**: M1 합성(003) / M2 전처리(022) / M3 라벨링(023) / M4 학습(004) / M5 추론(005) / M6 평가(024). 각 모듈은 추상 인터페이스 + 구현 클래스 + Pydantic DTO + 영속화 스키마로 구성. 모듈 간 의존은 `의존 매트릭스`로 명문화해서 순환 의존 방지. M2·M3는 M4·M5가 공유, LLM Adapter는 M1·M4·M5가 공유.

### Q30. 만약 처음부터 다시 한다면 뭘 바꾸시겠어요?
> 두 가지입니다. **(1) DB 스키마를 v1부터 정규화로 시작** — v1은 PoC 빠른 시작을 위해 JSONB 위주로 시작했는데, 결국 v2에서 `classification_levels`·`document_factor_scores`·`level_keywords` 정규화로 재작업했습니다. 처음부터 운영급으로 갔으면 좋았을 것. **(2) LangChain 적용 시점** — 초기에 직접 SDK 호출로 시작해서 PoC 검증 후 LangChain 도입 계획인데, 실은 처음부터 LangChain으로 시작하는 게 합성 단계 재작업을 줄였을 것 같습니다.
