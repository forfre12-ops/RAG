운영 런북

KOIPA 영업비밀관리시스템의 운영 절차서 — 일상 점검, 모니터링, 모델 배포·롤백, 장애 대응, 큐·비동기 관리, 재해 복구. 운영자가 정상·비상 상황에서 무엇을 어떤 순서로 수행할지 규정한다.

상태 범례

운영중 현재 동작 · 보강 본개발 정밀화 · 예정 본개발 신규

01일상 운영

일일 점검 체크리스트

  • 헬스체크 — /api/v1/healthz/{live,ready,deep}. live는 프로세스 생존, ready는 의존성(DB·벡터·LLM) 실측(실패 시 503), deep은 전체 점검.
  • 서비스 기동 확인 — api·worker·beat 컨테이너가 모두 올라와 있는지 점검. worker는 모든 큐를 구독하고, beat는 단일 인스턴스만 동작해야 한다(아래 §05).
  • 핵심 지표 — 분류 처리량, 오류율, 지연(p95), 방향성 FNR/FNR_TS, 검수 대기 건수.
  • 큐 상태 — Celery 큐 깊이(classify·index·synthesis·learning·celery), outbox 미처리, DLQ 크기.
  • 주기작업(beat) — drift·auto-rollback·outbox·active-learning·파티션 롤오버 tick이 정상 발행·소비되는지 확인(미발행 시 폐곡선 자동화 정지).
  • 드리프트 — 검색·분류 품질 드리프트 자가측정값.
02모니터링 · 관제

관측 지표

Prometheus로 RED 지표(Rate·Error·Duration)와 업무 지표(분류량·FNR·검수 대기)를 수집한다. 3-tier 헬스체크는 의존성을 실측하며, 스토리지 무음 폴백 같은 숨은 열화도 탐지한다.

관측 옵션 (환경변수)

운영 환경에 맞춰 다음 관측 기능을 켤 수 있다. 모두 미설정 시 기존 동작 보존(no-op)이며, 로그 수집기·트레이싱 백엔드 구성에 따라 선택 적용한다.

옵션설정동작
구조화(JSON) 로깅LLOYDK_LOG_JSON=1API·워커 로그를 JSON 라인으로 출력(request_id 상관관계). 로그 수집기(예: Loki/ELK) 연동 시 권장.
드리프트 연속위반 임계LLOYDK_DRIFT_CONSECUTIVE_REQUIRED (기본 1)단발 스파이크 오탐 억제 — drift 알람을 N회 연속 위반 시에만 발생. 2~3 권장.
OTel 비즈니스 spanOTel provider 설정 시 활성추론·검색 핵심 경로를 수동 span으로 노출(미설정이면 no-op). 식별자·등급·신뢰도만 부착, 문서 본문 비포함.
본개발 보강

알람 룰·Grafana 대시보드를 리포지터리에 포함, Celery 큐 깊이·DLQ 크기를 지표로 노출. OpenTelemetry 트레이스 연동.

03모델 거버넌스 (배포 · 롤백)

모델 배포 절차

표준 순서: 학습 → 서빙경로 평가 → 게이트 판정 → 활성화 → reload → 검증.

#단계내용
1평가실배포(서빙) 경로 전체를 통과해 측정 — 캘리브레이션·FNR-safe 오버라이드 포함. 원시 argmax 측정 금지(미탐 9배 과소평가).
2게이트FNR-safe 게이트 통과 시에만 배포 승인(예: fnr_high 지표 부재 시 배포 거부 = fail-secure).
3활성화tb_model_versions.is_active 전환 (activate). 롤백 시 직전 버전으로 되돌림.
4reloadPOST /admin/model/reload — 각 서빙 프로세스가 활성 모델을 메모리에 재적재(무중단).
5검증reload 후 헬스·샘플 추론으로 새 모델 반영 확인.
⚠ 현재 빈틈 (P0)

활성화는 DB is_active만 바꾸고, 각 서빙 프로세스가 reload를 개별 수신해야 반영된다. 여러 레플리카(파드)에 reload를 브로드캐스트하는 메커니즘이 없어, 안전 롤백이 일부 레플리카에만 적용될 위험이 있다. 본개발에서 Redis pub/sub 또는 버전 폴링으로 전체 레플리카 팬아웃을 배선한다. 또한 auto_rollback·auto_activate는 기본 OFF이므로, 모니터링을 동반해 활성 결정을 내린다.

캘리브레이션 운영

서빙은 모델 디렉토리의 temperature.json(온도 스케일링 보정값)을 읽어 confidence를 재산정한다. 보정 산출 절차:

  • 출력 위치 — calibrate_classifier.py의 --output 기본값은 <model-dir>/temperature.json이다(서빙이 읽는 위치). --output을 생략하면 보정 결과가 서빙 경로에 정확히 떨어진다.
  • 실 데이터 필수 — 실제 val logits 없이 더미로 만든 온도는 배포 금지. 도구는 fail-loud로 종료(exit 1)하며, 검증·CI 목적이면 --allow-dummy를 명시해야 한다.
  • 미보정 시 거동 — temperature.json 부재 시 서빙은 T=1.0(무보정)으로 동작한다(over-confident 위험).

폐쇄망 번들 — 학습모델 동봉

폐쇄망(에어갭) 배포 번들에는 학습된 분류기 가중치와 보정값을 반드시 동봉해야 한다. 베이스(HF) 모델만 포함하면 폐쇄망에서 미학습·무보정으로 동작한다.

  • 학습 가중치 포함 — build_offline_bundle.py에 --classifier-model-dir(또는 env CLASSIFIER_MODEL_DIR)로 학습 디렉토리를 지정하면 가중치+config와 temperature.json이 번들의 models/classifier-trained로 복사된다.
  • 누락 시 경고 — 미지정 시 베이스 모델만 번들되며 경고가 출력된다(폐쇄망에서 rule-fallback). temperature.json이 빠지면 무보정 경고가 추가된다.
  • 마이그레이션 포함 — 번들에는 alembic 마이그레이션 전체가 포함되며, 배포처에서 alembic upgrade head로 baseline+후속 revision(파티션 백필 포함)을 적용한다.

05큐 · 비동기

Celery 워커 · beat 운영

비동기 작업은 작업 종류별 큐로 라우팅되며(classify·index·synthesis·learning·celery), 주기작업은 별도 beat 컨테이너가 발행한다. 두 컨테이너 모두 정상 기동·구성돼야 폐곡선 자동화가 동작한다.

구성요소역할운영 주의
worker라우팅된 비동기 작업 소비-Q classify,index,synthesis,learning,celery로 모든 큐를 구독해야 한다. -Q 없이 기동하면 default(celery) 큐만 소비 → 다른 큐로 라우팅된 작업이 영영 소비되지 않는다.
beat주기작업 트리거 발행전용 컨테이너 필수. 없으면 drift·롤백·outbox·파티션 롤오버 등 자동화가 전혀 동작하지 않는다. 단일 인스턴스만 띄울 것(다중 beat = 중복 tick).

주기작업 (beat schedule)

작업주기내용
drift 점검15분운영 임베딩 드리프트 자가측정 → 임계 초과 시 알람 게이지.
active-learning30분검수 누적 임계 도달 시 재학습 권고/큐잉(+일별 03:00 스냅샷). 학습 사이트(지재원)에서만 실효 — 추론 전용 고객사에선 트레이너가 없어 큐잉이 무동작이고, 보정은 로컬 룰·진단용으로만 누적된다.
auto-rollback 점검60분활성 모델 라이브 미탐 회귀 점검(기본은 판정·로깅만, opt-in 시 실제 롤백).
outbox 배송60초enqueue된 콜백 실송신. 실패는 지수 백오프, max_attempts 후 DLQ.
파티션 롤오버매일 02:10향후 N개월 월 파티션 자동 생성(_default 비대화 방지). 아래 참조.
폐곡선 범위 · 재학습 주기

위 beat 자동화 중 active-learning→재학습 구간은 학습 사이트(지재원) 한정이다. 고객사는 추론 전용이라 그 tick은 무동작이며, 검수 보정은 로컬에 누적돼 룰·키워드·임계 보정과 진단(Confusion Matrix)에만 쓰인다. 고객사 보정을 지재원으로 반출할지는 미확정이다(확인 5, 기본 권고: 문서 무반출·집계 진단만). 모델은 상시 재학습되지 않으며, 실데이터 1차 학습(2026-09) 후 드리프트·이벤트 트리거 시 단발 재학습한다.

파티션 롤오버

  • 자동 연장 — beat가 매일 02:10 ensure_partitions_tick을 호출해 향후 N개월 월 파티션을 미리 생성한다(CREATE TABLE IF NOT EXISTS 멱등). 대상: tb_chunks·tb_llm_usage·tb_audit_log.
  • 배포 시 백필 — 신규 배포 시 마이그레이션 e5f6a7b8c9d0을 적용해 13개월치 월 파티션을 선생성한다(alembic upgrade head). 이후는 beat가 매일 연장.
  • 미동작 시 영향 — beat·롤오버가 정지하면 신규 행이 *_default 파티션에 누적돼 프루닝이 무력화되고, 나중에 정상 파티션 attach 시 default 검증 락이 운영을 막는다.
  • 지연 복구 — 이미 _default에 해당 월 행이 쌓인 뒤에는 자동 생성이 충돌·실패할 수 있다(경고만 남기고 beat는 계속 동작). 이 경우 수동 detach/move 절차가 필요하다.

비동기 처리 · DLQ

비동기 작업은 Celery + outbox(Redis ZSET) 패턴으로 처리하며, 실패 작업은 DLQ(Dead Letter Queue)로 격리된다. 가시성 타임아웃으로 중복 처리를 방지하고, 멱등성 미들웨어(Idempotency-Key)가 재시도 중복을 막는다.

DLQ 드레인 절차: ① DLQ 항목 원인 분류 → ② 일시 오류는 재투입, 영구 오류는 보류·기록 → ③ 재처리 후 잔량 0 확인.

⚠ 현재 빈틈 (P0)

/classify/async·/batch가 Celery delay() 대신 요청 스레드에서 인라인 실행하고 202를 반환한다(대량 배치 시 타임아웃). rate limiter·idempotency·job_store는 Redis 우선이나 무음 메모리 폴백이라 멀티워커에서 중복 실행 위험. 본개발에서 실제 classify_async.delay() 배선 + Redis 강제(폴백 fail-closed)로 전환한다.

06롤백 · 재해 복구

롤백 · DR

  • 모델 롤백 — 성능 열화 임계 초과 시 직전 버전으로 activate. 자동 롤백은 모니터링 동반 활성.
  • 백업 — DB·원문 스토리지 정기 백업, 복구 시점 목표(RPO)·복구 시간 목표(RTO) 정의(본개발).
  • DR 드릴 — dr_drill로 감사 체인 무결성·복구 절차를 주기 점검.
  • 감사 체인 동시성 — 감사 로그 해시 체인은 PostgreSQL advisory lock으로 직렬화돼, 동시 기록 시에도 체인 무결성이 보장된다(트랜잭션 종료 시 자동 해제). 모델 활성 전환도 동일 방식으로 직렬화된다.
