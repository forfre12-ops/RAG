검수 관리자 사용자매뉴얼 — AI 거버넌스 관제콘솔

한국지식재산보호원/지재원 영업비밀 자동 등급분류·RAG 시스템의 거버넌스 관제콘솔(admin.html) 검수 관리자 조작 절차서. 분류 → 검수(확정·재라벨) → 재학습·활성화 → 실시간 관제 → 골든셋 서명의 폐곡선을 화면 단위로 안내한다. 모든 동작은 기존 /api/v1 엔드포인트를 호출하며, 상태 변경 작업은 Safe Mode 해제 후에만 실행된다.

범위 · 기준

본 매뉴얼은 관제콘솔(admin.html)과 골든셋 서명 화면(signoff.html)의 검수 관리자 조작만 다룬다. KL 포털 인증·격리, 회원사 업로드 화면, 파싱·분류 시연(분류 콘솔의 #sec-parse 구역)은 범위 외다.

01접속 · 인증 · Safe Mode

관제콘솔(admin.html)은 API 서버가 서빙하는 단일 화면으로, 분류 → 검수 → 재학습 → 모델 리로드 → 메트릭의 거버넌스 폐곡선을 한 곳에서 조작한다. 모든 버튼은 기존 /api/v1 엔드포인트를 호출한다. 운영 배포 호스트 주소는 [발주처 입력].

접속 절차

  1. 브라우저로 관제콘솔(admin.html)에 접속한다. 상단 우측 연결 확인 헬스 표시가 자동 실행된다(GET /healthz).
  2. 「연결 · 인증 컨텍스트」 카드에서 API Base를 확인한다(기본 /api/v1, 다른 호스트면 전체 URL).
  3. X-API-Key에 발급받은 키를 입력한다(값은 화면에 노출되지 않음; 발급 절차 [발주처 입력]).
  4. Actor Role을 선택한다(검수=reviewer, 재학습·배포=admin).
  5. User ID (actor)에 실계정을 입력한다(교정 라벨러 신원으로 기록됨).
  6. 헬스체크 실행을 눌러 상단 헬스 표시가 정상으로 바뀌는지 확인한다.

Safe Mode (쓰기 작업 허용)

기본값 = 차단

「쓰기 작업 허용」 체크박스는 기본 해제 상태다. 체크하지 않으면 확정·재라벨·재학습·모델 활성화·핫리로드 같은 상태 변경 작업이 실행되지 않고, 조회·분류 시연만 수행된다. 상태 변경이 필요한 절차(§03·§04·§06)를 시작하기 전 반드시 체크한다.

운영 배포 시 확인

개발 기본에서는 X-Actor-Role 헤더가 신뢰된다(api_key_trust_actor_role_header=True). 운영(poc_mode=full)에서는 헤더 자칭을 무시하고 .env의 API_KEY_ROLE로 역할을 고정한다(값: [발주처 입력]).

02문서 분류 실행

「분류 실행」 카드에서 문서를 분류한다(FUN-003 등급분류·005 결과처리). 등급 결정 핫패스는 LLM 없이 인코더 PLM 분류기(FUN-004)가 수행하며, 결과는 S·V·M 3요소와 근거 키워드로 설명된다.

단건 분류

  1. 샘플 선택 드롭다운에서 골든셋 예시(등급별 2건, 총 8건)를 고르거나 doc_id·제목·본문을 직접 입력한다.
  2. 분류하기를 누른다(POST /classify).
  3. 결과에서 등급·신뢰도·모델 버전·소요(ms)와 검수 필요/게이트 통과 배지를 확인한다.
  4. S·V·M 3요소 카드와 근거 키워드 칩으로 판단 근거를 확인한다. warnings가 있으면 함께 표시된다.

일괄 분류

골든셋 8건 일괄 분류는 4등급(TS·S1·S2·S3) 8건을 순차 분류해 검수 큐에 적재하고, 기대 등급 일치 수를 요청 로그에 남긴다.

03검수 큐 처리 (확정 · 재라벨)

자동 확정되지 않은 needs_review 분류를 검수자가 확정하거나 재라벨한다(FUN-024·005). 이 루프는 회원사 운영 교정 루프이며, 골든셋 검수·서명(§06)과는 별개다.

Safe Mode 확인

확정·재라벨은 상태 변경(쓰기) 작업이다. 시작 전 「연결 · 인증 컨텍스트」의 쓰기 작업 허용을 체크한다. 미체크 시 차단 경고만 뜬다.

처리 절차

  1. 신뢰도 게이트(기본 0.70)를 확인한다. 신뢰도가 게이트 미만이거나 warnings가 있으면 「검수 필요」로 플래그되고, 이상이면 자동 확정 후보다.
  2. DB 검수 큐 불러오기를 누른다(GET /review-queue). 서버측 needs_review 대기 목록을 FIFO로 조회하며, 브라우저 세션과 무관하게 실제 대기 건을 본다. 상단 rq-info에 대기 건수가 표시된다.
  3. 각 항목의 doc_id·제목·본문 미리보기·현재 등급·신뢰도·상태 배지를 검토한다.
  4. 등급이 타당하면 확정 (현 등급)을 누른다(POST /confirm).
  5. 등급이 틀리면 재라벨 드롭다운에서 올바른 등급(TS·S1·S2·S3)을 고르고 재라벨 전송을 누른다(POST /relabel). 원 등급과 동일하면 확인 대화상자가 뜬다.

04재학습 · 모델 활성화 (배포 게이트)

누적 교정을 반영해 재학습하고, 검증된 모델 버전을 배포(활성화)한다. 활성화는 회귀 모델의 무심한 배포를 막는 deploy gate를 거친다.

재학습 트리거 (POST /train)

재학습 라우터는 enable_training(full-train 프로파일)에서만 활성이다. 비활성 프로파일에서는 404가 정상이다(프로파일 활성화 여부 [발주처 입력]).

  1. training_type을 선택한다(incremental · full · hyperparam_search).
  2. base_model(kf-deberta-base)과 use_rag 여부를 확인한다.
  3. 재학습 제출을 누른다(admin 역할). 잡 ID와 상태 URL이 로그에 남는다.
  4. 작업 목록 새로고침으로 잡 상태(queued/running/done/failed)와 model_version·트리거를 확인한다.

모델 활성화 · 배포 (POST /admin/model/activate)

  1. 활성화할 version_label을 입력한다(예: 현행 활성본 v-fe4b386b · 직전 배포본/롤백 타깃 v-dd3abab9).
  2. 활성화 (배포)를 누른다. 현재 활성본 대비 deploy gate(고등급 미탐 FNR·F1 회귀)가 적용되고, 하드닝 프로파일에서는 사람서명 locked_gold_eval readiness까지 요구한다.
  3. 결과 배지를 확인한다 — 활성화됨 / 게이트 차단(blocked) / 미활성.
  4. 게이트 차단 시 회귀 내용을 확인한다. 정당한 사유가 있을 때만 force (게이트 우회)를 체크하고 재시도한다(확인 대화상자 발생, forced=true로 감사 기록).
  5. 활성화 성공 시 프로세스 재기동 없이 자동 핫리로드된다. 필요하면 활성 모델 핫리로드(POST /admin/model/reload, admin)로 수동 반영한다.
force 우회 주의

force=true는 deploy gate를 무시하고 고등급 미탐 회귀 모델도 배포한다. 반드시 회귀 지표를 확인한 뒤에만 사용하며, 우회 사실은 감사 체인에 남는다. rollback·자동 배포는 거버넌스 스케줄러·CLI가 담당한다.

05실시간 관제 · 대시보드 해석

「실시간 관제」 토글을 켜면 관제 대시보드와 검수 큐를 주기적으로 읽기 전용으로 자동 조회한다. 확정·재라벨·재학습·활성화 같은 쓰기는 폴링하지 않는다(Safe Mode와 무관).

자동 갱신 조작

  1. 자동 갱신 드롭다운에서 주기를 선택한다(끄기 · 3 · 5 · 10 · 30초).
  2. 상태 표시를 확인한다 — 실시간 갱신 중(녹색) / 갱신 오류 · 재시도 중(적색) / 정지. 우측에 마지막 갱신 시각이 표시된다.
  3. 수동 조회는 관제 종합 새로고침(GET /admin/dashboard, admin 전용)을 누른다.

대시보드 패널 해석

각 패널은 독립 best-effort로 로드된다. 일부 소스가 미가용이면 그 패널만 degraded로 표기되며, 대시보드 전체가 500 오류로 죽지 않는다.

모델 메트릭 (수동 조회)

「모델 메트릭 · FNR 게이트」에서 최신 메트릭 · 이력 · 혼동행렬 · 등급체계 조회를 수동으로 조회한다(값은 재학습 때만 변하므로 폴링에서 제외). 정확도 · F1(macro) · FNR 전체 · 등급별 FNR을 확인하며, FNR이 5%를 넘으면 적색으로 강조된다. 혼동행렬은 먼저 최신 메트릭으로 활성 모델 버전을 로드한 뒤 조회한다.

06골든셋 검수 · 서명

골든셋 검수·서명은 지재원 관리자 권위로 골든 후보를 locked_gold_eval(사람서명 평가정답)로 승격하는 절차다. 운영 교정 루프(§03)와 별개이며, 배포 readiness(§05)를 채우는 유일한 경로다. 지정 검수자 [발주처 입력].

1) 골든 후보 생성

  1. 「골든셋 후보 빌더」에서 provider(noop/local_openai/vllm_qwen/anthropic/openai), n, require_evidence를 설정한다.
  2. 후보 생성 시작을 누른다(POST /golden/build, admin·kl_backend·system). golden_job_id가 발급된다.
  3. 상태 조회로 done을 확인하고, 리뷰 HTML 열기로 검수·서명 화면을 연다(review.html — 2026-08-18부터 signoff.html과 같은 화면이다).

2) 화면 서명 (signoff.html · review.html — 같은 화면)

  1. 서명 화면(/golden/jobs/{job_id}/signoff.html 또는 /review.html)을 연다. 링크에 붙은 ?t=는 화면을 여는 열쇠일 뿐 신원이 아니다.
  2. 로그인이 필요하다. 좌측 아래 「SIGN-OFF IDENTITY」에 로그인 계정이 표시된다. 「로그인 필요」가 보이면 그 링크로 로그인한 뒤 이 페이지를 새로고침한다. 화면은 검수자 이름·API 키를 받지 않는다 — 서명자는 로그인 쿠키(JWT sub)로만 확정된다(2026-08-17).
  3. 「서명 전 점검」 띠를 확인한다. 붉은 띠(제출할 수 없습니다)면 막힌 항목을 먼저 해결해야 하며 제출 버튼이 잠긴다. 노란 띠는 경고일 뿐 제출을 막지 않는다.
  4. 각 후보 카드에서 본문(「읽기 좋게 / 원문 그대로」 전환) · 룰/LLM 등급 · 판정 루브릭을 확인하고 승인(등급 유지) / 등급변경(드롭다운) / 거부 중 하나를 선택한다. 필요 시 메모를 남긴다. 판단 근거는 원문이 정본이다.
  5. 룰·LLM이 등급에 합의하지 못한 후보는 같은 목록에 보기 전용으로 섞여 있다(결정 폼이 없다). 내용만 확인하고, 확정은 골든셋 후보 관리 화면에서 한다.
  6. 평가정답을 즉시 반영하려면 라이브 반영(publish)을 체크한다(기본은 미리보기 — 라이브 무변경).
  7. 서명 제출을 누른다(POST /golden/jobs/{id}/signoff). 결과에서 locked 승격 건수 · 거부 사유 · readiness를 확인한다.
  8. 결정은 이 브라우저에 잡 단위로 남는다(서버 전송 아님). 창을 닫았다 다시 열면 「결정 N건을 복원했습니다」가 뜨고 이어서 할 수 있다. 「지우고 새로 시작」으로 버릴 수도 있다.

판정 루브릭

S×V×M

8=TS · 4=S1 · 1·2=S2 · 0=S3(S=0이면 S3). S1 vs TS 분기는 M — S2·V2에서 M=0 → S1(관리 미공식화), M≥1 → TS. 확신이 없으면 거부한다(미탐 안전).

서명 무결성 · 주의

서명자 신원

화면은 검수자 이름·API 키를 받지 않는다. 이름을 손으로 적을 수 있는 한 원장에 남는 서명자는 자칭이기 때문이다(2026-08-17 입력칸 제거). 토큰은 사람마다 따로 발급하고, 한 토큰을 여러 명이 쓰면 원장에 같은 이름만 남아 검수 기록이 성립하지 않는다. 고등급 TS/S1 이중서명 토글은 2026-08-06 제거됐다 — RFP·RTM에 근거가 없었다.

  • reviewer_id는 실계정만 허용된다. 머신/플레이스홀더 계정은 403으로 거부된다.
  • 화면은 이름을 보내지 않으며, 서버는 어떤 경로로 들어오더라도 reviewer_id를 인증 신원(JWT sub)으로 교정한다(위조 차단).
  • 미결정 후보는 제출에서 제외된다.
  • 정본 골든셋은 직접 변경되지 않는다. 승격분은 별도 locked_gold_eval 경로에 doc_id 기준으로 누적된다.
