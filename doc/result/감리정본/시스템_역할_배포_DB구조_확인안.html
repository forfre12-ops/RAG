2026-06-29 운영 전제 업데이트: 실데이터 0 · 빌드 검수 0 · 반출 0 제약에서는 배포 전 정확도 검증을 주장하지 않는다. 합성/LLM 라벨은 학습 시드·상대비교·회귀 테스트용이며, locked_gold_eval은 사람 서명 전용이다. 현재 목표는 "검증된 분류기 배포"가 아니라 룰 우선 안전 부트스트랩 + 보수적 검수 라우팅 + 운영 관리자 확정에서 배우는 루프다. 이 문서의 기존 F1/FNR/PASS 수치는 합성·OOD·프록시 또는 메커니즘 검증으로만 해석한다.

KOIPA AI 영업비밀 등급분류 시스템의 역할 분담(KL↔한국지식재산보호원)·배포 토폴로지(지재원/고객사)·DB 구조를 정리한 확인안입니다. 아래 구조가 맞는지 검토·확정 부탁드립니다. §6에 확인·합의가 필요한 항목을 모았습니다.

한눈에 보기   한국지식재산보호원 = "AI 엔진(합성·학습·분류·검수)",   KL = "관리시스템·인프라·고객사 운영".
① 지재원(중앙)에서 한국지식재산보호원가 학습·골든셋을 만들어 → ② 오프라인 매체로 → ③ 고객사(폐쇄망)에 배포. 고객사 운영·DB는 KL.
현 소스 기준 고객사 런타임은 Koipa 애플리케이션 DB 단일 테이블 세트로 동작한다. KL 원천 문서/EDMS/권한 시스템은 external_ref·API 계약으로 연동하며, ai_agent/admin schema 분리는 아직 구현된 전제가 아니다.

제안요청서 기능요구(FUN) 기준. 한국지식재산보호원는 AI 코어 6개, KL은 관리시스템·인프라.

2 배포 토폴로지 — 지재원(학습) / 고객사(추론)

두 서버는 네트워크로 연결되지 않는다. 모든 전달은 보안매체(오프라인)로만.

3 DB 구조 — 현재 소스 기준 단일 애플리케이션 스키마

고객사 PostgreSQL 운영 주체는 KL일 수 있으나, 현재 DDL/ORM은 schema 분리 없이 Koipa 테이블을 같은 기본 스키마에 생성한다.

4 테이블 소유 경계

현재 소스 기준 테이블은 schema로 나뉘지 않는다. 소유 경계는 DB schema가 아니라 런타임 책임과 외부 연동 계약으로 구분한다.

5 데이터 흐름 (오프라인)

IN (지재원 -> 고객사) : 골든 번들 = 모델 + 골든셋 + 스키마 DDL(마이그레이션) + 앱 이미지 · 서명·체크섬 · 보안매체 반입 · KL이 설치(alembic upgrade) OUT (고객사 -> 지재원) : [확인 5 미정] 검수교정 반출 여부 자체가 결정 대상 · A안(기본) = 문서 무반출·집계 리포트만(메일·유선 수준) · B안 = 온사이트 학습(고객 망내 폐루프, TS미탐 치명 고객 기본권고) · C안 = 문서단위 반출 -> 재학습
확정고객사는 외부망과 통신하지 않는다(완전 폐쇄망) — 온프렘 LLM(Qwen3-14B·GPU)·번들 모델(분류기)·로컬 스토리지·로컬 DB로 완결. 분류 등급결정 핫패스는 LLM-free(분류기+룰+RAG검색+메타, 333ms); 온프렘 LLM은 RAG /answer 답변합성·선택적 2차판정 전용. 학습은 지재원에서만. 역방향 환류(고객사→지재원)는 미확정 — 반출 여부 자체가 §6 확인 5의 결정 대상이다(기본 권고: 문서 무반출·집계 진단만 환류).

6 확인 · 합의 필요

아래 항목이 위 구조의 전제입니다. 맞는지 / KL과 합의가 됐는지 확인 바랍니다.

확인 1고객사 DB 운영 주체 — 폐쇄망 고객사 PostgreSQL을 KL이 운영하고 Koipa 앱은 전용 계정으로 접속하는 전제가 맞나?
확인 2schema 분리 여부 — 현 소스는 단일 스키마/테이블 세트다. ai_agent/admin 분리가 필요하면 ORM/Alembic/권한 설계를 별도 변경해야 한다.
확인 3확장 설치 — KL PG에 pgvector(필수) 설치 가능한가? (벡터검색 필수) pg_bigm은 선택 — 한국어 후보생성 가속용이고, 랭킹은 코어 ts_rank(별도 확장 불요)가 담당.
확인 4DDL 적용 주체 — Koipa 마이그레이션을 KL이 적용하나, 아니면 Koipa 컨테이너에 일시 DDL 권한을 주나? 현재 구현에는 cross-schema FK가 없으므로 admin.tb_documents 선생성/REFERENCES 권한 전제는 적용되지 않는다.
확인 5보정 환류 — "포맷"이 아니라 "반출 여부"가 먼저다. 고객사 검수교정을 지재원으로 반출해 재학습하는 그림은 세 가지로 막힌다: ① tb_corrections를 DB→파일로 뽑는 export 도구가 아직 없다(현 import_review_corrections.py는 import 전용·트리거 미연결), ② 반출 포맷이 라벨(doc_id·model_label·human_label·reason)뿐이면 원문 텍스트가 없어 분류기 재학습 자체가 불가(학습은 Chunk.content 필요·원문은 고객사에만 존재), ③ reason 자유텍스트가 원문 발췌를 담을 수 있어 "메타데이터-only도 무해하지 않다". → 폐쇄망 고객이 문서단위 검수데이터 반출에 동의하겠는가를 먼저 결정해야 한다(컬럼 규약은 그 다음 문제). 두 채널을 구분하라 — ① 문서 채널(doc_id·원문·발췌)은 어느 안이든 망 밖으로 내보내지 않는다; ② 집계 진단 리포트(등급별 오분류율·혼동행렬 카운트·문서식별 불가)는 지재원이 현장 성능을 보고 고등급 사각지대의 우선순위를 잡는 용도다 — 단 이건 조준 신호일 뿐, 갭을 메우는 데이터가 아니다(보강할 실데이터는 지재원이 자기 공개·프록시 코퍼스에서 따로 확보하며, 고등급일수록 A안만으론 못 메운다 → B안). 양이 작아(혼동행렬 한 장 분량) 자동 반출 채널이 아니라 고정 양식의 정기 리포트를 메일·유선·정기보고로 전달하면 충분하고, 양식을 못박는 목적은 전송이 아니라 '문서식별 필드 없음'을 고객 보안팀이 1회 승인받기 위함이다. 아래 A/B/C 중 택1(②는 공통 필수).
