보안 설계서

KOIPA 영업비밀관리시스템의 보안 설계 기준 — 위협 모델, 인증·인가, 테넌트 격리, 감사 무결성, 데이터 보호. 이미 구현된 통제(객체수준 인가·멱등성 격리·상수시간 비교·XSS 방어·본문 DoS 가드·감사 체인 직렬화 포함)와 본개발에서 보강할 P0 과제를 함께 명시한다. 영업비밀을 다루는 시스템이므로 기밀성·무결성·추적성을 동급으로 설계한다.

상태 범례

구현 PoC 적용 완료 · 보강 본개발 정밀화 · 예정 본개발 신규 통제

01개요 · 범위

보안 설계 범위

본 시스템은 기업의 영업비밀 문서를 등급(TS·S1·S2·S3)으로 분류·저장·학습한다. 따라서 보안 목표는 ① 기밀성(등급·원문이 권한 없는 주체·다른 테넌트에 노출되지 않음) ② 무결성(분류·검수 이력이 위변조되지 않음) ③ 추적성(누가 언제 무엇을 했는지 부인 불가)이다.

통제는 애플리케이션 계층(인증·RBAC·테넌트 결속·감사 체인)을 중심으로 하며, KL 웹 시스템과의 연동 구간은 상호 인증(mTLS)으로 보호한다. 인프라(망분리·방화벽)는 발주처 운영 환경 정책을 따른다.

03인증 · 인가

인증 (Authentication)

두 가지 방식을 지원한다. ① API Key — 테넌트별로 발급한 키의 해시를 등록해 두고, 요청 헤더 X-API-Key를 대조한다. 공유키 대조는 상수 시간 비교(hmac.compare_digest)로 수행해 바이트 단위 early-exit 타이밍 사이드채널을 차단한다. ② JWT(RS256) — 공개키로 서명을 검증하며 클레임에 테넌트·역할을 담는다. 둘 다 미충족이면 401.

인가 (Authorization) — RBAC

역할은 admin·reviewer·kl_backend·system 4종이다. 엔드포인트별 require_role로 강제한다 — 예: 등급기준 변경(schema PUT)·키 회전·모델 reload는 admin 전용, 검수(relabel)는 admin·reviewer, 합성 생성은 admin·kl_backend·system.

적용됨

공유 키 비교를 상수 시간 비교(hmac.compare_digest)로 전환해 타이밍 공격을 차단했다. JWT 키 롤오버(kid)·JWKS 로드를 지원한다.

본개발 보강

키 주기적 회전 절차 수립, 키 해시를 bcrypt 표준으로 일원화(레거시 SHA-256 마이그레이션 경로 정리).

04테넌트 격리

멀티테넌트 데이터 격리

모든 업무 테이블은 tenant_id를 가지며, 요청의 권위 테넌트(인증 주체)와 대상 리소스의 테넌트가 다르면 403(TENANT_MISMATCH)으로 차단한다. 타 테넌트 리소스 ID를 추측해 접근하는 IDOR/BOLA 공격이 막힌다.

객체 수준 인가 (IDOR/BOLA 차단)

분류 계열 엔드포인트(/classify·/classify/stream·/classify/explain)는 요청 본문의 tenant_id를 인증 신원에 결속한다. JWT 모드는 서명된 tenant 클레임이, API Key 모드는 해시 검증된 X-Tenant-Id가 진실이며, 본문 tenant_id가 이와 다르면 403으로 거부한다. 이렇게 산정한 유효 테넌트로 이후 모든 문서 조회·검증 라벨·근거(evidence) 조회가 스코프되어, 위조한 tenant_id로 타 테넌트의 문서·근거 토큰을 열람하는 객체 수준 인가 우회가 차단된다. 스트리밍(SSE)도 스트림 개시 전에 결속·검증을 수행해 차단 시점을 앞당긴다.

적용됨

JWT에 tenant 클레임이 없는데 본문이 tenant_id를 주장하면 스코프 보증 불가로 403. 운영(poc_mode=full)에서 X-Tenant-Id를 주장하는데 해당 테넌트에 api_key_hash가 미등록이면 honor-system 통과를 막고 fail-closed 403으로 거부한다.

⚠ 현재 빈틈 (P0)

테넌트에 키가 미등록된 단일 공유키 모드에서는 요청 본문의 tenant_id를 신뢰하는 하위호환 분기가 남아 있다(주장한 테넌트 스코프 내로는 제한되나 임의 테넌트 지정 가능). 본개발에서 권위 테넌트 부재 시 거부(deny-by-default)로 전환하고 Postgres RLS(행 수준 보안)를 도입해 DB 차원에서도 격리한다. tenant_id=None 통과 분기는 제거한다.

05감사 무결성

감사 해시 체인

주요 행위(분류 확정·검수·등급기준 변경 등)는 tb_audit_log에 기록되며, 각 레코드는 직전 레코드의 해시 + 현재 내용으로 다음 해시를 만든다(블록체인식 연쇄). 중간 레코드를 조작하면 이후 해시가 전부 어긋나 위변조가 탐지된다. 감사 actor·tenant·role은 위조 가능한 헤더 대신 인증이 해소한 신원(request.state.auth_*)을 우선 기록한다.

체인 직렬화 (동시요청 분기 방지)

해시 체인은 본질적으로 선형이라, 동시 요청이 같은 직전 해시를 읽고 각자 다음 레코드를 만들면 체인이 분기(fork)해 무결성 검증이 깨질 수 있다. 이를 막기 위해 직전 해시 읽기와 신규 레코드 삽입을 Postgres advisory-lock 단일 트랜잭션으로 묶어 모든 감사 삽입을 직렬화한다(pg_advisory_xact_lock — 트랜잭션 종료 시 자동 해제). 동시 요청 간에도 단일 선형 체인이 보장된다.

⚠ 현재 빈틈 (P0)

체인 비밀키(audit_chain_secret)가 설정에 정의되어 있지 않아 기본값이 키 없는 SHA-256이다. DB 쓰기 권한을 가진 내부자가 전체 체인을 재계산해 조작할 수 있다. 본개발에서 ① 비밀키 설정 항목 추가 + 운영 환경에서 빈 키면 기동 거부(fail-fast) ② verify_chain 정기 검증 작업(cron) + 관리자 엔드포인트 ③ 불일치 시 알람을 배선한다.
