FUN-003-④ — LangChain을 쓰지 않았는데 왜 "기능은 동작한다"고 하는가
요건이 요구한 것은 "프롬프트 체인을 구성하여 보안등급 기준에 맞는 문서를 자동 생성"하는 기능입니다. 이 기능은 지금 정상 동작합니다 — 등급·도메인별 프롬프트 구성 → LLM 호출 → 형식·등급 자동검증 → 불합격 시 조건을 강화해 재시도 → 합격분만 검수 큐로 이관. 요건과 다른 점은 수단 하나뿐입니다. 이 체인을 LangChain이라는 외부 프레임워크 대신 자체 모듈(generator.py + adapters/llm)로 만들었습니다.
사유 ① 폐쇄망은 "가져갈 수 있는 짐"이 정해져 있습니다. 운영 서버는 인터넷이 끊긴 망이라, 설치되는 라이브러리는 함께 딸려 들어오는 하위 패키지까지 전부 사전 반입·보안검토·SBOM 등재 대상이 됩니다. LangChain은 프레임워크 자체보다 끌고 들어오는 의존성 묶음이 큽니다. 즉 검토·반입 부담은 확실히 늘어나는데, 그 대가로 새로 생기는 기능은 없습니다. 실제로 운영 이미지는 Dockerfile.api.prod에서 [psh,otel,jwt,hwp,hwp-tables,xls]만 설치하며, langchain은 선택 extra [orchestration]로만 선언해 배포본에서 뺐습니다.
사유 ② 이 시스템에서 LLM이 맡은 일이 단순합니다. 등급을 실제로 결정하는 본경로에는 LLM이 아예 없습니다(분류기 + 규칙 엔진). LLM은 학습용 샘플 문서 생성과 라벨 보조에만 쓰입니다. 이 작업은 "프롬프트 1회 호출 + 실패 시 재시도"로 끝나므로, LangChain이 제공하는 다단계 체인·에이전트·메모리·툴 호출이 들어설 자리가 없습니다. 실제로 필요한 통제는 adapters/llm/base.py가 이미 직접 갖고 있습니다 — 호출 1건당 토큰·비용·지연·실패코드를 llm_usage 테이블에 적재하고, full-jitter 지수 백오프를 provider 공통으로 통제합니다.
부수 효과 — 오히려 다른 요건을 더 안전하게 만족합니다. 프레임워크에 묶이지 않아 LLM 교체(Claude·GPT·Gemini·온프렘)가 코드 변경 없이 됩니다(FUN-003-⑥). 프레임워크 버전이 올라가면서 생성 파이프라인이 깨지는 위험도 없습니다.
결론 — 기능 미구현이 아니라 구현 수단의 차이이며, 폐쇄망 납품 조건에서 내린 판단입니다. 발주처가 LangChain 채택을 요구할 경우 build_provider() 위에 얇은 어댑터를 얹는 방식으로 대응 가능합니다(본개발 결정사항).
