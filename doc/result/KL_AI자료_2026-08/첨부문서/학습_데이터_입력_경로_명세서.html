본 문서는 “사람이 검수한 결과가 학습에 어떻게 들어가는가” 하나에 답한다. 등급을 어떻게 정하는지는 등급분류 알고리즘 명세서, 계층이 무엇인지는 골든셋 종합이 다룬다. 서술은 전부 코드에서 확인한 것이며, 확인하지 못한 것은 §8 에 그렇게 적었다.

1. 세 경로 — 한눈에

학습셋에 사람의 판단이 들어오는 길은 셋이고, 성격이 다르다. 하나는 합성 문서 검수, 하나는 골든셋 계층 분할, 하나는 운영 중 교정이다.

#경로입력 → 출력 실행요건
1 합성 검수 승인 → 학습행 tb_sample_documents(승인분) → {doc_id,text,label,source,domain} JSONL 사람이 실행 FUN-003 “검수 후 학습셋 편입”
2 골든 후보 → 학습 시드 gold_candidate → silver_train.jsonl / synthetic_holdout.jsonl 사람이 실행 FUN-004 학습 입력
3 운영 교정 → 학습셋 증강 tb_corrections(미소비) → 기본 train.jsonl 에 병합 자동(조건부) FUN-004 재학습
경로 1·2 는 사람이 명령을 실행해야 진행된다. 요건 문장은 “검수 후 학습셋 편입”까지이고 자동 편입을 요구하지 않는다. 경로 3 만 자동이며, 그마저 아래 §4 의 조건을 모두 만족해야 발화한다.

2. 경로 1 — 합성 검수 승인이 학습행이 되는 절차

검수자가 승인한 합성 문서를 학습행으로 바꾼다. SynthesisService.build_training_rows() 가 이 일을 한다.

2-1. 라벨을 무엇으로 삼는가

상황학습행의 라벨근거
검수자가 등급을 고쳤다corrected_level_id승인 단계의 판단이 생성 요청 시점의 목표 등급보다 뒤이고 더 정확하다
고치지 않고 승인했다target_level_id생성 시 요구한 등급이 그대로 유효하다

두 값을 한 칸에 뭉개지 않고 따로 둔다. 한 칸에 덮어쓰면 교정이 있었다는 사실 자체가 사라진다. 산출물에 grade_corrected 카운트를 함께 내보내므로, 학습셋 파일을 열어 보지 않고도 교정이 몇 건 반영됐는지 확인할 수 있다.

2-2. 무엇을 걸러내는가

승인됐어도 학습에 넣지 않는 것이 있다. 합성 생성기가 정상 산출을 내지 못한 경우다.

표시(label_source)무엇인가처리
noop_fallback본문 생성이 실패해 자리표시 문자열이 들어간 산출학습 편입 금지 — excluded_noise 로 계수
llm_nonjsonLLM 이 규정 형식(JSON)이 아닌 응답을 낸 산출학습 편입 금지 — excluded_noise 로 계수
—(본문이 빈 문자열)본문 길이 0제외 — excluded_empty 로 계수
제외를 조용히 버리지 않는다. 반환값에 approved_total / included / excluded_noise / excluded_empty / grade_corrected 를 사유별로 함께 낸다. 승인 건수와 학습행 수가 다를 때 그 차이가 어디서 왔는지 숫자로 설명된다.

2-3. 실행

cd poc
python scripts/build_synth_training_set.py --out datasets/synth_approved/train.jsonl

매 호출이 승인분 전체에서 다시 만든다(결정적·중복 없음). 이어 붙이는 방식이 아니므로 같은 명령을 두 번 돌려도 결과가 같다.

선행 조건 — DB 스키마. 이 경로는 tb_sample_documents.corrected_level_id 칸을 읽는다. 해당 칸은 2026-08-24 커밋 48405949 의 마이그레이션 f0a1b2c3d4e5 가 만든다. 마이그레이션이 적용되지 않은 서버에서는 이 경로뿐 아니라 합성 검수 목록 조회 자체가 실패한다 — 조회가 표의 모든 칸을 읽기 때문이다 (synth_repo.py select(SampleDocument)). 적용 여부는 select version_num from alembic_version; 한 줄로 확인한다.

3. 경로 2 — 골든 후보가 학습 시드가 되는 절차

골든셋은 한 덩어리가 아니라 계층으로 나뉘고, 계층마다 쓸 수 있는 용도가 다르다. 이 구분이 무너지면 시험 문제로 공부하고 그 시험을 보는 것(train-on-test)이 된다.

계층학습평가무엇인가
locked_gold_eval금지허용사람 서명이 끝난 평가정답. 학습에 넣으면 성능 수치가 무의미해진다
gold_candidate허용—자동 게이트를 통과했고 사람 서명을 기다리는 것
silver_train허용금지학습 시드 전용
legal_floor허용보조법적 기준으로 등급이 정해지는 것
held_review금지금지서명이 유효하지 않거나 본문이 합성인 격리분. 어느 쪽으로도 쓰지 않는다

held_review 는 서명 자격을 잃은 것이 학습 연료로 흘러드는 역방향 누수를 막으려고 명시적으로 둔 칸이다. “평가에서 뺐으니 학습에는 써도 되겠지”가 성립하지 않는다는 뜻이다.

3-1. 분할

golden_split.split_run_dir() 이 gold_candidate 를 등급으로 층화해 75/25 로 나눈다. 누수 행을 먼저 떨어내고 나누므로 결과가 결정적이다.

cd poc
python scripts/run_golden_split_signoff.py datasets/golden_runs/<run_dir>
  → silver_train.jsonl / synthetic_holdout.jsonl / split_stats.json

4. 경로 3 — 운영 교정이 재학습에 반영되는 절차

회원사에서 검수자가 등급을 고치면 tb_corrections 에 쌓인다. 이것이 자동으로 학습셋에 병합되는 유일한 경로다.

4-1. 라벨과 병합

항목내용
정답 라벨해당 분류의 가장 최신 교정의 corrected_level_code (검수자 최종 동의)
병합 대상train 만 증강한다. val·test(홀드아웃)는 건드리지 않는다
소비 규칙실제로 학습셋에 들어간 correction_id 만 소비 처리한다
소비 규칙이 중요한 이유 — 반영하지 않은 채 “소비했다”고 표시하면 그 교정은 영영 학습에 들어가지 못한다. 제외된 교정은 소비하지 않으므로 다음 실행에 다시 후보로 올라온다.

4-2. 누수 차단

교정 행이 홀드아웃(val·test)과 doc_id 또는 본문이 겹치면 train 병합에서 뺀다. 이 검사가 없으면 시험 문제가 학습셋에 섞여 배포 게이트가 재는 미탐률이 실제보다 좋게 나온다.

4-3. 언제 도는가

방아쇠주기발화 조건
active_learning_tick30 분 미탐 누적이 임계에 닿으면 즉시 재학습을 큐에 넣는다
nightly_incremental_retrain_tick매일 02:00 (KST) 기본은 등록되지 않는다. enable_nightly_retrain_schedule 을 켠 회원사에서만 등록된다

야간 무인 실행을 기본에서 뺀 이유는 셋이고, 전부 2026-08-08 실측이다(§7). ① 이 틱이 태우는 것은 증분분이 아니라 기본 TrainSpec — 5에폭 전체 미세조정이다. AVX 없는 서버에서는 2,042행에 약 13시간이라 02:00 에 시작하면 업무시간 내내 CPU 를 점유한다. AVX-512 8스레드에서도 약 4.5시간이라 야간 안에 끝나지 않는다(§7 실측). ② 고객사 프로파일 워커 4GiB 에서는 40초 만에 OOM 으로 죽는다. ③ 새벽에 실패하면 알아차릴 사람이 없다. 관리자가 버튼을 눌러도 목적(고객사 교정을 반출하지 않고 현장에서 반영)은 그대로 달성된다 — 반출은 어느 쪽이든 0 이다.

4-4. 어느 서버에서 도는가

노드프로파일학습 가드비고
지재원 학습·골든full-trainenable_training미탐 임계 도달 시 자동 재학습

4-5. 학습이 끝나면

재학습본은 후보로만 등록되고 자동으로 서비스에 올라가지 않는다. retrain_auto_activate 의 기본값이 꺼짐이다. 검증되지 않은 모델이 사람 확인 없이 운영에 나가는 것을 막는다.

활성화 여부는 사람의 인상이 아니라 자동 게이트가 정한다. 판정은 m6_evaluation/deploy_gate.py 의 evaluate_deploy_gate() 한 곳에서 하고, 결과는 tb_training_runs.final_metrics->'deploy'->'gate' 에 남는다. 원칙은 fail-closed 다 — 지표가 없거나 리포트가 깨져 판정할 수 없으면 통과가 아니라 거부다. 미탐을 치명으로 보는 설계에서 “측정 못 함”을 “이상 없음”으로 읽지 않기 위해서다.

검사거부 조건왜
degenerate혼동행렬의 한 예측 열이 99% 이상 차지전부 한 등급으로 찍는 모델은 지표가 좋아 보여도 분류가 아니다. 기준선 유무와 무관하게 무조건 거부한다
fnr_high_present후보에 fnr_high 지표가 없음고등급 미탐율을 못 재면 회귀 검증이 불가능하다. 보류한다(fail-closed)
fnr_high_regression후보 fnr_high > 기준선 + 0.02미탐이 나빠지는 모델은 다른 지표가 좋아도 올리지 않는다. 이 시스템의 1순위 축이다
f1_regression후보 F1-macro < 기준선 − 0.05미탐이 같아도 전반 성능이 크게 떨어지면 회귀다
first_deploy_fnr_floor기준선이 없을 때 fnr_high > 0.10비교 대상이 없는 최초 배포에도 절대 상한을 둔다
anchor_high_grade_miss앵커 평가에서 고등급(TS·S1) 미탐 칸이 1개라도 FAIL등급별 최소 보증을 지표 평균이 가리지 못하게 한다
metamorphic_forward_regression사실을 유지한 채 문체만 바꾼 쌍에서 등급이 내려간 위반율의 신뢰구간 하한 > 0표현이 바뀌었다고 등급이 내려가면 미탐 경로다. 표본이 5 쌍 미만이면 측정 불가로 두고 통과시키지 않는 대신 검사를 생략한다
검사 이름은 코드에 9 개가 있고, 한 실행에서 도는 것은 기준선 유무에 따라 갈린다 — 기준선이 있으면 fnr_high_regression · f1_regression 을, 없으면(최초 배포) baseline_present · first_deploy_fnr_floor 를 본다. 앵커·메타모픽은 리포트가 없으면 *_eval_skipped 로 기록된다 — 강제 옵트인 운영에서는 리포트 부재 자체가 거부 사유다. 위 도식이 이 갈래를 그린 것이다.

근거 — poc/src/koipa/modules/m6_evaluation/deploy_gate.py(검사 정의) · poc/src/koipa/config.py(retrain_fnr_high_tolerance 0.02 · deploy_gate_first_deploy_fnr_high_max 0.10). 강제 옵트인으로 앵커·메타모픽을 켜 둔 운영에서는 리포트가 없다는 사실 자체가 거부 사유다 — 리포트 생성이 조용히 깨졌는데 게이트가 통과하는 경로를 막는다.

5. 기본 학습셋 경로

위 세 경로가 증강하는 바탕 학습셋은 설정에서 온다.

항목값
디렉터리settings.training_dataset_dir
분할 파일train.jsonl · val.jsonl · test.jsonl
교정 병합 산출settings.retrain_dataset_dir/train_corr_<8자리>.jsonl

이 경로가 종전에는 코드에 datasets/labeled/… 로 박혀 있었고, 그 디렉터리는 리포에도 배포본에도 없었다. 그래서 하이퍼파라미터 없이 호출되는 경로(콘솔의 재학습 트리거, POST /train 기본형)가 배포 서버에서 항상 파일 없음으로 끝났다(2026-08-08 실측). 설정에서 끌어오도록 바꿔 학습셋 세대가 바뀌어도 코드를 고치지 않는다.

6. 문서 출처 — 라벨과 별개의 축

계층은 라벨이 얼마나 믿을 만한가를 말하고, 출처는 본문이 실제 문서인가를 말한다. 둘은 직교한다. 사람이 서명한 합성 문서가 있을 수 있고, 라벨이 약한 실문서도 있다.

출처무엇인가
public_real공개 실문서(판례·금융보고서 등)
customer_real고객사 실(비식별)문서 — 최종 운영 성능 근거
synthetic합성 생성물
unknown명시도 유도도 안 되는 것. 기본값이며 real 로 취급하지 않는다
최종 운영 성능의 근거는 실문서에서만 나온다. 합성만으로 학습한 분류기를 실문서에 적용했을 때 F1 이 0.26 이었다 — 안전하지만 자동화에는 쓸 수 없는 수준이다. 검수를 거쳤다고 해서 합성이 실문서가 되지는 않는다.
