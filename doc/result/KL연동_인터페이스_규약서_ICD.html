KL 연동 인터페이스 규약서
R6 S/V/M 메타데이터 (ICD)

KL 웹수집 계층이 Lloydk AI 코어로 전달하는 출처·보안표시·접근범위 메타데이터의 인터페이스 정의서(Interface Control Document). 이 메타데이터는 비공지성(S)·비밀관리성(M) 산정의 핵심 입력으로, 본문 텍스트만으로 판정 곤란한 축을 보완한다. 본 문서는 협의안(v0.9)이며 화요일 미팅에서 필드·값 도메인을 확정한다.

합의 필요 — 현재 갭

현행 API 명세(부록B)에는 metadata.source_type(출처) 1개 필드만 정의돼 있다. 그러나 R6은 보안표시·접근범위까지 받아 M(비밀관리성)을 산정해야 한다 — 이 두 필드는 아직 미정의 상태다. 본 ICD가 그 빈자리를 채우는 합의 초안이다.

01배경 · 책임 경계

왜 메타데이터가 필요한가 (R6)

비밀관리성(M)과 사실적 비공지성(S)은 문서 본문 텍스트만으로는 판정이 곤란하다. "이 문서에 극비 도장이 찍혔는지", "누구까지 열람 가능한지", "어디서 수집됐는지"는 문서 외부 정보이기 때문이다. 따라서 이 신호는 문서를 수집·보관하는 KL 웹계층이 메타데이터로 제공하고, AI 코어는 이를 S/M 산정 입력으로 받는다.

축본문 텍스트로 판정KL 메타데이터 필요
S 비공지성부분 가능 (출원 전·미공개 신호)출처(공개/내부) — Gate-1
V 경제적 유용성가능 (가치·복제 신호)불필요 (텍스트 충분)
M 비밀관리성곤란보안표시 + 접근범위
책임 경계

KL = 메타데이터를 수집·정규화해 채워서 전달(채울 수 없으면 명시적 null). 로이드케이 = 전달된 메타데이터를 S/M 점수로 환산하고 미전달 시 텍스트 기반 폴백. 메타데이터 값의 정확성은 KL, 점수 환산 로직은 로이드케이 책임.

02전달 방식

전달 방식 — 분류 요청의 metadata 객체

KL은 문서 분류 요청 시 POST /api/v1/classify(또는 비동기 /classify/async)의 metadata 객체에 아래 3개 필드를 담아 전달한다. 인증·테넌트 헤더는 기존 규약(X-API-Key)을 따른다.

POST /api/v1/classify
X-API-Key: <key>
Content-Type: application/json; charset=utf-8

{
  "doc_id": "KL-2026-000123",
  "tenant_id": "default",
  "content": "<문서 본문>",
  "metadata": {
    "source_type":      "internal",      // ① 출처 provenance
    "security_marking": "대외비",          // ② 문서 보안표시
    "access_scope":     "department"      // ③ 접근범위
  }
}
03필드 정의

메타데이터 필드 정의

3.1 source_type — 출처 provenance 선택(권장)

문서가 어디서 왔는지. 공개 출처면 비공지성 게이트(Gate-1)가 S=0 → S3로 강제한다. 미전달 시 doc_id의 저장 출처로 hydrate.

값의미S 영향
public공개 웹·보도·공시·뉴스레터S=0 (Gate-1)
registered_patent등록·공개 특허·실용신안S=0 (Gate-1)
academic학술 발표 논문·학위논문S=0 (Gate-1)
internal사내 비공개 문서·저장소텍스트로 S 산정
external_confidentialNDA 하 외부 수령(파트너·고객)텍스트로 S 산정
null / 미전달불명 — doc_id 저장출처로 hydrate폴백

3.2 security_marking — 보안표시 신규

문서에 찍힌 공식 보안 등급 표기. 명시표기는 등급 산정에서 최우선으로 반영된다(§4.4 명시표기 우선 규칙). 표기가 없으면 none.

값문서 표기 예M·등급 영향
top_secret극비 · 특급기밀 · Top Secret · Eyes-OnlyM=2 · TS 후보
secret1급 비밀 · 기밀M=2 · S1↑
confidential대외비M=1 · S2↑
none표기 없음접근범위로 M 산정

3.3 access_scope — 접근범위 신규

실제로 누구까지 열람 가능한지. 보안표시가 none일 때 M(비밀관리성) 산정의 주 입력이 된다(§4.7 M 앵커).

값의미M 매핑
approved_only승인된 자에 한해 공개 (물리·시스템 통제)M=2
designated지정된 접근자만 (NDA·열람 제한)M=1
department특정 부서·임직원 일부M=1
all_employees전 임직원 열람 가능M=0
null / 미전달불명텍스트 폴백(보수적)
04산정 매핑 · 폴백

메타데이터 → S/V/M 산정 규칙

① source_type 이 public/registered_patent/academic
        → S = 0  → S×V×M = 0 → S3 강제 (Gate-1, 내용 무관)

② security_marking ≠ none
        → 명시표기 우선: top_secret→TS후보 / secret→S1↑ / confidential→S2↑
          (M = 표기 등급, AI 등급보다 높으면 채택 — FNR-safe)

③ security_marking = none
        → M = f(access_scope):
             approved_only→2 / designated·department→1 / all_employees→0
        → S·V 는 본문 텍스트로 산정, 최종 = grade_from_svm(S,V,M)

④ 메타데이터 미전달(null)
        → 텍스트 단독 폴백. M 불명 시 보수적으로 검수 라우팅
          (silent 하향 금지 — 미탐 방지)
미전달 시 동작 — fail-secure

메타데이터가 비어도 분류는 수행한다(텍스트 폴백). 단 M 불명으로 등급이 애매하면 공개(S3)로 떨어뜨리지 않고 검수 라우팅한다. "메타데이터가 없어서 공개로 흘리는" 미탐 경로를 차단하기 위함(R2 콘텐츠 미탐 가드).

06요청 제약 · 에러 계약

요청 제약 · 에러 계약 (KL backend 영향)

이번 차수에 KL ↔ 로이드케이 호출 계약에 추가된 요청 제약과 에러 응답이다. KL 백엔드는 아래 한도·결속 규칙에 맞춰 호출해야 하며, 명시된 에러코드를 처리(분할·재시도·정정)할 수 있어야 한다. 모든 항목은 §2 전달 방식과 동일한 인증·테넌트 헤더 규약을 전제로 한다.

6.1 요청 본문 크기 한도 신규

JSON 요청 본문 크기에 상한이 적용된다. 한도는 max_request_body_mb(기본 25MB)이며, Content-Length가 한도를 초과하면 본문 파싱 전에 즉시 413으로 거부된다. Content-Length가 없는 chunked 전송은 누적 바이트가 한도를 넘는 순간 차단된다.

KL 영향 — 대용량 batch 분할

KL이 다건 문서를 한 요청에 묶어 보내는 대용량 batch 호출은 본문이 한도를 넘으면 413으로 거부된다. KL backend는 한도 이내로 요청을 분할해 호출해야 한다. 413 응답은 재시도해도 동일하게 실패하므로(비-일시적), 분할 후 재호출이 정답이다.

HTTP/1.1 413 Payload Too Large
Content-Type: application/json

{
  "detail": "request body too large",
  "code": "LLOYDK_BODY_TOO_LARGE"
}

6.2 테넌트 결속 신규

요청 본문의 tenant_id는 인증 신원과 일치해야 한다. 인증이 결정하는 권위 있는 테넌트(JWT의 tenant claim, 또는 hash 검증된 X-Tenant-Id)와 body의 tenant_id가 불일치하면 403으로 거부된다.

인증 방식권위 테넌트 출처body tenant_id 불일치 시
jwtJWT tenant claim(서명됨)403
jwt (tenant claim 없음)없음403 (tenant 주장 거부)
api_key + 검증된 X-Tenant-Idhash 검증된 테넌트403
api_key 단일키(미검증)없음(하위호환)body 값 사용
KL 영향 — 일관된 tenant 사용

KL backend는 인증 자격증명과 동일한 tenant를 모든 요청 body에 사용해야 한다. 한 자격증명으로 다른 테넌트의 tenant_id를 보내면 객체 수준 권한(IDOR/BOLA) 차단으로 403이 반환된다. 결속된 유효 tenant는 이후 모든 문서 조회·영속화 스코프에 적용된다.

6.3 /classify/stream 호출 빈도 한도 신규

SSE 스트리밍 분류(POST /api/v1/classify/stream)는 분당 30회 한도가 적용된다. 초과 시 429와 Retry-After 헤더(재시도까지의 초)가 반환된다. 한도 키는 인증된 테넌트/주체 기준이며, 인증 불가 시 IP로 폴백한다.

엔드포인트한도초과 시
/classify · /classify/async · /classify/batch60/분429 + Retry-After
/classify/stream · /classify/explain30/분429 + Retry-After
 
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/json

{
  "code": "LLOYDK_RATE_LIMIT",
  "message": "rate limit exceeded: 30 per 1 minute",
  "retry_after_sec": 60
}

6.4 멱등성 — Idempotency-Key 헤더 신규

변경성 요청(POST/PUT/PATCH)에 Idempotency-Key 헤더를 실으면 같은 키는 1회만 처리되고, 이후 동일 키 요청에는 저장된 응답이 그대로 재현된다. 헤더가 없거나 조회성(GET/HEAD/DELETE/OPTIONS) 요청이면 멱등성은 적용되지 않고 그대로 통과한다(기존 동작 무영향).

상태응답응답 헤더
최초 처리·저장 (2xx)핸들러 결과X-Idempotent-Stored: true
완료된 키 재호출저장된 응답 재현X-Idempotent-Replay: true
처리 중(in-flight) 동시호출409X-Idempotent-Conflict: true
키 격리 — 주체별 네임스페이스

멱등성 키는 주체(자격증명 + X-Tenant-Id)별로 격리된다. 같은 키 문자열이라도 다른 자격증명/테넌트면 분리되어, 교차 주체 간 키 충돌이나 응답 재현 누출이 발생하지 않는다. KL backend는 자신의 키 공간 안에서 임의 키를 자유롭게 쓸 수 있다.

  • 비-2xx 응답과 스트리밍(SSE, text/event-stream) 응답은 저장하지 않는다 — 동일 키로 재시도 가능.
  • 멱등성 저장소 장애 시에는 멱등성을 미적용하고 정상 처리한다(가용성 우선).

6.5 에러코드 정합

본 차수에서 KL 연동 계약에 추가된 에러코드 요약. 응답 본문에 code 필드로 식별 가능하다.

HTTPcode의미KL 처리
413LLOYDK_BODY_TOO_LARGE요청 본문이 한도(max_request_body_mb, 기본 25MB) 초과batch를 분할 후 재호출
403tenant 불일치body tenant_id가 인증 신원과 불일치인증과 동일 tenant로 정정

409멱등성 in-flight같은 Idempotency-Key 요청이 처리 중완료 후 재조회/재시도
