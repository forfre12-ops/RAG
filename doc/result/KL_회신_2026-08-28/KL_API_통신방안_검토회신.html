0. 결론 세 줄

#사안회신
1연계 방식 구현 범위와 운영 복잡도를 고려하면 현 시점에서는 1안(REST 직접 연동)을 우선 검토하는 것이 효율적입니다. 1안이 제공하는 것은 이미 갖추고 있으며(§4), 2안 채택 시에는 요청 소비 루프 신규 개발이 필요하여 범위·일정 협의가 선행되어야 합니다
2결과 반환 항목 label 만으로는 연동이 성립하지 않습니다. confidence · status · warnings 를 함께 받으셔야 합니다
3요청 절차 등록 → 분류 2단계입니다. 등록 절차를 포함하는 방안을 권고드립니다(§2)

2. 요청 절차 — 등록 후 분류 2단계

가장 중요한 조정 사항. 초안은 POST /classify 하나에 파일을 실어 보내는 1단계 구조입니다. 본 엔진은 문서 등록과 분류가 분리되어 있고, 등록 없이 분류를 호출하면 HTTP 200 을 반환하면서도 분류 결과가 저장되지 않습니다.

2-1. 실제 절차

① 문서 등록
   POST /api/v1/documents
   Content-Type: multipart/form-data
   <인증 헤더>                          (배포 확정 방식 · 또는 동일 오리진 세션 쿠키)

   form-data
     file          (필수) 원본 파일
     actor         (필수) Actor JSON 문자열 — 없으면 422
                   예: {"user_id":"kl-portal","role":"kl_backend"}
     external_ref  (선택) KL 문서번호. 예: KL-2026-000123
     security_marking / access_scope   (선택) 상향 게이트 입력
   → 응답에 doc_id(UUID) 발급 · 원본은 AES-256-GCM 으로 암호화 저장

② 분류 요청
   POST /api/v1/classify/async
   Content-Type: application/json
   <인증 헤더>                          (배포 확정 방식)

   { "doc_id": "3f2a9c14-...",              ← ①이 발급한 UUID
     "callback_url": "https://portal/…/callback" }
   ※ content 는 넣지 않습니다. 생략하면 ①에서 저장한 본문을 사용합니다.
   → job_id 즉시 반환

③ 완료 통보 (엔진 → 관리시스템)
   POST {callback_url}
   { "job_id": "...", "status": "done", "results": [ { ... 20필드 ... } ] }

정상 경로(①~③)와 등록을 건너뛴 경로(붉은 점선)를 한 그림에 두었습니다.

인증. 코드 기본값은 API Key 헤더 방식이며 JWT 모드도 지원합니다 — 연동에 적용할 방식은 인증 협의에서 확정해 회신드리겠습니다. 어느 방식이든 서버가 헤더 또는 같은 오리진 세션 쿠키로 신원을 확인하며, 미인증이면 401 을 반환합니다. 화면이나 요청 본문으로 자격증명을 받지 않으며, 실제 자격증명은 본 문서를 포함한 어떤 문서에도 기재하지 않고 별도 안전 경로로 전달합니다.

2-2. 저장이 건너뛰어지는 지점

분류 요청을 받으면 doc_id 가 문서 테이블에 등록되어 있는지 먼저 확인하고, 없으면 영속화 단계를 건너뛴 뒤 경고만 응답에 붙입니다.

근거 — poc/src/koipa/services/classify_service.py

doc_id 가 문서 테이블에 없으면 분류는 수행되지만 이력·조회·검수 대상 목록에 남지 않습니다. 이력·검수 연계를 위해 등록 절차를 포함하는 방안을 권고드립니다 — 등록을 거치지 않은 요청은 사람 검수로 등급을 확정하는 절차(FUN-024)가 성립하지 않습니다.

2-3. 1단계 경로도 있습니다 — 다만 결과가 남지 않습니다

초안이 그리신 파일 하나로 끝나는 1단계 호출은 실제로 존재합니다 — POST /api/v1/documents/analyze 가 업로드·파싱·검수 게이트·분류를 한 요청 안에서 끝내고 등급을 돌려줍니다. 그럼에도 연동 경로로 권하지 않는 이유는 하나입니다.

이 경로는 분류 결과를 저장하지 않습니다. 문서가 등록되지 않은 상태이므로 2-2 의 document_exists 검사에서 영속화가 건너뛰어집니다. 따라서 분류 결과가 검수 대기 목록·판정 이력에 남지 않습니다(호출 자체는 감사 로그에 기록되며, 남지 않는 것은 분류 결과입니다). 사람 검수로 등급을 확정하는 절차(FUN-024)가 성립하지 않으므로, 시연·진단 목적에 적합하며 운영 연계에는 등록형 절차가 더 적합합니다.

2-4. 파일 크기 상한 — 확정 회신

초안 2쪽 「본문 상한」 칸의 비고에 “멀티파트 업로드 용량 제한 협의 필요”로 적어 주신 사항에 대한 회신입니다. 현재 운영 상한은 20MB 이며(초안 기재값 500MB), 20MB 를 넘는 문서는 413 을 받습니다. 필요 용량을 협의해 조정 여부를 결정하면 좋겠습니다 — 실제 다루시는 최대 파일 크기를 회신하여 주시면, 설정으로 되는 값인지 코드 수정이 필요한 값인지를 회신 후 5영업일 안에 회신드리겠습니다.

요청. 실제 다루시는 문서의 최대 크기를 회신하여 주십시오. 설정 조정만으로 되는 값이면 바로 반영해 배포하겠고, 코드 수정이 필요한 값이면 일정을 함께 회신드리겠습니다. 참고로 측정에 쓴 100쪽 PDF 가 14MB 였습니다 — 도면·이미지가 포함된 문서는 20MB 를 넘길 수 있습니다. 어느 값으로 정하시든 대용량은 비동기 경로 사용을 함께 권합니다(§4 참조).

3. 결과 반환 항목 — 확대 요청

초안의 콜백 항목은 5개(doc_id · success · etc · file_name · label)다. 응답은 20필드이며, 그중 검수 라우팅에 필요한 항목이 빠져 있습니다.

우선필드없으면 무엇이 안 되는가
필수status이 건을 사람이 봐야 하는지를 알 수 없습니다(needs_review)
필수confidence검수 우선순위를 매길 수 없습니다(저신뢰 우선 정렬)
필수warnings왜 검수로 보냈는지 설명할 수 없습니다
권장evidence검수자가 근거 없이 본문 전체를 다시 읽어야 합니다
권장rule_grade · model_grade룰·모델 불일치를 화면에 표시할 수 없습니다
권장model_version어느 모델이 판정했는지 추적할 수 없습니다(감사 대응)
참고scores · decision_path · automation_assessment판정 근거 심층 확인용
왜 이것이 규격 문제가 아니라 설계 문제인가. 본 시스템의 목표는 정확도가 아니라 미탐 최소화이며(RFP 성능요건), 그 목표는 확신이 낮은 건을 사람에게 돌려 달성합니다. 등급만 전달되면 모든 건이 자동확정된 것과 같아지고, 검수 라우팅 설계 전체가 작동하지 않습니다.

4. 콜백 — 이미 구현되어 있습니다

초안 협의사항의 “Callback 실패 처리 · 재시도 기준”은 신규 개발 항목이 아닙니다. 현행 구현이 다음을 이미 제공합니다.

기능구현 내용
콜백 주소 지정요청 본문의 callback_url 필드
신뢰 전달Outbox 패턴 — 결과를 먼저 적재하고 별도 배송기가 발송합니다
재시도지수 백오프. 발송 주기 60초
영구 실패 처리최대 시도 소진 시 DLQ 이동 + 지표 노출(koipa_outbox_dlq_total)
SSRF 차단루프백·클라우드 메타데이터·link-local·reserved·multicast 주소를 콜백 대상에서 거부. 사설 대역(RFC1918)은 폐쇄망 정상 콜백이라 기본 허용이며, 외부망 배포에서는 설정으로 차단합니다

따라서 재시도·실패 처리는 엔진이 담당합니다. 콜백 수신 경로와 상호 인증 방식을 함께 확정하면 연계 준비가 가능합니다 — 수신측 인증 방식은 협의 항목으로 남아 있습니다.

5. Redis Stream 방식(2안)에 대한 의견

용어 구분. 여기서 말하는 Stream 은 Redis 의 메시지 큐 자료구조이며, HTTP 실시간 전송(스트리밍)이 아닙니다. 이름이 같아 혼동되기 쉬워 먼저 밝힙니다. 실시간 진행 표시가 필요하신 것이라면 별도 수단으로 제공 가능하며, 2안 채택 여부와 무관합니다.
현 시점에서는 1안을 우선 검토하시기를 권해 드립니다. 기술적으로 불가능해서가 아니라, 1안이 이미 제공하는 것을 새로 만들어야 하기 때문입니다.
항목현황
Stream 소비자 구현되어 있지 않습니다. Redis 용도는 작업 큐 브로커와 Outbox 저장소이며, Stream 자료구조는 DLQ 한 곳에서만 씁니다. 요청 소비 루프는 신규 개발입니다
미소비 Timeout 감시 초안은 관리시스템 Scheduler 가 미소비 요청을 감시하는 구조인데, 1안에서는 불필요합니다 — 엔진이 job 상태를 보유하고 콜백으로 통보하며, 조회 엔드포인트도 있습니다
파일 전달 Base64 는 본문을 약 33% 키우고, 공유 mount 는 원본 암호화 저장을 우회한다(§5-1)
스트림 키 이름 초안은 kopia: 접두사를 쓰고, 패키지·DB·컨테이너·도메인 식별자는 koipa 입니다. 채택 시 koipa: 로 통일해 주시기를 요청드립니다
접속 비밀번호 초안 6쪽 비밀번호 칸에 값이 적혀 있습니다(비고 “협의 필요”). 확정 값이라면 문서에서 빼고 별도 안전 경로로 전달하실 것을 권해 드립니다

5-1. 파일 공유 mount 방식에 대한 별도 의견

초안은 “같은 환경에서 구동되므로 mount 로 읽을 수 있을 것”이라 적고 있습니다. 폐쇄망 설계는 원본 문서를 AES-256-GCM 으로 암호화해 저장합니다. 관리시스템이 평문 원본 경로를 넘기고 엔진이 그 경로를 직접 읽으면 이 암호화 저장 경로를 지나치게 됩니다. 등록 API(POST /api/v1/documents)를 통해 반입하시면 암호화 저장이 보장됩니다.
