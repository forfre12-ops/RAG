## 2. 공통 데이터 모델 (Postgres 스키마 요지)

> **운영 스키마는 [`07_DB_스키마_v2.sql`](07_DB_스키마_v2.sql) 사용** (v2). 본 §2는 핵심 의도 요약. v2 주요 차이:
> - 등급체계 정규화: `grade_schema(JSONB)` → `classification_levels` + `evaluation_factors` + `level_keywords`
> - 대용량 텍스트는 MinIO 외부화 (`documents.raw_text_uri`)
> - 확정 라벨 진실 소스 단일화: `corrections` 테이블 (이전 `inference_result.confirmed_at` 중복 제거)
> - 멀티 테넌트(`tenant_id`)·청크/사용량/감사로그 월별 파티셔닝
> - 벡터는 ES `dense_vector(int8_hnsw)` 외부화, `audit_log` 추가

```sql
-- 등급체계 (관리자 수정 가능)

  schema_version  TEXT PRIMARY KEY,

-- 가이드 문서 (FUN-002 연계)

  guide_id        TEXT,
  version         TEXT,

-- 전처리 결과 캐시

  doc_hash        TEXT PRIMARY KEY,   -- 원문 SHA-256
  doc_id          TEXT,

  source_format   TEXT,
  cleaned_text    TEXT,
  structure_json  JSONB,
  chunk_count     INTEGER,
  processed_at    TIMESTAMPTZ
);

-- 추론 결과 (staging -> confirmed)
CREATE TABLE inference_result (
  inference_id    UUID PRIMARY KEY,
  doc_id          TEXT,
  tenant_id       TEXT,
  model_version   TEXT,
  predicted_grade TEXT,
  confidence      REAL,
  scores          JSONB,
  evaluation_factors JSONB,
  evidence        JSONB,
  rag_used        BOOLEAN,
  rag_context     JSONB,
  status          TEXT,        -- staging/confirmed

);

-- 재라벨 (능동학습 입력)
CREATE TABLE relabel_event (
  relabel_id      UUID PRIMARY KEY,

  original_grade  TEXT,

-- 합성 문서 (검수 큐)

  reviewer        TEXT,
  added_to_dataset TEXT,

);

-- 학습 작업 / 모델 레지스트리 (MLflow와 병행)
CREATE TABLE train_job (
  train_job_id    UUID PRIMARY KEY,
  training_type   TEXT,
  base_model      TEXT,
  dataset_version TEXT,
  hyperparams     JSONB,
  status          TEXT,
  metrics         JSONB,
  model_version   TEXT,
  mlflow_run_id   TEXT,

  finished_at     TIMESTAMPTZ

-- 라벨링 규칙 (FUN-023, 가이드 변경 시 외부화)
CREATE TABLE labeling_rule (
  rule_version    TEXT PRIMARY KEY,

  factor_weights  JSONB,        -- (A안 보조 시) 가중치 / B안은 S×V×M 매핑 설정
  effective_from  TIMESTAMPTZ
);
```

## 3. M1 · Synthesis (FUN-003)

### 책임
가이드/시드 문서를 컨텍스트로 LLM이 등급별 합성 문서를 생성하고 검수 큐에 적재한다. LangChain 체인 + 다중 LLM Adapter.

### 클래스 다이어그램
```
┌────────────────────────────────────┐
│  <<interface>> LLMAdapter          │
│  + complete(prompt, opts) -> Text  │
│  + embed(texts) -> List[Vector]    │  (m2/m4 공용)
└────────────────────────────────────┘
        ▲                ▲
        │                │
  AnthropicAdapter   VLLMAdapter   ... (openai, google, ollama)

┌────────────────────────────────────┐
│  PromptChain (LangChain)           │
│  + template: ChatPromptTemplate    │
│  + parser: PydanticOutputParser    │
│  + run(SynthRequest) -> SynthDoc   │
└────────────────────────────────────┘
              │ uses
              ▼
┌────────────────────────────────────┐
│  SyntheticDocGenerator             │
│  - llm: LLMAdapter                 │
│  - chain: PromptChain              │
│  - seed_repo: GuideRepo            │
│  + generate(req) -> List[SynthDoc] │
└────────────────────────────────────┘
              │
              ▼
┌────────────────────────────────────┐
│  SynthesisService                  │
│  + enqueue(SynthRequest)           │
│  + review(synth_id, decision)      │
│  + promote_to_dataset()            │
└────────────────────────────────────┘
```

### 시퀀스 (합성 → 검수 → 학습셋 편입)
```
KL --POST /synth/generate--> SynthesisService
SynthesisService --> Celery worker (synth_job)
  worker --> SyntheticDocGenerator
    Generator --> GuideRepo (가이드 N건 fetch from MinIO/Postgres)
    Generator --> PromptChain
      PromptChain --> LLMAdapter (Claude/Qwen/...)
        LLMAdapter <-- 합성 텍스트
      PromptChain --> Parser (JSON 구조 검증)
    Generator --> synthetic_doc INSERT (status=pending)
  worker done --> notify
KL --GET /synth/queue--> 검수 UI
KL --POST /synth/{id}/review--> SynthesisService
  if approve: synthetic_doc UPDATE status=approved, added_to_dataset_version
  if reject : UPDATE status=rejected
```

### 프롬프트 설계 (등급별)
- 시스템 프롬프트: "당신은 한국 영업비밀 가이드라인에 따라 등급 {grade}에 해당하는 사내 문서를 작성한다. 가이드 컨텍스트:\n{guide_chunks}\n준수 사항: ..."
- 출력 스키마(JSON): `{title, body, document_type, dept_hint, rationale_tags[]}`
- 정책: 실제 기업명/인명/주민번호 등 PII 금지 (Adapter에서 후처리 검증).

### 비용·운영
- 합성 1건 평균 1.5K 토큰 입출력 → Claude Sonnet 4.6 기준 약 $0.025/건
- 800건 PoC 시 약 $20 (수행사 부담)
- 운영 단계 발주처 부담 한도는 환경변수로 일·월 상한 설정 → `/synth/generate`에서 사전 비용 추정 응답

## 4. M2 · Preprocess (FUN-022)

### 책임
HWP/DOCX/PDF → 텍스트 → 정규화 → 노이즈 제거 → 구조화 → 청크. 결과는 `preprocessed_doc`에 캐시(SHA-256 키).

### 클래스 다이어그램
```
<<interface>> Extractor
  + supports(mime) -> bool
  + extract(bytes) -> RawDoc

  HwpExtractor / DocxExtractor / PdfExtractor / OcrExtractor

<<interface>> Normalizer
  + apply(text) -> CleanedText

  StopwordNormalizer / WhitespaceNormalizer
  SpellNormalizer / NoiseRemover

StructureParser
  + parse(RawDoc) -> StructuredDoc      # 머리글/본문/표 분리

Chunker
  + split(StructuredDoc, max_tokens, overlap) -> List[Chunk]

PreprocessPipeline
  - extractors: List[Extractor]
  - normalizers: List[Normalizer]
  - structurer: StructureParser
  - chunker: Chunker
  + run(file|text) -> PreprocessedDoc
```

### 처리 흐름
```
input(file bytes 또는 text)
  → MIME 식별 + 적합한 Extractor 선택 (fallback: LibreOffice)
  → RawDoc(paragraphs/tables/headers/footers)
  → Normalizer 체인 (불용어→공백→특수문자→맞춤법)
  → NoiseRemover (헤더/푸터/광고/반복)
  → StructureParser → StructuredDoc(JSON/Markdown)
  → Chunker (모델 max_len=512, overlap=64, 한국어 문장 경계 우선)
  → preprocessed_doc INSERT (캐시) + 반환
```

### Extractor 우선순위·fallback (2026-05 갱신)
| MIME | 1차 | 2차 | 3차 |
|---|---|---|---|
| HWP / HWPX | **rhwp-python** (Rust, 통합 API) | pyhwp/hwp5 | LibreOffice headless |
| DOCX | python-docx | LibreOffice | — |
| PDF (텍스트) | PyMuPDF | pdfplumber | — |
| PDF (이미지) | PaddleOCR | Tesseract+kor | Qwen2-VL (Vision LLM) |

### 성능 목표
- 평균 1MB PDF/HWP 추출+정규화 ≤ 2초 (CPU)
- OCR 포함 시 ≤ 10초/페이지 (GPU 가속 시 ≤ 3초)

## 5. M3 · Labeling (FUN-023)

### 책임
정본 가이드 3요건(비공지성 S / 경제적 유용성 V / 비밀관리성 M, 각 0~2점)을 텍스트·메타데이터에 매핑하여 라벨/태그를 생성하고 **등급 = S×V×M**(곱셈, 정본 B안)으로 산정. 비공지성(S)·비밀관리성(M)은 본문만으로 판정이 어려워 출처·보안표시·접근범위 메타데이터를 함께 입력받는다(R6). 학습 데이터에는 정답 라벨, 추론 결과에는 보조 점수로 활용.

### 클래스 다이어그램
```
LabelMapper
  - grade_schema: GradeSchema
  - rules: LabelingRule (YAML, 외부화)
  + map_to_grade(scores) -> Grade

FactorScorer
  + score(text, metadata, factor) -> int[0..2]   # 정본 S/V/M 0·1·2
  Concrete: SecrecyScorer(S), ValueScorer(V), ManagementScorer(M)
  (S·M은 출처/표시/접근 메타데이터 + 텍스트, V는 텍스트 중심)

TaggingEngine
  + tag(text, metadata) -> List[Tag]
  Tag = {kind: keyword|pattern|metadata, span, weight}

LabelingPipeline
  - factor_scorers: Dict[Factor, FactorScorer]
  - tagger: TaggingEngine
  - mapper: LabelMapper
  + label(StructuredDoc, metadata) -> LabelingResult
```

### LabelingRule (YAML 외부화 예)
```yaml
version: 2026-06           # 정본 가이드(B안) 반영
method: multiplicative      # 등급 = S × V × M (각 0~2)
factors: [SECRECY, VALUE, MANAGEMENT]   # 정본 3요건 (가산 가중치 미사용)
factor_signals:            # 각 요소 0/1/2 산정 신호 (키워드·패턴·메타데이터)
  SECRECY:                 # 비공지성 — 출처/공개여부 (메타데이터 우선)
    - {signal: "공개출처(판례·공시·보도·공개특허)", score: 0}   # 게이트: 0이면 곱=0=공개
    - {pattern: "(대외비|내부)",          score: 1}
    - {pattern: "(극비|특급기밀|비공개)",  score: 2}
  VALUE:                   # 경제적 유용성
    - {pattern: "(매출|수익|원가|단가|특허출원)",     score: 1}
    - {pattern: "(핵심기술|원천기술|레시피|소스코드)", score: 2}
  MANAGEMENT:              # 비밀관리성 — 접근통제/표시 (메타데이터 우선)
    - {signal: "접근통제·NDA·보안표시 있음", score: 2}
grade_mapping:             # S×V×M → 등급 (DB 설정화, FUN-005 관리자 수정 가능)
  8: TS    # 특급기밀(극비)
  4: S1    # 1급 비밀
  2: S2    # 2급 대외비
  1: S2
  0: S3    # 3급 공개 (한 요소라도 0이면 곱=0)
```

### 처리 흐름
```
StructuredDoc + metadata
  → 각 FactorScorer 호출(텍스트+메타) → S,V,M ∈ {0,1,2}
  → TaggingEngine → 태그 + evidence span
  → S×V×M 곱 → grade_mapping → Grade (학습 라벨 후보)
  → LabelingResult {grade, factor_scores:{S,V,M}, svm, tags, evidence}
```
**중요**: M3의 출력은 *학습 데이터 라벨*이지 *최종 추론 결과가 아님*. 추론은 M5가 BERT 모델로 수행하고 M3 출력은 evidence·factor_scores로 함께 제공된다.

## 6. M4 · Training (FUN-004)

### 책임
사전학습 PLM(KF-DeBERTa-base 기본)을 4-class 분류로 파인튜닝. Chunk 단위 학습, Train/Val/Test 자동 분리, RAG 옵션은 분리된 임베딩 인덱스로 구성.

### 클래스 다이어그램
```
DatasetBuilder
  + build(version_tag) -> HFDataset
  - sources: [preprocessed_doc(approved), synthetic_doc(approved), relabel_event]
  - split: stratified 70/15/15 (configurable)
  - chunk: M2.Chunker로 청크화, doc_id 보존

ClassifierModel (HuggingFace)
  - base: AutoModelForSequenceClassification
  - aux_head: FactorRegressionHead (optional)

ChunkAggregator
  + aggregate(chunk_preds) -> doc_pred  # voting/max/attention

TrainerJob
  + run(spec) -> ModelVersion
    - HF Trainer + custom compute_metrics (F1, FNR by grade)
    - MLflow 자동 로깅
    - 가중치를 MinIO에 업로드, model_version 발급
    - registry 갱신 (Staging)

RAGIndexer
  + index_guides(version) -> int    # 청크 임베딩 + ES `_bulk` upsert (alias 스위칭)
  + reindex_on_change() -> None
```

### 학습 시퀀스
```
KL --POST /train--> TrainingService
TrainingService --> train_job INSERT (queued)
  --> Celery worker
    1) DatasetBuilder.build(dataset_version)
       - 가이드 변경 시 RAGIndexer.reindex 병행
    2) ClassifierModel 초기화 (base=kf-deberta)
    3) Trainer.train (GPU)
       - epoch 별 MLflow log_metrics
       - early stop: val FNR 최소화 기준
    4) Trainer.evaluate (test set)
       - confusion matrix, FNR by grade
    5) MinIO 업로드 + train_job UPDATE (status=done, model_version)
    6) Staging으로 등록, KL에 알림
KL --상태 폴링--> /train/jobs/{id}
```

### RAG 옵션 (선택적)
- 기업 자원 부족 시 RAG OFF 가능. ON일 때만 동작.
- 인덱서: 가이드 문서 + 기업 사내규정을 청크→KURE-v1 임베딩→Elasticsearch `secrets-{role}-{tenant}-{model}-{version}` 인덱스 (테넌트별 인덱스 분리, alias 스위칭)
- 학습 시: RAG는 *학습 데이터 증강용*이 아닌 *추론 시 컨텍스트 결합*에 사용. 학습 자체는 RAG 없이 진행되며, 추론기는 RAG 토글 가능.

### 하이퍼파라미터 기본값
| 항목 | 값 |
|---|---|
| max_seq_len | 512 |
| chunk_overlap | 64 |
| batch_size | 16 (24GB VRAM) / 8 (16GB) |
| epochs | 5 (early stop val_fnr) |
| learning_rate | 2e-5 |
| optimizer | AdamW |
| lr_scheduler | linear warmup 10% |
| class_weight | inverse frequency (불균형 보정) |
| eval_metric_best | val_fnr_overall (낮을수록 좋음) |

## 7. M5 · Inference (FUN-005)

### 책임
KL의 분류 요청을 받아 staging 라벨을 반환. RAG 옵션 시 사내규정 컨텍스트를 결합. 근거(키워드/문맥)와 4대 요소 점수를 함께 출력.

### 클래스 다이어그램
```
ModelRegistry
  + load(model_version="latest_production") -> ClassifierModel
  + warmup() -> None
  + reload(version) -> None

RagRetriever
  - vdb: VectorStore  # EsStore 기본
  - embed: LLMAdapter.embed
  + retrieve(query_chunks, namespace, top_k=5) -> List[Context]

EvidenceExtractor
  + extract(text, model_attention) -> List[EvidenceSpan]
  # IG, attention rollout, or keyword highlight fallback

InferencePipeline
  - preprocess: PreprocessPipeline   # M2 재사용
  - labeling: LabelingPipeline       # M3 보조점수
  - model: ClassifierModel
  - aggregator: ChunkAggregator      # M4 재사용
  - rag: Optional[RagRetriever]
  - evidence: EvidenceExtractor
  + run(ClassifyRequest) -> ClassifyResponse
```

### 추론 시퀀스
```
KL --POST /classify--> ClassifyService
ClassifyService --> InferencePipeline.run
  1) cache 조회 (preprocessed_doc.doc_hash)
     hit: 캐시 사용 / miss: PreprocessPipeline.run
  2) (use_rag=true 시) RagRetriever.retrieve
     - 청크 임베딩 → ES 하이브리드(dense kNN + BM25 + RRF) top-K → 컨텍스트
  3) ClassifierModel 추론 (각 청크)
  4) ChunkAggregator → 문서 단위 라벨/확률
  5) EvidenceExtractor → 근거 span
  6) LabelingPipeline 점수 (보조)
  7) inference_result INSERT (status=staging)
  --> 200 ClassifyResponse
```

### 판단근거(XAI) 2단계 — 자원조건부 (KL 참고자료 §1-2)
- **1단계 기본(상시)**: `EvidenceExtractor`(IG / attention rollout / 키워드 하이라이트 폴백) + M3 4대 요소 점수 → `/classify/explain`. **GPU 불필요**, CPU 추론 환경에서도 항상 반환.
- **2단계 선택(자원조건부)**: 운영 환경에 **GPU·자원 여건 충족 시** LLM(Claude/Qwen3)이 1단계 근거를 입력으로 **자연어 설명문**을 생성. `settings.explain_llm` 토글(RAG ON/OFF 패턴과 동일), 미충족·실패 시 1단계로 graceful degrade → 기업 배포 환경(GPU 미보유 가능)에서도 무중단.

### RAG ON 시 결합 전략
- 컨텍스트는 *모델 입력*이 아니라 *후처리 보강*: BERT 분류 결과 + RAG Top-K 가이드 청크의 등급 분포를 결합(가중 평균)하여 최종 라벨 보정
- 이유: BERT 시퀀스 분류는 외부 컨텍스트 토큰 결합 시 학습-추론 불일치 발생. 별도 보강 레이어로 처리

### 성능 목표
- p50 latency RAG OFF ≤ 800ms (단일 문서 ≤ 8KB)
- p50 latency RAG ON  ≤ 2.0s
- 배치 1000건 RAG OFF ≤ 5분 (GPU 1장)

## 8. M6 · Evaluation / Active Learning (FUN-024)

### 책임
정확도/정밀도/재현율/F1/**FNR(미탐율, 핵심 KPI)** 산출, Confusion Matrix 시각화, 오분류 재라벨 누적 → 자동 재학습 트리거.

### 클래스 다이어그램
```
MetricsCalculator
  + compute(y_true, y_pred, scores) -> Metrics
  + confusion_matrix(...) -> Matrix
  + fnr_by_grade(...) -> Dict

ReportGenerator
  + html_report(metrics, cm) -> bytes
  + pdf_report(metrics, cm) -> bytes
  # Grafana data source 별도

ActiveLearningQueue
  + push(relabel_event)
  + size() -> int
  + drain(threshold) -> List[RelabelEvent]

RetrainTrigger
  + on_relabel(): if queue.size >= threshold: TrainingService.start(incremental)
  + on_schedule(): cron 주기 재평가
```

### 능동학습 루프
```
M5 추론 (staging)
  → KL 관리자 검수 → /relabel 호출
  → relabel_event INSERT
  → ActiveLearningQueue.push
  → if size ≥ threshold (예: 100):
      RetrainTrigger.fire
        → TrainingService.start(training_type=incremental)
        → M4 학습 (이전 가중치 + 새 데이터)
        → 새 model_version Staging 등록
        → 성능 비교 리포트 (이전 vs 신규 FNR)
        → 관리자 승인 시 Production 승격
```

### 평가 정책 — 미탐 가중
- 핵심 KPI: **FNR (특히 TS→S2/S3, S1→S3 같은 고등급 미탐)**
- 손실함수에 비대칭 가중치 (옵션):
  - 고등급 정답을 저등급으로 예측한 경우 cost 가중 ×2~×5
- early stop 기준을 `val_fnr_overall` 기준으로 설정 (M4 7.항과 연결)

### 대시보드 데이터 (KL 노출용)
- `/metrics/latest`, `/metrics/history`, `/metrics/confusion-matrix/{ver}` 엔드포인트 제공
- Grafana는 직접 PostgreSQL/MLflow를 읽도록 별도 구성

## 9. 공통 인프라

### 9.1 LLM Adapter
```python
class LLMAdapter(Protocol):
    name: str
    def complete(self, messages: list, **opts) -> str: ...
    def embed(self, texts: list[str]) -> list[list[float]]: ...
    def estimate_cost(self, messages: list, **opts) -> float: ...
```
구현체: `AnthropicAdapter`, `OpenAIAdapter`, `GoogleAdapter`, `VLLMAdapter`, `OllamaAdapter`.
설정: `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY`(secrets), `LLM_BASE_URL`.

### 9.2 Vector DB Adapter
```python
class VectorStore(Protocol):
    name: str
    def ensure_collection(self, name: str, dim: int) -> None: ...
    def upsert(self, collection, ids, vectors, payloads=None) -> int: ...
    def search(self, collection, query, top_k=5, filter=None) -> list[SearchHit]: ...
    def search_hybrid(self, collection, query_text, query_vec, top_k=5,
                       filter=None, **kwargs) -> list[SearchHit]: ...   # 신규
    def count(self, collection: str) -> int: ...
```
**구현체 (2026-05-27 v2)**:
- `EsStore` (기본) — Elasticsearch 8.14+ `dense_vector` HNSW + BM25 + RRF 하이브리드, retriever API 우선 / legacy `rank.rrf` 폴백
- `PgvectorStore` (2순위 폴백) — KL이 PostgreSQL만 운영할 때
- `QdrantStore` (3순위 롤백) — 본 사업 전환 전 baseline 비교용으로만 유지
- `InMemoryStore` (dryrun) — `search_hybrid`는 vec-only 폴리필 (BM25 기여 미측정 한계)

`build_store(backend=...)`는 env `VECTOR_BACKEND`로 분기. 호출부는 alias만 사용. 상세: [doc/13_벡터DB_ES_전환_계획서.md](13_벡터DB_ES_전환_계획서.md).

### 9.3 Storage
- 원본/모델/스냅샷: MinIO (`s3://lloydk/{models|guides|synth|datasets}/...`)
- 메타: PostgreSQL
- 캐시/큐: Redis (+ Celery)

### 9.4 Observability
- 모든 요청에 `request_id` 부여 (FastAPI middleware)
- Prometheus 메트릭: 요청수/지연/에러율, 모델 추론 시간, RAG 적중률
- 로그: 구조화 JSON → Loki
- MLflow: 학습 실험·모델 레지스트리

### 9.5 보안
- API Key (KL 백엔드 간) + 호출자 `Actor` 메타로 감사 로그 보강
- 비밀번호/API Key는 환경변수/Secret 볼륨 분리, 코드에 하드코딩 금지
- 합성 문서 PII 후처리 검증
- 모든 텍스트 입력 길이/인코딩 검증 (DoS 방지)
