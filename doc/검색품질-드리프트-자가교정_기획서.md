# (가칭) DriftKeeper — 한국어 검색 품질 드리프트 자가교정 시스템
### 제품 기획서 / POC 설계서 (v0.1)

> 한 줄 정의: **"데이터가 자라도 검색 품질이 안 무너지게, 외부 API 없이(폐쇄망), 한국어에 맞춰, 스스로 교정하는 사이드카."**

---

## 0. 핵심 포지셔닝

- **이건 무엇이 아닌가 (명확히 선 긋기)**
  - ❌ 새 검색 엔진(NovaXDB류 대체엔진) — 보수적 채널은 엔진 교체를 거부함(지재원=PG+ES 선택이 그 증거).
  - ❌ "RAG 품질 *측정* 도구" — Ragas/Arize/Langfuse 등으로 이미 레드오션. 셀프호스팅도 흔함.
  - ❌ 클라우드 API/LLM-as-judge 의존 — 폐쇄망에서 못 돎.
  - ❌ 카테고리 창출(시장이 안 사는 걸 설득) — 함정.
- **이건 무엇인가**
  - ✅ 고객의 기존 스택(Elasticsearch/PG) **위에 얹는 사이드카**.
  - ✅ **측정이 아니라 "고치는 루프"** — 업계 도구 대부분이 못 하는 지점(detect→prevent의 다리).
  - ✅ **완전 오프라인 + 한국어 특화**.
- **차별점(해자)의 세 교집합**
  1. 완전 오프라인 (셀프호스팅이 아니라 *외부 호출 0*)
  2. 한국어 튜닝
  3. 측정이 아닌 *자가교정 루프*
- **솔직한 규정**: 블루오션도 세계 최초도 아님. *차별화된 틈새*. 글로벌이 구조적으로 한국어·폐쇄망을 안 함 + 누적 정답 데이터(복리) + 안전한 자동교정(가드레일)이 어려움 → 이 세 겹이 방어력.

## 1. 문제 정의 — "드리프트"

**드리프트 = 정답은 그대로인데, 시간이 지나며 검색 *순위*가 흐트러져 품질이 조용히 무너지는 현상.**

- 원인(공통): 검색 점수가 *코퍼스 통계에 상대적*임.
  - 렉시컬(BM25/`ts_rank`): 문서가 쌓이면 IDF·길이정규화가 흔들려 1위가 밀림.
  - 벡터: 임베딩 공간 밀집, ANN 인덱스의 갱신 시 recall 저하, 모델 버전 교체 시 전면 재배치.
- 적용 범위: **RAG 전용이 아님.** PostgreSQL FTS, MySQL FULLTEXT, Elasticsearch/Solr/Lucene, 그리고 RAG의 벡터/하이브리드 — *순위를 매기는 모든 검색*. (Tio의 MongoDB Atlas 경험이 바로 이 FTS 드리프트.)
- 비적용: 결정적 정렬(`ORDER BY 컬럼`)은 드리프트 없음 — 관련성 점수 기반일 때만.
- 사촌 개념: 쿼리 플랜 드리프트(통계 낡음→플랜 저하→ANALYZE). *모양은 동일, 도메인은 다름(성능 vs 관련성).*

**왜 아픈가**: 고객이 "데이터 품질이 나쁘다"고 불평하는 상당수가 사실 이 드리프트. 그런데 *재는 도구도, 자동으로 고치는 도구도* 현장에 거의 없음 → 사람이 매번 수동 재튜닝(비용·리스크).

## 2. 아키텍처

### 2.1 형태: 사이드카
- ES/PG **안에 박지 않음**. 옆에 붙어 **API로 대화**(질의 전송, 결과·점수 읽기, 보정 반영).
- "스택 그대로 두고 모듈만 추가" → 보수적 채널이 받아들이는 형태.

### 2.2 보편 코어 + 엔진별 어댑터
- **보편 코어(한 번만 구현)**: 추상표현 "질의 → 점수매겨진 결과 → 관련성 판단" 위에서 동작.
  - 정답(ground truth) 저장소
  - 드리프트 탐지
  - 관련성 평가(MRR/recall@k/nDCG)
  - LTR 모델(LambdaMART = LightGBM/XGBoost)
  - Active Learning(애매 케이스 선별)
  - 가드레일(적용 전 회귀 검증)
- **어댑터(엔진별, 얇게)**: 질의 실행/점수 읽기/보정 반영을 그 엔진 문법으로 번역.
  - ⚠️ *추상은 샌다(leaky)* — 엔진마다 보정 레버가 다름:
    - PG FTS: 약함(`ts_rank` 가중치·사전·시노님)
    - Elasticsearch: 풍부(function_score·부스트·analyzer·LTR 플러그인)
    - 벡터 스토어: 거리·재인덱싱 중심
  - **규율: 미리 일반화하지 말 것.** 코어 + *어댑터 1개(ES)* 먼저. 나머지는 수요 생길 때.

### 2.3 자가교정 닫힌 루프
1. **정답 축적** — "이 질의엔 이 문서가 1위" (전문가 라벨 / 클릭·👍 / 비즈니스 규칙). ← *AI가 못 베끼는 해자 데이터.*
2. **드리프트 탐지** — 갱신마다 known 질의 재실행 → 정답이 제자리인지 확인.
3. **자동 보정** — 누적 정답으로 LTR 재학습 / 부스트·가중치 재조정.
4. **가드레일** — 적용 전 *전체 정답셋*으로 검증 → 평균이 개선될 때만 반영(다른 걸 안 망가뜨리게). ← *가장 어렵고 가장 방어적인 부분.*

### 2.4 우선순위는 "판단"이 아니라 "학습·보존"
- 시스템은 보편 정답을 *모름*. 각 프로젝트의 정답 정의를 *배워서 지킴*(priority-preservation).
- 프로젝트 내 충돌/애매 → *추측 금지*, 사람에게 escalate(Active Learning). 운영자가 우선순위 정책(가중치·권위 소스) 설정.
- "프로젝트마다 다름" = 버그가 아니라 *설계 의도이자 해자의 원천*(이전 불가, 복리).

### 2.5 기술 스택
- 언어: **Python**(IR/ML 생태계·ES/PG 클라이언트 성숙, 핫패스 아님). Rust 불필요.
- 검색: 로컬 Elasticsearch(Docker).
- LTR: LightGBM/XGBoost (작고 CPU-only, **완전 오프라인**, GPU/외부API 불필요).
- 한국어 임베딩(벡터 단계에서): 로컬 모델(예: KURE 계열). POC 1차에는 *렉시컬만*.
- 인라인 리랭킹이 필요해지면: ES LTR 플러그인(엔진 내 실행, hop 없음) 또는 해당 부분만 후속 최적화.

## 3. POC 설계 (상세)

### 3.1 목표 & 성공 기준
- **목표**: 단 한 장의 그래프 — *"한국어 데이터를 늘릴수록 품질이 조용히 무너지는데, 루프를 켜면 안 무너진다 (외부 API 0)."*
- **성공 기준(정량)**:
  - 교정 OFF: 코퍼스 성장에 따라 known 정답의 평균순위/MRR/recall@3가 *유의미하게 하락*.
  - 교정 ON: 같은 성장에도 *베이스라인 수준 유지*(예: recall@3 하락폭 ≤ 베이스라인 대비 절반).
  - 가드레일: 보정으로 인해 *전체* 평가셋이 회귀하지 않음.

### 3.2 데이터 (클린룸)
- **KorQuAD**(공개 한국어 QA): 질문↔정답 단락 쌍이 *이미 존재* → 정답셋(ground truth)을 공짜로 확보. 별도 라벨링 UI 불필요.
- 클린룸 원칙: **로이드케이/지재원 등 프로젝트의 코드·데이터·기밀 일절 미사용.** 공개 데이터 + 본인 코드만.

### 3.3 단계 (4단계, 약 1–2주)

**[0] 셋업**
- Docker로 로컬 ES 1노드(오프라인).
- KorQuAD 적재 파이프라인: 단락=문서, 질문=질의, 정답단락=ground truth.
- 한국어 분석기 설정(nori 등) — *이 설정 자체가 품질에 큰 영향*, 의도적으로 기록.

**[1] 드리프트 재현 (문제 증명)**
- 초기 문서 N개 색인 → known 질의 실행 → 정답단락 *순위 기록*(베이스라인).
- 질의어와 어휘가 겹치는 문서를 *배치로 점점 추가*(IDF 흔들기) → 매 배치 후 재측정.
- 산출물: "정답 순위가 1→3→6…로 밀리는" 곡선. ← 데모이자 문제 증거.

**[2] 탐지**
- 사이드카가 갱신마다 known 질의를 자동 재실행 → 정답이 top-k 밖으로 이탈 시 "드리프트 감지" 이벤트.
- 임계값/규칙 설정(예: recall@3 하락, 정답 평균순위 상승).

**[3] 교정 + 가드레일**
- 누적 정답쌍으로 LTR(LambdaMART) 학습 → ES 결과 리랭크(또는 부스트 재조정).
- *적용 전* 전체 정답셋으로 검증 → 개선 확인 시에만 반영.
- 산출물: "교정 ON" 라인을 "OFF" 라인 위에 겹친 비교 그래프.

### 3.4 범위 통제
- **In**: ES 단일 어댑터, 렉시컬(BM25) only, 스크립트+그래프, KorQuAD 정답 활용.
- **Out(나중)**: 타 엔진(PG/벡터), 하이브리드, 대시보드/UI, 정교한 Active Learning, 패키징, 멀티테넌시.

## 4. 평가 지표

| 지표 | 용도 |
|---|---|
| 정답단락 평균순위 | 드리프트의 직관적 신호 |
| MRR (Mean Reciprocal Rank) | 정답이 얼마나 위에 오나 |
| recall@3 / recall@10 | 정답이 상위 후보에 드나 |
| nDCG@10 | 순위 품질 종합 |
| (가드레일) 보정 전후 전체 평가셋 델타 | 회귀 방지 |

- 드리프트 = 위 지표가 코퍼스 성장 따라 *하락*.
- 교정 성공 = 위 지표가 성장에도 *유지*, 동시에 가드레일 델타 ≥ 0.

## 5. 리스크 & 정직한 단서

1. **수요 미검증(가장 큰 리스크)**: 현재 채널에서 "자동 교정"은 *희망사항*이었고, 파트너가 비용·리스크로 컷한 항목. → POC 그래프로 *드리프트를 눈에 보여주는 것*이 곧 수요 검증 실험. "예산으로 바뀌는가"를 확인하기 전엔 풀 빌드 금지.
2. **콜드스타트**: 신규 프로젝트 초반 정답 부족 → 자동교정 약함. 전문가 라벨 소량 + 비즈니스 규칙으로 씨앗, Active Learning으로 빠르게 키움. day 1 마법 아님.
3. **leaky 어댑터**: 엔진마다 보정 레버 상이 → 어댑터는 실제 작업. ES 하나에 집중.
4. **경쟁 emerging**: 측정/관측 도구는 레드오션. "고치는 루프"도 초기 진입자 존재(예: 자동 RAG 최적화 시도). 우리 방어선은 *오프라인+한국어+가드레일된 교정*의 결합.
5. **가드레일 난이도**: 나쁜 자동튜닝은 하나 고치다 열을 망침. 안전한 교정이 핵심 난제이자 가치.
6. **IP/클린룸(치명적)**: 반드시 본인 IP로, work-for-hire와 분리, 프로젝트 산출물·기밀 미파생. 계약서 IP/경업 조항 확인, 필요시 전문가 자문. (Claude는 변호사 아님.)

## 6. POC 이후 로드맵

- **단기**: ES 단일 어댑터 완성 → 드리프트 데모 그래프 확보.
- **검증 게이트**: 그래프로 파트너/잠재고객의 *유료 의향* 확인. (여기서 No면 방향 재검토.)
- **확장(수요 기반)**: PG FTS 어댑터 → 벡터/하이브리드 → 대시보드 → Active Learning UI → 패키징.
- **GTM (영업 약점 보완)**: 로이드케이를 *유통 파트너*로. 단, **소유한 완성품을 먼저 들고** 접근(아이디어 선제안 금지). 라이선스/수익배분으로 협상.
- **IP/계약 가드레일**: 본인 법인(AntiGravity) 명의, 클린룸, 조건 문서화 후 공개. 협상 부분은 전문가 위임 검토.
