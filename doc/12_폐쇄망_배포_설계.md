## 0. 본 문서의 범위

본 문서는 **운영 환경이 폐쇄망(에어갭 또는 망분리)일 때 Lloydk AI 파트의 배포·갱신 절차**를 정의합니다. doc/13의 ES 전환 설계, doc/04의 모듈 구조를 폐쇄망 제약 하에 어떻게 운영하는지가 핵심입니다.

**전제**: KOIPA 운영 환경의 망 등급은 [K1 회신](06_협의요청서_KL_발주처.md)으로 확정됩니다. 본 문서는 L1·L2·L3 세 시나리오를 모두 다루되, **L2(망분리)를 기본 가정**으로 설계합니다.

## 1. 망 등급 정의와 시나리오

### 1.1 등급 정의

| 등급 | 인터넷 | 외부망 반입 | 대표 환경 | 본 시스템 대응 |
|---|---|---|---|---|
| **L1. 일반 사내망** | 프록시로 가능 | 자유 | 일반 기업 | docker pull 가능, 표준 배포 |
| **L2. 망분리** (업무망/인터넷망) | 인터넷망만 가능, 업무망 격리 | USB·승인된 반입경로 | 금융·공공 다수 | **본 문서 기본 가정** |
| **L3. 완전 폐쇄망(에어갭)** | 전혀 불가 | 매체 반입 심사 (수일~수주) | 국정원·국방 일부 | 번들 + 매체 반입 + 심사 동의서 |

### 1.2 KOIPA 추정

지식재산보호원은 십중팔구 L2 또는 L3입니다. 근거:
- 영업비밀 시스템 자체가 외부 노출 금지 도메인
- 공공기관 보안 가이드라인상 망분리 의무 적용 가능성
- KL 측 ES 운영도 폐쇄망 내일 가능성 큼

→ K1 회신에 **망 등급(L1/L2/L3) + 반입 매체 + 심사 절차**를 명시 질의 필요 (협의요청서 K1 보강 권장).

## 2. 4가지 설계 기둥

doc/13 §11.5에서 4개 기둥을 제시했고, 본 문서는 그 4개를 각각 절차 단위로 구체화합니다.

```
┌─────────────────────────────────────────────────────────────┐
│ 기둥 1. 개발-운영 분리 (Dev/Ops Split)                       │
│   외부망 개발 → 자기완비 번들 → USB → 폐쇄망 운영           │
│                                                              │
│ 기둥 2. 모델·의존성 사전 패키징                              │
│   Docker tar + 모델 가중치 + wheel + apt + ES 플러그인       │
│                                                              │
│ 기둥 3. 합성·LLM 정책 재정의                                 │
│   Claude API 제거, Qwen3-14B 자체 호스팅 강제                │
│                                                              │
│ 기둥 4. 업데이트 채널                                        │
│   모델 가중치 + 변경로그 표준 반입 단위, Blue/Green 배포    │
└─────────────────────────────────────────────────────────────┘
```

| Docker 이미지 7~8개 | 약 8~12 GB |

## 4. 번들 빌드 절차 (외부망)

### 4.1 `build_offline_bundle.sh` 명세

```bash
poc/scripts/build_offline_bundle.sh \
    --version 1.0.0 \
    --output ./dist/lloydk-airgap-bundle \
    --include-trainer \
    --es-license ./license.json  # 옵션 (Platinum 시)
```

**수행 작업** (순서대로):
1. 작업 디렉터리 생성, git commit SHA 기록
2. Docker 이미지 빌드 (`docker compose build`) → `docker save` 7~8개
3. HuggingFace 모델 다운로드 (`huggingface-cli download`) → models/ 복사
4. Python wheels 수집 (`pip download -r requirements.lock.txt`)
5. ES 플러그인 zip 다운로드
6. 인프라 설정 파일 복사 (docker-compose, ES 템플릿, Nori 사전, ILM 정책)
7. SHA256 계산 → `CHECKSUMS.sha256`
8. `manifest.yaml` 생성
9. Trivy 보안 스캔 → 결과 `manifest.yaml`에 기록
10. `tar -czf` 또는 디렉터리 그대로 → 결과 검증

**dry-run 모드** (`--dry-run`): 다운로드·빌드 없이 매니페스트만 미리 생성, 예상 크기·체크리스트 출력.

### 4.2 빌드 환경 요구사항
- Docker 24+ + BuildKit
- HuggingFace 계정 (KURE/BGE 다운로드 인증)
- 디스크 50GB 여유
- Python 3.11
- 빌드 시간: 약 2~3시간 (네트워크 속도 의존)

### 4.3 빌드 산출물 검증
```bash
poc/scripts/verify_bundle.sh ./dist/lloydk-airgap-bundle
# 검증 항목:
# - CHECKSUMS.sha256 전체 통과
# - manifest.yaml 스키마 valid
# - Docker tar 7~8개 모두 존재 + load 가능
# - 모델 디렉터리 구조 + tokenizer.json 존재
# - wheels 모두 .whl 확장자
# - es-plugins 2개 zip 존재
# - third-party-licenses.txt 비어있지 않음
```

## 5. 매체 반입 절차 (L2/L3)

### 5.1 표준 절차

```
[외부망] 번들 빌드 + Trivy 스캔        (Lloydk DevOps)
   ↓
[보안 심사 신청서 작성]                 (Lloydk PM)
   - 번들 매니페스트 첨부
   - 변경 사항 요약 (CHANGELOG)
   - 보안 스캔 결과
   - 라이선스 보고서
   ↓
[USB/CD 매체 봉인]                       (Lloydk DevOps)
   ↓
[KL/보호원 보안 심사]                   (KL/KOIPA 보안팀)
   - 매체 검역 (악성코드 스캔)
   - 매니페스트 vs 실제 파일 대조
   - 라이선스 검토
   - 심사 기간: 1~3주 예상
   ↓
[승인 → 운영망 반입]                     (KL DevOps)
   ↓
[install.sh 실행]                        (KL/Lloydk 합동)
   ↓
[verify.sh 실행 + smoke test]
```

### 5.2 매체 봉인·전달 표준
- USB: BitLocker AES-256 또는 LUKS 암호화
- 패스프레이즈는 **별도 채널**(서면 또는 별도 보안 메신저)로 전달
- 매체 외부에 봉인 라벨 (build_date, SHA256 short, bundle version)
- 반입 후 USB는 **운영망 보안 금고**에 보관 (3개월 후 폐기)

### 5.3 반입 주기 권장
- **소규모 패치**: 반입하지 않고 누적
- **마일스톤 단위 묶음 반입** (분기 1~2회)
- **긴급 보안 패치**: 별도 신속 심사 채널 (KL과 사전 합의)

## 6. 폐쇄망 docker-compose 변형

### 6.1 외부망 → 폐쇄망 변경 사항

| 항목 | 외부망 | 폐쇄망 |
|---|---|---|
| 이미지 source | `docker pull` | `docker load -i image.tar` |
| 모델 다운로드 | HuggingFace 런타임 | `models/` 볼륨 마운트 + `TRANSFORMERS_OFFLINE=1` |
| Python 패키지 | PyPI runtime | 이미 이미지에 포함 또는 `--no-index --find-links=/wheels` |
| LLM provider | `anthropic` (Claude API) | `vllm` (Qwen3 자체 호스팅) — **강제** |
| ES 플러그인 | `elasticsearch-plugin install ...` | pre-installed 이미지 또는 zip mount |
| 텔레메트리 | 기본 활성 | `xpack.telemetry.enabled: false` |
| 시간 동기화 | NTP 외부 | NTP 내부망 |

### 6.2 핵심 환경 변수 (`.env.airgap.template`)

```bash
# === 폐쇄망 강제 설정 ===
LLM_PROVIDER=vllm                    # Claude/OpenAI/Gemini 금지
VLLM_BASE_URL=http://vllm:8000/v1
VLLM_MODEL=Qwen/Qwen3-14B-Instruct-AWQ
VLLM_ENABLE_THINKING=false
TRANSFORMERS_OFFLINE=1
HF_HUB_OFFLINE=1

# === ES ===
VECTOR_BACKEND=es
ES_URL=http://elasticsearch:9200
ES_USERNAME=lloydk_writer
ES_PASSWORD=<keystore reference>     # Elastic keystore 사용
ES_VERIFY_CERTS=true
ES_CA_CERTS=/etc/lloydk/certs/ca.crt

# === 시크릿 ===
# 평문 금지 — 운영망 내 Vault 또는 systemd-creds 사용
```

### 6.3 vLLM 서비스 추가

폐쇄망에선 Qwen3-14B 자체 호스팅이 필수이므로 docker-compose에 vLLM 컨테이너 추가:

```yaml
  vllm:
    image: vllm/vllm-openai:v0.8.5
    command: >
      --model /models/Qwen-Qwen3-14B-Instruct-AWQ
      --quantization awq
      --max-model-len 8192
      --enable-reasoning --reasoning-parser deepseek_r1
    runtime: nvidia
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: [gpu]
    volumes:
      - ./models:/models:ro
    ports:
      - "8000:8000"
```

## 7. 업데이트 채널 (운영망 ← 외부망)

### 7.1 업데이트 단위

| 단위 | 빈도 | 매체 반입 |
|---|---|---|
| **번들 v1.x.0 (마이너)** | 분기별 | 정식 심사 1~3주 |
| **번들 v1.x.y (패치)** | 월 1회 | 정식 심사 |
| **모델 가중치 갱신** | 능동학습 결과 누적 시 | 모델 단독 반입 (라이트 심사) |
| **사용자 사전** (`userdict_ko.txt`) | 분기 또는 가이드 개정 시 | 텍스트 파일 단독 |
| **ILM 정책 / index template** | 정책 변경 시 | JSON 단독 |
| **긴급 보안 패치 (CVE Critical)** | 즉시 | 신속 심사 (사전 합의) |

### 7.2 모델 가중치 단독 반입 절차

외부망에서 능동학습 + 재훈련 후 모델만 반입:

```
1. 외부망에서 MLflow Model Registry에 신모델 등록
2. 가중치 export:
     mlflow models export-model -m runs:/<id>/model -o ./model-export
3. 매니페스트 (모델 메타 + 평가 지표) 생성
4. 매체 반입 (라이트 심사)
5. 운영망 MLflow에 import:
     mlflow models load -m ./model-export -n kf-deberta-finetuned-v2
6. Blue/Green 또는 Canary로 점진 배포:
     - 신규 요청의 10% → v2, 90% → v1
     - 1주 모니터링 → 100% 전환
     - 문제 시 즉시 v1 복귀
```

### 7.3 Blue/Green 무중단 배포

ES 인덱스도 동일 원리:
```
secrets-guides-koipa-kure-v1   ← 현재 운영 (alias 가리킴)
secrets-guides-koipa-kure-v2   ← 신규 인덱스 (재인덱싱 후)
                                  ↓
                                 alias 스위칭 (1초 미만)
                                  ↓
secrets-guides-koipa-kure-v2   ← 신규 운영
secrets-guides-koipa-kure-v1   ← 백업 (2주 보존 후 삭제)
```

→ [`EsStore.swap_alias`](../poc/src/lloydk/adapters/vectorstore/es_store.py) 활용.

## 8. 폐쇄망 보안 정책 (doc/13 §11.5 확장)

### 8.1 외부 호출 차단 강제 설정

| 컴포넌트 | 차단 설정 |
|---|---|
| **Elasticsearch** | `xpack.telemetry.enabled: false`, `xpack.monitoring.collection.enabled: false`, `xpack.security.transport.ssl.enabled: true` |
| **vLLM** | `--disable-usage-stats` |
| **MLflow** | tracking URI 내부망 강제, `MLFLOW_TRACKING_TOKEN` 사용 |
| **MinIO** | `MINIO_BROWSER=on`이되 외부 노출 금지, S3 호환 API만 내부망 |
| **PyTorch/HF** | `TRANSFORMERS_OFFLINE=1`, `HF_HUB_OFFLINE=1`, `HF_DATASETS_OFFLINE=1` |
| **OpenTelemetry/Sentry** | 비활성 또는 내부 collector만 |

### 8.2 시크릿 관리

- **금지**: `.env` 평문 비밀번호, 코드에 키 하드코딩
- **권장**:
  - Elastic Keystore (`bin/elasticsearch-keystore add ...`)
  - Docker secrets 또는 systemd-creds
  - 운영망 내부 HashiCorp Vault (있는 경우)

### 8.3 감사 로그

- 모든 컴포넌트 로그를 Loki 또는 KL 측 SIEM으로 forwarding
- ES audit log 활성화 (Basic 라이선스 가능)
- API 요청 로그에 `request_id` + `actor_user_id` 필수
- 감사 로그 retention: 1년 (E8 회신 시 갱신)

### 8.4 라이선스 활성화

- **Basic (무료)**: 자동 활성, TLS·RBAC·API Key·Audit log 사용 가능
- **Platinum**: 라이선스 파일 (`license.json`) 매체 반입 → `POST /_license` API
- 라이선스 갱신 (1년): 만료 30일 전 알림 → 매체 반입 절차 동일

## 10. 폐쇄망 PoC 검증 (회신 전 준비)

K1 회신이 L2/L3이면 본 절차가 발동됩니다. 회신 전이라도 다음은 미리 검증 가능합니다:

| 검증 항목 | 방법 | 회신 의존? |
|---|---|---|
| 번들 빌드 스크립트 동작 | `--dry-run` 모드로 manifest.yaml 생성 검증 | ❌ |
| Docker save/load 라운드트립 | 외부망에서 자체 검증 | ❌ |
| `TRANSFORMERS_OFFLINE=1`로 모델 로드 | 외부망에서 인터넷 끊고 검증 | ❌ |
| 사용자 사전 Git 미러 갱신 → 인덱스 reload | docker compose 환경에서 검증 | ❌ |
| vLLM 자체 호스팅 정상 동작 | GPU 환경 확보 후 검증 (Q1 회신 의존) | ⚠️ Q1 |
| ES Nori 플러그인 사전 설치 이미지 | 외부망에서 빌드 검증 | ❌ |
| Blue/Green 모델 교체 | `EsStore.swap_alias` 테스트 (이미 완료) | ✅ 완료 |

→ 회신 전에 **번들 빌드 dry-run + 모델 오프라인 로드 검증**까지는 미리 완료할 것 권장.

## 11. 결정 사항 요약 (v0.9)

1. **L2(망분리)를 기본 가정**, L3은 추가 매체 심사 절차로 처리
2. **자기완비 번들 약 25~30 GB** — USB 64GB 1개 또는 외장 SSD
3. **Claude/OpenAI/Gemini API는 폐쇄망 운영 시 완전 제거** — vLLM + Qwen3-14B 자체 호스팅 강제
4. **번들 빌드는 `build_offline_bundle.sh`로 자동화**, dry-run 모드 보유
5. **마일스톤 단위 묶음 반입** (분기 1~2회), 긴급 패치는 신속 심사 채널 별도 합의
6. **Blue/Green 무중단 배포** — 모델·인덱스 모두 alias 스위칭
7. **외부 텔레메트리·자동 업데이트 채널 강제 차단**
8. **K1 회신에 망 등급(L1/L2/L3) + 반입 매체 + 심사 절차 명시 요청** (협의요청서 K1 보강 권장)
