## 1. 프로젝트 한눈에

- **무엇**: 한국어 문서(HWP/PDF/DOCX)를 업로드하면 AI가 4단계 보안등급(특급/1급/2급/3급)을 자동 분류
- **누구**: 한국지식재산보호원(KIPRA) 발주, 각 기업이 **온프레미스 Docker**로 설치해 사용
- **역할 분담**: KL(웹 UI/권한/보관함/감사 등 18개 기능) ↔ **로이드케이(AI 코어 6개: FUN-003·004·005·022·023·024)**
- **로이드케이가 책임지는 6개 모듈**

| 모듈 | FUN | 책임 |
|---|---|---|
| M1 합성 | 003 | LLM 기반 학습용 합성 문서 생성 |
| M2 전처리 | 022 | HWP/PDF → 텍스트 → 정규화 → 청크 |
| M3 라벨링 보조 | 023 | 4대 평가요소 점수·evidence 추출 |
| M4 학습 | 004 | BERT 분류기 파인튜닝 |
| M5 추론 | 005 | 등급 분류 + RAG 보강 + 근거 출력 |
| M6 평가/능동학습 | 024 | F1·FNR 집계, 재라벨→자동 재학습 트리거 |

- **핵심 한 줄**:
  > 한국어 문서를 받아서 → 분해·정규화 → BERT 모델로 등급 추론 → RAG로 기업별 변동성 보강 → **미탐(FNR) 최소화**하며 능동학습 루프로 운영.

## 2. 전체 워크플로우

### 2.1 사용자 한 명이 문서를 올렸을 때 (단일 요청 흐름)

```
[1] 사용자가 HWP 문서 업로드 (KL 웹 UI)
       │
       ▼
[2] KL 백엔드 → Lloydk API: POST /classify
       │  Body: {doc_id, content, use_rag, tenant_id, actor}
       ▼
┌────────────────────── Lloydk AI Engine ─────────────────────┐
│                                                             │
│ [3] M2 전처리 (FUN-022)                                     │
│     rhwp-python HWP/HWPX → 텍스트 추출                      │
│     soynlp/KoNLPy 정규화                                    │
│     머리글·푸터·반복 제거                                   │
│     512토큰 청크 분할 (overlap 64, 문장 경계 우선)          │
│     → preprocessed_doc 캐시 (SHA-256 키)                    │
│                                                             │
│ [4] M3 라벨링 보조 (FUN-023)                                │
│     YAML 규칙 기반 4대 요소 점수                            │
│     (경제적가치/비공지성/관리수준/유출영향도)               │
│     evidence span 추출                                      │
│                                                             │
│ [5] (옵션) RAG 검색                                         │
│     청크 → KURE-v1 임베딩 → Qdrant Top-K                    │
│     테넌트 네임스페이스 분리                                │
│     기업 사내규정·KIPRA 가이드 청크 회수                    │
│                                                             │
│ [6] M5 추론 (FUN-005)                                       │
│     KF-DeBERTa 분류기로 청크별 등급 확률                    │
│     ChunkAggregator로 문서 단위 어그리게이션 (vote/avg)     │
│     RAG ON이면 컨텍스트 등급분포로 보정                     │
│     EvidenceExtractor (attention rollout) → 근거 span       │
│                                                             │
│ [7] 응답 구성                                               │
│     {label, confidence, scores{TS,S1,S2,S3},                │
│      evaluation_factors{4개}, evidence[10],                 │
│      model_version, rag_used}                               │
│     → status: "staging" (관리자 확정 대기)                  │
│     → inference_result INSERT                               │
└─────────────────────────────────────────────────────────────┘
       │
       ▼
[8] KL이 응답 받아 관리자 UI 표시
       │
       ▼
[9] 관리자 액션:
     (a) /confirm  → 최종 라벨 확정
     (b) /relabel  → 능동학습 큐로 (FUN-024)
                       │
                       ▼ 큐 100건 누적
                  자동 재학습 트리거 (Celery)
```

### 2.2 학습 워크플로우 (재학습 트리거 시)

```
[학습 트리거] (관리자 수동 or 능동학습 임계)
        │
        ▼
[M1] 합성 데이터 생성 (FUN-003)
   - 영업비밀 실데이터는 외부 공개 불가 → LLM 합성으로 보완
   - Claude Sonnet 4.6 (상용) 또는 Qwen3-14B (OSS) 등급별 800~1,500건
   - LangChain ChatPromptTemplate + PydanticOutputParser (JSON 보장)
   - PII 정규식 후처리 + 관리자 검수 (Cohen's Kappa ≥ 0.75)
        │
        ▼
[DatasetBuilder]
   - 합성 + 공개(AI Hub/공공데이터/DART/영업비밀보호법령)
     + 재라벨 누적분
   - Stratified Train 70 / Val 15 / Test 15
   - M2.Chunker로 청크화 (doc_id 보존하여 누수 차단)
        │
        ▼
[M4] 학습 (FUN-004)
   - 베이스: KF-DeBERTa-base (카카오뱅크, 한국어 금융·법률 도메인)
   - 4-class head + class weight (불균형 보정)
   - AdamW, lr=2e-5, linear warmup 10%, batch 16(24GB)/8(16GB)
   - Early stop: val_FNR_overall 최소화
   - 전 실험 MLflow 자동 로깅 + RAG 인덱스는 분리 트랙(가이드 변경 시만 reindex)
        │
        ▼
[M6] 평가 (FUN-024)
   - Accuracy / Precision / Recall / F1-macro / **FNR-by-grade**
   - Confusion Matrix (TS→S2/S3 같은 고등급 미탐 별도 알람)
   - 미탐 비대칭 가중 cost ×2~×5 옵션
        │
        ▼
[모델 레지스트리]
   - 가중치 → MinIO 업로드
   - Postgres train_job + MLflow Model Registry 동시 기록
   - Staging 등록 → 관리자 승인 → Production 승격 (롤백 가능)
```

### 2.3 능동학습 루프 (운영 중 모델이 좋아지는 메커니즘)

```
M5 추론 (staging)
   → KL 관리자 검수 → /relabel
   → relabel_event INSERT (original, corrected, reason, actor)
   → ActiveLearningQueue.push (Redis)
   → if queue.size >= threshold(=100):
        RetrainTrigger.fire
          → TrainingService.start(incremental)
          → M4 재학습 (이전 가중치 + 새 데이터)
          → 새 model_version Staging 등록
          → 이전 vs 신규 FNR 비교 리포트 자동 생성
          → 관리자 승인 시 Production 승격
```

LangGraph로 이 루프를 상태 머신으로 명시 — `idle → collecting → training → evaluating → awaiting_approval → promoted`.

### 3.2 코드 레이어

```
API (FastAPI 라우터, OpenAPI 1:1)
  ↓
Service (도메인 오케스트레이션: classify/training/synthesis/evaluation)
  ↓
Modules (M1~M6)
  ↓
Adapters (LLM / VectorDB / Storage) ← 모두 Protocol 기반 추상화
  ↓
Infra (Postgres/MinIO/Qdrant/Redis/MLflow)
```

**핵심 설계 원칙**:
- LLM/VectorDB는 **Adapter Pattern**으로 교체 가능 (Anthropic↔OpenAI↔Qwen3+vLLM 무중단 스왑)
- 모델 가중치는 컨테이너 이미지 외부 MinIO 볼륨 → 재빌드 없이 모델 교체
- 모든 요청에 `request_id` + `actor{user_id, role, tenant_id}` → 감사 로그 보강

## 4. 분류 모델: 후보 비교 · 장단점 · 선택 이유

### 4.1 후보 비교 매트릭스

| 후보 | 파라미터 | 사전학습 도메인 | 최대 토큰 | 한국어 | 도메인 적합도 | 자원 부담 | 종합 |
|---|---|---|---|---|---|---|---|
| **KF-DeBERTa-base** | 184M | **금융·법률** 한국어 | 512 | ★★★★★ | ★★★★★ (영업비밀=경영/기술/법률 문서) | ★★★★ | **★★★★★ 채택** |
| KoELECTRA-base | 110M | 한국어 일반 | 512 | ★★★★ | ★★★ | ★★★★★ | ★★★★ 경량 옵션 |
| KLUE-RoBERTa-large | 337M | 한국어 NLU 벤치 | 512 | ★★★★★ | ★★★★ | ★★★ | ★★★★ |
| KoBigBird | ~200M | 한국어 + 긴 문서 | **4096** | ★★★★ | ★★★★ | ★★★ | ★★★ |
| Qwen3-14B (디코더 LLM) | 14B | 다국어 + 코드 | 32K~131K | ★★★★ | ★★★ | ★ (분류용으론 과잉) | ★★ |

### 4.2 KF-DeBERTa 채택 이유 (3가지)

1. **도메인 적합성**: 영업비밀 후보 문서(매출/원가/특허/계약서/내부지침)는 *금융·법률 어휘 비중이 높음*. KF-DeBERTa는 카카오뱅크가 한국어 + 금융 + 법률 텍스트로 사전학습 → 도메인 임베딩 공간이 이미 정렬되어 있음.
2. **분류기로서의 효율**: 184M 인코더는 GPU 1장(24GB)에서 batch 16으로 초당 수십 건 추론. 14B 디코더 LLM은 1건당 수 초 + 비용 큼 + 결정성·해석성 떨어짐.
3. **해석성**: attention rollout / IG로 evidence span 추출 가능. 보안 시스템은 "왜 이 등급인지" 근거를 함께 제공해야 함 (관리자 검수·감사 대비).

### 4.3 KoELECTRA를 *동시에* 유지하는 이유

자원 부족 기업(GPU 16GB 이하·CPU 추론 환경)을 위한 **이중 트랙**.
- KoELECTRA-base 110M → CPU 추론도 현실적
- 분류 헤드·학습 파이프라인은 동일하므로 *동일 데이터셋·동일 평가체계*로 두 모델을 함께 학습 → 환경별 골라쓰기

### 4.4 왜 LLM 분류기를 안 쓰는가 (자주 받는 질문)

> "GPT-4 / Claude로 zero-shot 분류하면 안 되나요?"

| 항목 | LLM zero-shot | BERT fine-tune |
|---|---|---|
| 단건 추론 시간 | 1.5~5초 | **0.05~0.2초** |
| 1건당 비용 | $0.005~$0.02 (상용 API) | **0** (자체 GPU) |
| 결정 일관성 | 프롬프트·온도에 흔들림 | **가중치 고정 → 재현 가능** |
| 기업별 변동성 학습 | 프롬프트로 우겨넣어야 함 | **데이터로 학습** |
| 외부 송신 | 네트워크 필요 (보안 이슈) | **오프라인 가능** |
| FNR 보정 | class_weight 못 씀 | **비대칭 cost로 미탐 가중** |
| 근거 출력 | 자유 텍스트 (검증 어려움) | attention/IG로 span |

**결론**: 분류 코어는 BERT, LLM은 *합성 데이터 생성·RAG 보강·라벨링 경계 판단*에 보조 활용 (역할 분리).

## 5. 임베딩 모델: 후보 비교 · 장단점 · 선택 이유

### 5.1 후보 비교 (한국어 RAG 관점)

| 후보 | 차원 | 최대 토큰 | 한국어 성능 | 라이선스 | 특징 |
|---|---|---|---|---|---|
| **KURE-v1** (고려대 nlpai-lab) | 1024 | 8192 | **Recall@1 0.5264, NDCG@1 0.6055** | MIT | BGE-M3를 한국어 retrieval 데이터로 fine-tune. **BGE-M3 대비 일관된 우위 (+1.6%p)** |
| BGE-M3 (BAAI) | 1024 | 8192 | Recall@1 0.5178, NDCG@1 0.5985 | MIT | KURE의 베이스. dense+sparse+ColBERT 멀티 벡터 출력 |
| ko-sroberta-multitask | 768 | 512 | 중간 | Apache 2.0 | 경량 SBERT, CPU 환경용 |
| E5-large-multilingual | 1024 | 512 | 다국어 (한국어 특화 아님) | MIT | KURE/BGE-M3 대비 한국어 약함 |

### 5.2 KURE-v1을 1순위로 두는 이유

1. **한국어 성능 직접 우위**: 동일 베이스(BGE-M3) 위에서 한국어 retrieval 데이터로 추가 학습 → 한국 공문/기업문서 검색에서 일관된 성능 향상.
2. **운영 리스크 낮음 (Swap-In 가능)**: 차원·토크나이저가 BGE-M3와 동일 → Qdrant 인덱스 재구축 없이 모델만 바꿀 수 있음. PoC에서 BGE-M3로 시작했더라도 무중단 교체.
3. **라이선스/소속 신뢰**: 고려대 NLP&AI Lab 한국 연구기관 산출물, MIT.
4. **PoC P2에서 직접 검증**: KIPRA 가이드 + 사내규정 시드로 Top-K 정확도 직접 비교 → 측정 결과로 1순위 확정.

### 5.3 폴백 전략

- **BGE-M3**: KURE-v1과 동등 인터페이스, 다국어 문서 비중이 큰 기업용
- **ko-sroberta-multitask**: 임베딩 서버를 별도 띄울 수 없는 경량 환경용 (768차원으로 Qdrant 인덱스 별도)

## 6. LLM: 상용 vs OSS — 후보 비교 · 선택 이유

### 6.1 LLM이 필요한 두 가지 자리

| 자리 | 용도 | 요구 특성 |
|---|---|---|
| **FUN-003 합성** | 학습용 가상 문서 생성 | 한국어 자연스러움, JSON 출력 안정성, 다양성 |
| **FUN-005 RAG 보강** | 추론 시 컨텍스트 결합·라벨 경계 판단 | 짧은 응답, 결정성, 추론(reasoning) |

### 6.2 상용 API 비교

| 후보 | 한국어 | 컨텍스트 | 단가($/1M tok 입력+출력) | JSON 안정성 | 종합 |
|---|---|---|---|---|---|
| **Claude Sonnet 4.6** | ★★★★★ | **1M tok** | $3 + $15 | ★★★★★ | **★★★★★ 채택** |
| GPT-4o | ★★★★ | 128K | $2.5 + $10 | ★★★★ | ★★★★ |
| Gemini 2.5 Pro | ★★★★ | 1M | $1.25 + $10 | ★★★ | ★★★★ |

**Claude Sonnet 4.6 채택 이유**:
- 한국어 합성 문서의 자연스러움·전문어휘 적정성에서 1순위 (자체 PoC P3로 검증 예정)
- 1M 컨텍스트로 KIPRA 가이드 다발을 한 번에 컨텍스트에 넣고 합성 가능
- Anthropic JSON 출력 강제 (tool use) 안정적

### 6.3 OSS 온프레미스 비교

| 후보 | 파라미터 | VRAM(FP16/Q4) | 한국어 | 특징 |
|---|---|---|---|---|
| **Qwen3-14B** | 14B | ~30GB / ~10GB | ★★★★ | **2025-05 공개**, thinking/non-thinking 모드 전환, vLLM ≥0.8.5 공식 지원, 32K(YaRN 131K), Apache 2.0 |
| Qwen2.5-14B-Instruct | 14B | ~30GB / ~10GB | ★★★★ | Qwen3 출시로 베이스라인 강등 |
| EXAONE 3.5 32B (LG) | 32B | ~65GB / ~20GB | ★★★★★ | 한국어 SOTA급, **라이선스 확인 필요(공공사업 호환성)** |
| Llama 3.1-8B + Bllossom | 8B | ~16GB / ~5GB | ★★★ | 경량, 한국어 파인튜닝 |

**Qwen3-14B 채택 이유**:
- **thinking 모드**: 라벨 경계 판단·평가요소 점수화 시 `enable_thinking=True`로 추론 과정 활용
- **non-thinking 모드**: 합성 다량 생성(FUN-003) 시 빠른 처리
- vLLM ≥0.8.5 공식 지원 → 운영 안정성
- Apache 2.0 → 공공사업 무리 없음

**EXAONE**: 한국어 성능은 더 좋지만 라이선스 검토 필요 → §15 미해결 이슈로 분리.

### 6.4 추상화 — LLM Adapter Pattern

```python
class LLMAdapter(Protocol):
    name: str
    def complete(self, messages: list, **opts) -> str: ...
    def embed(self, texts: list[str]) -> list[list[float]]: ...
    def estimate_cost(self, messages: list, **opts) -> float: ...
```

구현체: `AnthropicAdapter`, `OpenAIAdapter`, `GoogleAdapter`, `VLLMAdapter`, `OllamaAdapter`
설정 한 줄(`LLM_PROVIDER=anthropic|vllm|...`)로 교체 가능. 합성·RAG·평가 모든 곳에서 동일 인터페이스.

## 9. 학습 전략과 KPI — 왜 FNR을 최우선으로 두는가

### 9.1 핵심 KPI: FNR (False Negative Rate, 미탐율)

보안 시스템에서 두 오류의 비용은 비대칭이다.

| 오류 | 결과 | 비용 |
|---|---|---|
| **미탐 (FN)**: 고등급을 저등급으로 잘못 분류 | 영업비밀이 낮은 보호등급으로 유통 → **유출 사고 직결** | **매우 큼** |
| 오탐 (FP): 저등급을 고등급으로 잘못 분류 | 업무에 불편, 결재 지연 | 작음 |

따라서 학습/평가 모든 곳에서 FNR을 우선한다.

### 9.2 손실 함수와 Early Stop

- **class_weight = inverse frequency**: 등급 불균형 보정
- **비대칭 cost**: TS→S2/S3 같은 *고등급 미탐* cost ×2~×5 (옵션)
- **Early Stop 기준**: accuracy가 아니라 **val_FNR_overall** (낮을수록 좋음)
- **Confusion Matrix 모니터링**: 등급별 오분류가 어디로 새는지 별도 추적

### 9.3 하이퍼파라미터 기본값

| 항목 | 값 |
|---|---|
| max_seq_len | 512 |
| chunk_overlap | 64 |
| batch_size | 16 (24GB VRAM) / 8 (16GB) |
| epochs | 5 (early stop val_fnr) |
| learning_rate | 2e-5 |
| optimizer | AdamW |
| lr_scheduler | linear warmup 10% |
| class_weight | inverse frequency |
| eval_metric_best | val_fnr_overall ↓ |

### 9.4 Chunk Aggregation (청크 → 문서 단위 라벨)

문서는 512토큰 청크로 분할 학습 → 추론 시 다시 문서 단위로 합쳐야 함. 3가지 전략 비교:

| 전략 | 장점 | 단점 |
|---|---|---|
| **Max-vote** | 단순 | 고등급 일부 문장이 있어도 묻힘 |
| **Mean-prob** | 안정적 | 미탐 위험 |
| **Max-prob (any-high)** | 미탐 최소화 | 오탐 증가 |

**채택**: 보안 도메인 특성상 **Max-prob 기반 + RAG 보강** (PoC P1에서 정량 비교).

## 10. RAG 결합 방식과 그 한계

### 10.1 왜 RAG를 분류에도 쓰는가

기업마다 영업비밀 기준이 다르다. 같은 "매출 자료"라도 A기업은 1급, B기업은 2급일 수 있다. *학습 모델 하나로 모든 기업의 변동성을 다 잡을 수 없다*. 그래서:
- 기업별 사내규정·정책을 **KURE-v1 임베딩 → Qdrant** (테넌트 네임스페이스 분리)
- 추론 시 Top-K로 회수 → 모델 출력을 **후처리 보강**

### 10.2 결합 방식 — *모델 입력*이 아니라 *후처리 보강*

```
BERT 청크 추론 → 청크별 등급 확률
                    │
                    ▼ ChunkAggregator
              문서 단위 등급 확률
                    │
       (RAG ON이면)  ▼
RAG Top-K 가이드 청크의 등급 분포 회수
                    │
                    ▼ 가중평균 (α·model + (1-α)·rag)
              최종 라벨 + confidence
```

**왜 모델 입력에 RAG 컨텍스트를 넣지 않는가?**
- BERT 시퀀스 분류는 *학습 시 본 적 없는 외부 컨텍스트 토큰*을 입력에 결합하면 학습-추론 분포 불일치(distribution shift)가 생김
- 별도 보강 레이어로 처리하면 *학습은 깨끗이, 추론은 유연하게*

### 10.3 한계

- RAG 적중률이 낮으면 보강 효과 없음 → KURE-v1 채택으로 retrieval 성능 보강
- 테넌트별 사내규정 데이터가 부족한 기업은 RAG 효과 제한 → **RAG는 선택 옵션**, 자원 부족 기업은 OFF 가능

## 11. 합성 데이터 전략 — 왜 LLM 합성이 불가피한가

### 11.1 데이터 부족 문제

- 영업비밀은 **외부 공개 불가** → 실데이터 거의 없음
- 공개 데이터(AI Hub/공공데이터/DART)는 *영업비밀과 정확히 일치하는 라벨이 없음*
- 발주처 비밀해제 문서 제공 가능성 낮음

### 11.2 3중 데이터 전략

| 출처 | 비중 (PoC) | 비고 |
|---|---|---|
| **공개 데이터** | 30% | AI Hub 행정문서·계약서, 공공데이터 공문서, DART 공시, 영업비밀보호법령 — 라이선스 클리어 |
| **LLM 합성** | 50% | Claude/Qwen3로 KIPRA 가이드 컨텍스트 기반 가상 사내문서 등급별 200~400건 — 이중 검수자 검수(Cohen's Kappa ≥ 0.75) |
| **재라벨 누적** | 20% (운영 후 증가) | 능동학습 큐에서 100건씩 자동 편입 |

### 11.3 합성 품질 보증

- 시스템 프롬프트에 KIPRA 가이드라인 컨텍스트 강제 주입
- PydanticOutputParser로 JSON 출력 스키마 검증 (`{title, body, document_type, dept_hint, rationale_tags[]}`)
- **PII 정규식 후처리**: 주민번호·전화·이메일·계좌·실제 기업명 패턴 차단
- **이중 검수자**: 두 명이 등급 라벨 일치 여부 확인 → Cohen's Kappa ≥ 0.75 미달 시 폐기

### 11.4 합성 비용 (운영 견적)

- Claude Sonnet 4.6 기준 합성 1건 평균 1.5K 토큰 입출력 → 약 **$0.025/건**
- PoC 800건 → 약 **$20** (수행사 부담)
- 운영 단계 발주처 부담 한도는 환경변수로 일·월 상한, `/synth/generate`에서 사전 비용 추정 응답

## 12. 능동학습 루프 — LangGraph 상태 머신

### 12.1 상태 전이

```
idle ── (relabel 발생) ──▶ collecting
   collecting ── (size ≥ 100) ──▶ training
       training ── (M4 완료) ──▶ evaluating
           evaluating ── (FNR 개선) ──▶ awaiting_approval
                                          │
              ── (FNR 후퇴) ──▶ rejected   │
                                          ▼
                              (관리자 승인) promoted
                              (관리자 거부) rejected
```

### 12.2 안전장치

- **모든 데이터·모델 버전 보관**: MLflow Model Registry + Postgres `train_job` + MinIO 가중치
- **승인 전엔 Staging만**: Production은 관리자 명시 승인 후 승격
- **롤백**: 신규 모델 FNR이 운영 중 후퇴하면 이전 model_version으로 1줄 명령 롤백
- **재라벨 출처 추적**: `relabel_event.actor`로 누가 언제 어떻게 수정했는지 감사 추적

| RAG 적중률 낮은 기업 | RAG 효과 제한 | RAG OFF 옵션, BERT 단독 모드 보장 |
| LLM API 외부 송신 | 보안 정책 충돌 가능 | OSS Qwen3+vLLM 폴백 (완전 폐쇄망 가능) |

### 15.3 향후 검토 (PoC 이후)

- **GraphRAG**: 단일 문서 등급 판정엔 entity graph 효과 제한적이라 PoC 범위 밖. 다중 문서 연계 판정 요구 발생 시 재검토
