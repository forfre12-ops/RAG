# 문서 등록 시 접근범위(access_scope) 제공 요청

작성 2026-09-10 · 근거 재현 `poc/scripts/measure_management_input_gap.py`

---

## 1. 요청 사항

문서 등록 API 호출 시 `metadata.access_scope`를 함께 보내 주시기를 요청합니다.
값은 인터페이스 규약서(ICD §3.3)에 이미 정의된 네 가지 중 하나입니다.

| 값 | 뜻 |
|---|---|
| `approved_only` | 승인된 자에 한해 열람 (물리·시스템 통제) |
| `designated` | 지정된 접근자만 (NDA·열람 제한) |
| `department` | 특정 부서·임직원 일부 |
| `all_employees` | 전 임직원 열람 가능 |

보안표시(`security_marking`)가 문서에 찍혀 있는 경우에는 그 값도 함께 주시면
접근범위보다 우선하여 반영합니다(ICD §3.2).

## 2. 왜 필요한가

영업비밀 등급은 **비공지성(S) × 경제적유용성(V) × 비밀관리성(M)** 으로 판정합니다.
이 가운데 **비밀관리성(M)은 문서 본문에서 관측되지 않습니다.** 관리성의 증거는
보관 위치와 접근권한이며, 그 정보는 문서를 보관하는 시스템에만 있습니다.

실제로 저희가 보유한 전체 데이터에서 이 값을 가진 문서는 한 건도 없습니다.

```
검사 범위   파일 373개 · 문서 432,820행 (전수)
보안표시    0건
접근범위    0건
입력 지문   189244d2be6706c1
```

## 3. 값이 없으면 무엇이 불가능해지는가

판정식에서 **S1 등급이 나오는 요소 조합은 (2,2,0) 하나뿐**입니다. 즉 비밀관리성이
확인되지 않으면 S1은 구조적으로 판정할 수 없습니다.

요소값을 모두 갖춘 검증 집합 2,700건으로 측정한 결과입니다.

| 측정 항목 | 결과 |
|---|---|
| M 값에 따라 등급이 갈리는 문서 | 2,385 / 2,700 (88.3%) |
| M을 못 받아 보수적으로 채웠을 때 등급이 틀리는 문서 | 885 / 2,700 (32.8%) |
| 그 오판의 내역 | S1을 TS로 750건 · S3을 S2로 135건 (전부 과대 판정) |

보수적으로 채운다는 것은 관리성을 최고 수준으로 가정한다는 뜻입니다. 미탐을 막는
방향이지만, 그 대가로 **문서 세 건 중 한 건이 실제보다 높은 등급으로 판정**됩니다.
검수 부담이 그만큼 늘어납니다.

## 4. 값을 주시면 무엇이 달라지는가

두 가지를 나누어 말씀드립니다. 같은 값이 두 경로에서 다르게 작동합니다.

**즉시 반영되는 것 — 현재 배포본**

- 접근범위가 제한적인데 예측 등급이 낮으면 자동 확정하지 않고 검수로 보냅니다.
- 관리성이 확인되었는데 판정식상 더 높은 등급이 나와야 하는 문서를 검수로 보냅니다.
- 보안표시가 예측보다 높으면 그 등급으로 상향합니다(하향은 하지 않습니다).
- 화면과 API 응답의 비밀관리성 요소값이 **실제 확인값**으로 바뀝니다. 지금은 등급에서
  역산한 값이 표시되고 있습니다.

**향후 반영되는 것 — 요소 기반 판정 경로**

위 88.3%·32.8%는 요소값으로 등급을 직접 산출하는 구조를 전제한 수치입니다. 현재
배포본은 등급을 먼저 정하고 요소를 뒤에 맞추는 구조이므로, 접근범위를 받는 것만으로
등급 자체가 바뀌지는 않습니다. 요소 기반 경로를 적용한 뒤 이 효과가 나타납니다.

## 5. 개발 측 준비 상태

- 인터페이스 규약(ICD §3.2·§3.3)에 값과 매핑이 이미 정의되어 있습니다.
- 수신·해석·검수 라우팅 로직이 구현되어 있으며 시험으로 고정되어 있습니다.
- 값이 오지 않아도 기존 동작은 그대로입니다. **보내 주시는 시점부터 작동합니다.**

## 6. 근거 재현

이 문서의 모든 수치는 아래 명령으로 다시 산출할 수 있습니다.

```
python scripts/measure_management_input_gap.py
```

검사 대상 파일 수와 입력 지문을 함께 출력하므로, 데이터가 바뀌면 지문으로 확인하실
수 있습니다.
