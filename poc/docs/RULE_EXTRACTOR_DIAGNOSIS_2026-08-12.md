# 룰 추출기 진단 — S/V/M 은 추출되는 것이 아니라 등급에서 역산된다

작성 2026-08-12. `V7_RESULT_2026-08-12.md` §4 의 후속. 서빙 자동확정이 0% 인 원인을
쫓다가 룰 추출기까지 왔고, 예상보다 깊었다.

---

## 1. 출발점

분포 밖 데이터에서 자동확정률이 0% 였고 사유의 99.4% 가 `rule under-detected S/V/M`
이었다. 합의 게이트가 "룰과 모델이 다르면 검수"라서, 자동화를 막는 것은 분류기가 아니라
**룰 추출기**다.

처음 세운 가설은 "시드 사전이 복합어 위주라 매칭이 안 된다"였다. 절반만 맞았다.

## 2. 시드 사전 — 맞지만 표면

```
시드 404개 · 전부 exact 문자열 매칭 · 1어절 41개뿐(90%가 복합어)
semantic 매칭 코드는 있으나 쓰는 시드 0개
```

무음 미탐 문서(178자, 공급망 대응 계획)로 돌리니 잡힌 키워드가 **`'공급망'` 하나**였다.
"내부", "공개 전", "유출", "협상력 약화"를 전부 놓쳤다. 사전을 뒤져 보니 `원가 구조`·
`납품 단가 협상`·`리콜 대응 계획` 같은 복합어는 있는데 기본어가 없고, **`유출`·`누출`은
시드에 아예 없다** — 영업비밀 판단에서 가장 중심적인 단어인데도.

### semantic 활성화는 불가 (실측 후 폐기)

코드에 있는 semantic 경로를 켜 보려고 배포본 임베더(KURE-v1)로 실측했다:

```
임계 0.75 · 실측 코사인 0.30 ~ 0.53 → 전부 미달
음성 대조군 "점심 메뉴 안내"          0.316
양성 시드   "경제적 가치가 있는 영업상 정보"  0.335   ← 구분 안 됨
```

임계를 낮춰도 소용없다. **양성과 음성이 같은 구간에 겹친다.** 문장 단위로 쪼개도 최대
0.53 이고 최유사 문장이 대부분 동일한 문장으로 나온다 — KURE-v1 이 잡는 것은 주제
(공급망·원가)이지 비공지성이 아니다. 검색용 임베더에 법적 요소 판단을 시킬 수는 없다.

## 3. 진짜 원인 — 요소 코드가 서로 다르다, 그리고 레벨은 등급에서 역산된다

### (a) 코드 불일치

```
FACTOR_SEEDS(출력 스키마)  SECRECY · VALUE · MANAGEMENT
KEYWORD_SEEDS(시드 사전)   NON_PUBLICITY · ECONOMIC_VALUE · MANAGEMENT_LEVEL · LEAK_IMPACT
교집합                     [] (공집합)
```

누산부가 `factor_raw[factor] = factor_raw.get(factor, 0.0) + score` 라서 KeyError 대신
**새 키가 조용히 생긴다.** 정본 3요소는 0.0 에 머문다. 이 방어 코드는 DB 커스텀 스킴의
KeyError 를 막으려고 넣은 것인데, 결과적으로 결함을 가렸다.

### (b) 레벨은 요소 근거가 아니라 등급에서 나온다

```python
s_lv = 0 if (public or content_grade == "S3") else (2 if strong else 1)
v_lv = 2 if strong else (0 if content_grade == "S3" else 1)
m_lv = 2 if has_mgmt else (0 if content_grade in ("S3", "S1") else 1)
```

`content_grade` 는 키워드 점수의 argmax 등급이다. 즉 **등급을 먼저 정하고 거기서 S/V/M 을
역산**한다. 애써 누산한 `factor_raw` 는 표시용 0~5 정규화에만 쓰이고 곧바로 덮인다.

그리고 이 S/V/M 이 다시 `grade_from_svm()` 에 들어가 등급이 된다. **순환이다.**
합의 게이트가 "독립 근거"로 믿는 룰 경로는 독립 근거가 아니라 키워드 argmax 등급의
재진술이다.

## 4. 결과 — 분포 밖에서 룰은 아무 일도 하지 않는다

```
v3 final_800 (400건 표본)   룰 등급: S3 400건 (100%)      정답: S3 120 · S1 101 · S2 99 · TS 80
hardened42   ( 42건)        룰 등급: S3 15·TS 12·S2 9·S1 6  정답: S1 14 · TS 12 · S2 9 · S3 7
```

**v3 에서 룰은 400건 전부를 S3 라고 한다.** 요소값도 200건 전부 (0,0,0) 이다.
등급 일치율 30.0% 는 성능이 아니라 v3 의 S3 기저율(240/800)과 같은 값이다.

hardened42 에서 분포가 나오는 이유는 그 문서들이 시드 사전이 만들어진 바로 그 시나리오
코퍼스의 어휘로 쓰였기 때문이다. **룰 엔진은 자기 사전이 유래한 문체에서만 동작한다.**

기준선 측정(`scripts/measure_rule_extractor.py`):

```
v3 final_800 (N=800)   등급 일치 30.0% · 키워드 무매칭 0.0%
  secrecy     평균차 -1.44 · MAE 1.44 · 낮게봄 84.6% · 높게봄 0.0%
  value       평균차 -1.44 · MAE 1.44 · 낮게봄 84.6% · 높게봄 0.0%
  management  평균차 -0.94 · MAE 0.94 · 낮게봄 63.0% · 높게봄 0.0%

hardened42 (N=24)      등급 일치 45.8% · 키워드 무매칭 29.2%
  secrecy     -0.79 / 58.3% 낮게봄        value -0.72 / 50.0%
  management  +0.33 / 41.7% 높게봄
```

0~2 척도에서 MAE 1.44 는 한 단계를 넘는 오차다. 그리고 **과검출이 0.0%** 다 —
한 방향으로만 틀린다.

## 5. 무엇을 고쳐야 하나

세 가지가 겹쳐 있고 순서가 있다.

| | 내용 | 위험 |
|---|---|---|
| ① | 요소 코드 정합 — 누산이 정본 3요소에 실제로 쌓이게 | 낮음. 지금은 죽은 값이다 |
| ② | 레벨을 요소 근거에서 산출(등급 역산 제거) | **높음 — 서빙 등급이 바뀐다** |
| ③ | 기본어 시드 보강(`유출`·`누출`·`재고`…) | 중간. 정밀도 하락 가능 |

②가 본질이지만 서빙 동작을 바꾼다. 합의 게이트 → 검수 라우팅 → 자동확정률이 모두
연동되므로 고등급 FNR 을 먼저 재고 들어가야 한다.

⚠ **과적합 주의.** 심판 요소값이 붙은 골든 문서는 실질 24건뿐이다. 거기 맞춰 시드를
튜닝하면 그 24건에만 좋아진다. v3 final_800 은 `expected_factor_scores` 를 구성상
800건 전부 가지므로 이쪽을 주 측정면으로 쓴다. 수정 전후로 **양쪽 다** 재고, v3 에서
개선이 없으면 과적합으로 본다.

## 6. ①③ 을 해봤고, 시드 튜닝으로는 안 된다는 결론이 나왔다

### ① 요소 코드 정합 — 했다. 단독으로는 무효다

`_accumulate_factor()` 를 넣어 키워드 점수가 원래 코드와 정본 3요소 **양쪽**에 쌓이게 했다
(커스텀 코드는 정본으로 우겨넣지 않는다 — genericity 계약). 검증:

```
NON_PUBLICITY 0.6 · ECONOMIC_VALUE 0.9 · LEAK_IMPACT 0.4 · MANAGEMENT_LEVEL 0.5 · WEIRD_CUSTOM 0.3
  -> SECRECY 0.6 · VALUE 1.3 · MANAGEMENT 0.5 · 레거시/커스텀 키 그대로 보존
```

값이 살아났지만 **화면에 보이는 결과는 그대로다.** §3(b) 의 등급 역산이 곧바로 덮기
때문이다. ①은 ②의 선행조건일 뿐 그 자체로는 아무것도 바꾸지 않는다. 그래도 남긴다 —
죽은 값을 살려두지 않으면 ②를 할 때 또 같은 자리에서 막힌다.

### ② 임계 탐색 — 상수 예측기가 이겼다

튜닝면 v6 train(1,833건)·검증면 v3 final_800(800건)으로 분리해 임계를 찾았다
(두 셋의 계보 독립은 `report_holdout_independence.py` 로 확인, verdict True).

```
SECRECY     t1=0.00 t2=0.00  ← "항상 2" 라는 뜻
VALUE       t1=0.00 t2=0.00  ← 같음
MANAGEMENT  t1=0.15 t2=0.15  ← 사실상 "근거 있으면 2, 없으면 0"
```

임계가 코너로 몰렸다. 이유는 누산 점수 분포에 있다(v3 300건 표본):

```
SECRECY     0점  0.0% · 중앙 1.35 · 90분위 1.35 · 최대 1.35   ← 전 문서 동일값
VALUE       0점 100.0% · 최대 0.00                            ← 근거 전무
MANAGEMENT  0점 100.0% · 최대 0.00                            ← 근거 전무
```

모든 문서에서 같은 키워드 두 개(`'내부 자료'` 0.6 + `'공개 가능'` 0.75 = 1.35)만 걸리고
VALUE·MANAGEMENT 는 300건 전부 0 이다. **분산이 0이라 임계를 정할 대상이 없다.**

## 7. 그래서 결론 — 시드로는 못 고친다

오늘 네 가지를 시도했고 세 개가 막혔다:

| 시도 | 결과 |
|---|---|
| semantic 매칭 활성화 | 폐기. 코사인 0.30~0.53, 음성 대조군과 겹침 |
| 요소 코드 정합 | 했으나 등급 역산이 덮어 단독 무효 |
| 요소 근거 임계 탐색 | 불가. VALUE·MANAGEMENT 근거가 300건 전부 0 |
| 기본어 시드 보강 | **안 했다** — 아래 이유로 하지 않는 편이 낫다 |

기본어를 넣으면 v3 에서 뭔가 걸리기는 할 것이다. 그러나 v3 는 합성 저술 코퍼스이고
어휘가 템플릿에서 온다. **거기 맞춰 사전을 키우면 v3 를 외우는 것**이지 회원사 문서에서
동작한다는 근거가 되지 않는다. 오늘 "무음 미탐 0"이 v3 한정 수치였던 것과 같은 함정이다.

한국어 사내문서 전반의 비공지성·경제적유용성 어휘를 수기 사전으로 덮는 것은 규모가
다른 작업이고, 검증할 실문서가 0건인 상태에서는 개선을 증명할 방법도 없다.

## 8. 대신 할 만한 것 — 요소를 모델이 예측하게

지금 구조는 **등급 → 요소 → 등급** 순환이다. 이걸 끊는 현실적인 방법은 요소를 학습으로
뽑는 것이다. 데이터가 이미 있다:

```
labeled_v6_factor_grounded/train.jsonl   1,833건 · expected_factor_scores 전건 보유
proxy_eval/.../final_800.locked.jsonl      800건 · 전건 보유 (검증용, 손대지 않음)
```

S/V/M 3-헤드로 학습하고 `grade_from_svm()` 으로 등급을 내면:
- 순환이 사라진다 — 요소가 먼저 나오고 등급이 따라온다
- 설명이 제대로 된다 — "비공지성 2 · 경제적유용성 2 · 관리성 0 이라 S1"
- 합의 게이트가 비교할 대상이 실제로 생긴다

⚠ 다만 이러면 룰과 모델의 독립성이 약해진다. 그런데 **지금의 독립성은 이미 허구다** —
§4 에서 봤듯 분포 밖에서 룰은 800건 전부에 S3 라는 상수를 낼 뿐이다. 없는 독립성을
지키느라 자동화를 막고 있는 셈이다.

이것은 제안이며 아직 하지 않았다. 학습·평가·서빙 계약이 모두 걸리는 변경이라
별도 판단이 필요하다.
