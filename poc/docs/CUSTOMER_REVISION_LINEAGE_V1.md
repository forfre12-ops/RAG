# 식별자 변경 진단뷰의 판본 계보·노출 전파 v1

2026-09-15. 원본 정본을 교체하거나 답안을 승인하는 도구가 아니다.
별칭 삭제의 대상 식별 의미 보존이 아직 확인되지 않았으므로 변경안은 **미채택 진단뷰**로만 다룬다.
`adoption_allowed=false`, `authoritative_parent_replaced=false` 및 기존 데이터 사용 금지 플래그를 유지한다.

## 1. 세 가지 수량을 구별한다

- **원본 정본:** 기존 참조 원고와 답안은 수정하지 않는다.
- **제안 진단뷰:** 지정된 부모 패널만 1대1 대응으로 교체한 가상의 전체 입력 집합이다. `active_documents`는 이 집합의 크기다.
- **선언된 노출 판본:** 원본의 노출 이력을 보존하고 실제 본문이 바뀐 새 ID만 추가한다. 변경되지 않은 뷰는 다시 더하지 않는다.

이번 계약의 기준은 원본/진단뷰 각 260개, 패널 64개, 기존 연결 그룹 236개다.
변경 뷰가 K개이면 선언 노출 기록은 260+K개가 된다. 이를 260+64개의 신규 원고나 완전한 실제 접근 이벤트 이력으로 세지 않는다.
최종 실행 수치는 통합 보고서와 실행 산출물을 따른다.

## 2. 검증 API

`customer_revision_lineage_v1.audit_revision`은 다음을 받는다.

- 원본 전체 문서·답안·근거 sidecar와 제안뷰 전체 문서·답안·근거 sidecar
- 원본에서 직접 확인한 패널 부모 ID와 패널 계보 행
- 기존 노출 장부와 기대 내부 지문, 원본 manifest 지문, 변경안 출처·지문
- 기존 의미 연결 목록 및 고정 문서/패널/그룹 수

계보 행에는 부모·자식 ID, 입력/본문/답안/근거 지문, 정책·맥락 지문, 세 계열 식별자,
변경 여부와 literal 변경 스팬, `new_document_count=0`, 사용 금지 플래그가 들어간다.

검사는 다음 순서로 수행한다.

1. 원본·진단뷰의 기존 참조 계약과 장부 지문을 검증한다. 원본 전체 ID가 기존 장부에 정확히 있어야 한다.
2. 지정 부모마다 계보가 정확히 하나여야 한다. 누락·초과·중복·부모 부재·자식 ID 재사용을 거절한다.
3. 본문이 바뀌면 내용+맥락에서 계산한 새 문서 ID와 새 입력 지문을 요구한다. 변경되지 않으면 원본 ID를 유지한다.
4. 계보의 모든 sidecar 지문을 실제 객체와 대조한다. 맥락, 정책, 등급, 규칙, 등급 배제 이유와 비본문 메타데이터를 보존한다.
5. 부모 본문 위치의 `before`와 제안뷰 위치의 `after`를 재현한다. 명시하지 않은 변경, 숫자열 변경, 겹치는 스팬을 거절한다.
6. 주장 이름·순서·상태를 보존하고 인용문·위치·지문을 새 본문 위치에 정확히 재결합한다. 변경 스팬이 주장 경계 중간을 자르면 거절한다.
7. 패널 밖 문서·답안·근거는 전체 객체가 원본과 같아야 한다. 패널 내 근거 sidecar도 ID/입력 지문/본문 지문 외에는 같아야 한다.
8. 기존 노출 행은 그대로 유지하고 변경된 새 판본만 추가한다. 의미 연결의 부모 ID를 진단뷰 ID로 옮겨 기존 `audit_exposure`를 다시 적용한다.
9. 전체 진단뷰의 최종 평가 제외와 기존 그룹 수 보존을 확인한다. 이를 미노출 인증이나 평가셋 승인으로 해석하지 않는다.

원본 대상의 식별 의미까지 자동으로 검증하는 기능은 아니다. 예를 들어 본문의 `분말 R`을 `분말`로 줄이면
글자 스팬·숫자·관리 맥락이 보존되어도 어떤 분말에 대한 문서인지 구별하는 정보가 사라질 수 있다.
이 도구가 구조 검사를 통과시켰다는 이유로 그 변경을 정본으로 채택하거나 기존 등급을 새 본문의 정답으로 인증하지 않는다.
독립 대상 식별 검토는 별도이며 `alias_semantics_independently_certified_here=false`다.

## 3. 반환값과 노출 이력

`exposure_ledger`는 확장된 장부, `exposure_audit`는 진단뷰에 대한 기존 엔진의 전수 점검,
`semantic_links_remapped`는 대응 ID를 적용한 의미 연결 목록이다.
원본 장부를 덮어쓰지 않으며 새 출력 위치에서만 보관한다.

장부 지문에는 `source_ref` 문자열도 포함된다. 같은 manifest를 상대경로와 절대경로로 적은 별도 실행은
내용상 같은 판본이어도 장부 지문이 다를 수 있다. 후속 작업에서는 통합 담당이 지정한 하나의 기준 장부를 사용하고,
별도 재현 장부의 동일 문서 ID를 추가 노출 판본으로 합산하지 않는다.

`parents_absent_from_diagnostic_view`는 제안뷰에서 새 ID로 대응된 원본 부모들이다.
호환 필드 `retired_parent_ids`도 같은 목록이지만, `retired_parent_ids_scope`에서
**제안뷰 안의 부재일 뿐 원본 정본의 폐기·은퇴가 아니다**라고 명시한다.

본문 변경 판본 역시 이미 개발에 사용된 같은 계열의 자료다. 새 ID 발급으로 최종 블라인드 평가 제외를 회피할 수 없다.
장부 지문은 기록된 바이트를 묶을 뿐 작성자의 권한·승인·노출 이력의 완전성을 인증하지 않는다.

## 4. CLI와 출력 보호

`scripts/audit_customer_revision_lineage_v1.py`는 다음 세 팩을 명시적으로 받는다.

1. 기존 `reference_v0_6`: 원본 manifest 고정 지문으로 문서·답안·근거와 `batch06_metadata`의 패널 ID를 확인한다.
2. 별도 제안뷰 팩: 호출자가 준 기대 manifest 지문과 입력 멤버 지문을 확인한다.
3. 기존 `integration_v1`: 고정 manifest 지문과 장부 내부 지문으로 기존 노출·의미 연결을 확인한다.

출력은 반드시 새 폴더여야 한다. 입력 팩 안, 기존 manifest가 있는 조상 폴더 안, 경로 별칭으로 같은 곳을 가리키는 경우는 거절한다.
소스 코드는 입력 팩을 읽기 전부터 지문에 묶고 입력 파일과 함께 출력 전후 재확인한다.
`result.json/summary.json`을 쓴 뒤 마지막 확인에 성공한 경우에만 `manifest.json`을 완료 표시로 쓴다.
실패 시 결과 파일 일부가 남을 수 있으나 완료 manifest가 없으면 성공 팩이 아니다.

manifest의 `source_files_sha256` 경로는 `poc` 기준 상대 경로다. 결과 객체 내부의 모듈 지문은 별도 이름 매핑을 유지한다.
네트워크·모델·학습기·채점기를 실행하지 않는다. 실제 산출물 실행은 통합 담당이 새 출력 경로에서 수행한다.

```powershell
.\.venv\Scripts\python.exe -B scripts/audit_customer_revision_lineage_v1.py `
  --original-pack reports/CUSTOMER_GUIDE_PARALLEL02_20260915/reference_v0_6 `
  --revision-pack reports/CUSTOMER_GUIDE_REPAIR_20260915/reference_repair_v1 `
  --expected-revision-manifest-sha256 <검증한-제안뷰-manifest-SHA256> `
  --prior-integration-pack reports/CUSTOMER_GUIDE_PARALLEL02_20260915/integration_v1 `
  --out reports/CUSTOMER_GUIDE_REPAIR_20260915/lineage/<새-출력-폴더>
```

작업 폴더는 `F:\antigravity\rag\poc`다. 예시의 자리표시는 실제 검증한 값으로 바꾼다.
