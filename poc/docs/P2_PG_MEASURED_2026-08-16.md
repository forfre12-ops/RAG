# 검색 품질을 **출하 구성(PG)** 으로 처음 쟀다 — 지연 기준을 넘는다

작성 2026-08-16.

---

## 1. 왜 쟀나

릴리스 게이트의 P2(검색 품질) 수치가 **우리가 쓰지 않는 구성**의 것이었다.

```
배포본        vector_backend = pg (pgvector)
게이트 리포트   backend = es (Elasticsearch) · 2026-06-02 생성
```

P1 에서 "원시 모델을 재고 있었다" 와 같은 종류다 - 게이트가 출하물을 안 잰다.

⚠ 나는 이 지적을 한 번 **틀리게 기각했다.** "ES 는 이미 안 씁니다" 라고 했는데 리포트를
  안 열어봤다. 시스템이 ES 를 안 쓰는 것은 맞지만 **평가는 ES 로 한 것**이 남아 있었다.

`vectorstore/__init__.py` 주석이 이미 알고 있었다.

> ⚠️ 라이브 PG(pgvector 이미지) × 실코퍼스 × 자연어(비발췌) 쿼리 **재검증 게이트는 미실행**
> (실 PG 부재). 실측 R@5 확정 후 caveat 제거 예정.

"실 PG 부재" 로 못 하던 것인데 KL 서버에 PG 가 있어 실행했다.

**출하 구성이 지연 기준을 넘는다.** verdict 가 `CONDITIONALLY_READY` -> **`FAIL`** 이 됐다.

⚠ Recall 은 0.925 -> 0.8875 로 3.8pp 낮지만 기준(0.80)은 넘는다. 문제는 지연이다.

## 3. 이 수치를 어디까지 믿을 수 있나

```
같은 코퍼스        14,755 청크 (ES 측정과 동일)
같은 쿼리          80건 (동일)
같은 임베더        KURE-v1 (동일)
다른 것            백엔드(es -> pg) · 측정 하드웨어
```

⚠ **하드웨어가 다르다.** ES 측정은 GPU 였고(embed_corpus_ms 692,079 = 11.5분), 이번 PG
  측정도 GPU 로 했지만(973,648 = 16분) **서버·GPU 모델이 다르다**(L4). 임베딩 시간은
  검색 지연과 무관하지만, 검색 지연 자체는 그 서버의 PG 성능에 달렸다.

⚠ 그리고 이 PG 는 **테스트 서버의 것**이다(메모리 2GB 제한). 실 운영 PG 사양이 다르면
  지연도 다르다. `docker stats` 실측: postgres 컨테이너 메모리 상한 2GiB.

**"PG 가 ES 보다 느리다" 가 아니라 "이 서버의 이 PG 구성에서 223ms 다" 가 정확하다.**

## 4. 지연이 어디서 오는지 나눠 쟀다 — 원인 확정

`scripts/profile_pg_retrieval.py` · `explain_pg_lexical.py` · `tune_pg_parallel.py` ·
`bench_pg_concurrency.py` · `bench_pg_minimal_sets.py` 로 좁혔다.

### 4.1 출처 — 어휘 후보가 테이블 전체를 순차 스캔한다

`EXPLAIN (ANALYZE, BUFFERS)` 실측.

```
Seq Scan  tb_rag_vectors   rows=14,703 / 전체 14,755   →  99.6% 가 매칭
```

어휘 후보 조건이 `tsv @@ to_tsquery('simple', bigram1 | bigram2 | ...)` 라 **거의 모든
문서가 최소 한 bigram 에 걸린다.** 매칭이 그렇게 넓으면 GIN 인덱스로 행을 하나씩 찾는
것이 순차 스캔보다 비싸서 플래너가 인덱스를 안 쓴다 — 인덱스가 없어서가 아니다.

OR 로 묶는 것은 설계 결정이다. AND(`plainto_tsquery`)로 하면 패러프레이즈 질의에서
0 매치가 난다(pg_store 주석에 실측 근거). 그래서 **스캔 자체는 없앨 수 없다.**

### 4.2 레버 — 정렬도 메모리도 아니고 그 스캔의 병렬 워커 수

처음엔 정렬이 디스크로 넘치는 것(`external merge 7,888kB`)이 원인으로 보였다.
`work_mem` 을 올려 메모리 정렬로 바꿔 봤다.

```
work_mem  4MB   외부 병합정렬 7.9MB · 병렬 3워커    p50   191.8ms
work_mem 32MB   메모리 퀵정렬 22MB · 단일 스레드    p50   450.1ms
```

**반대로 느려졌다.** 비용이 싸 보이면 플래너가 병렬을 포기하기 때문이다. 같은 일이
SQL 을 좁혔을 때도 일어났다(CTE 가 id 만 들도록 → 퀵정렬 1.4MB · 단일 → 438.5ms).

그래서 병렬을 강제하고 워커를 늘렸다.

```
              단일 클라이언트         워커
기본             191.8ms / 237.9ms      2
워커 4           124.3ms / 151.6ms      4      반환 id·점수 40/40 동일
워커 6            88.8ms / 102.5ms      6      반환 id·점수 40/40 동일
```

### 4.3 필요한 설정은 둘뿐

하나씩 빼며 확인했다(`bench_pg_minimal_sets.py`).

```
min_parallel_table_scan_size = 0  +  max_parallel_workers_per_gather = 4   →  124.3ms · 워커 4
둘 중 하나라도 빼면                                                        →  191.9ms · 워커 2
parallel_setup_cost·parallel_tuple_cost 는 걸든 안 걸든 같다
```

`min_parallel_table_scan_size` 가 필수인 이유: PostgreSQL 은 이 값을 **눈금** 삼아
테이블 크기에서 워커 수를 정한다(3배마다 +1 — 8MB=1·24MB=2·72MB=3). 이 테이블 힙이
26MB 라 2개에서 멈춘다. 0 으로 두면 그 상한이 풀려 워커 수 설정이 실제로 듣는다.

⚠ 사전에 "힙 26MB 면 8MB 문턱을 넘으니 안 걸어도 된다" 고 적었는데 **틀렸다.**
  그 값은 병렬을 켤지 말지의 문턱이 아니라 워커 개수의 눈금이다.

### 4.4 동시 요청에서는 이득이 줄고, 많아지면 사라진다

쿼리 하나가 워커 N 개를 잡는데 서버 전체가 유한하다(이 서버 `max_parallel_workers` 8 ·
CPU 8). 동시 클라이언트를 늘려가며 쟀다.

```
        기본 p50/p95      워커4 p50/p95      워커6 p50/p95
동시 1   189.5/221.2       125.4/143.8        88.8/102.5
동시 2   214.2/261.1       148.7/207.5       101.5/306.3
동시 4   260.5/342.6       184.7/555.0       140.7/576.2
동시 8   362.2/900.2       415.2/884.3       443.3/890.3

처리량은 동시 4 이상에서 13~15건/s 로 포화 — 설정과 무관하다
```

**동시 1~2 에서는 p50·p95 가 함께 좋아진다. 동시 4 부터는 p50 만 좋아지고 꼬리(p95)는
나빠진다. 동시 8 에서는 이득이 없다.** 워커를 6개로 올리면 먼저 온 쿼리가 다 가져가고
뒤 쿼리는 0개를 받아 편차가 커진다. 그래서 **4** 를 택했다.

⚠ 동시 8 은 기본 설정에서도 p95 900ms 다. 그 구간은 병렬 설정 문제가 아니라
  **서버가 포화한 것**이다. 동시 사용자가 그 수준이면 서버를 늘리는 문제가 된다.

### 4.5 적용

```
config       pg_search_parallel_workers = 4   (0 이면 서버 기본값)
적용 위치     pg_store.search_hybrid 의 트랜잭션 안에서만 (SET LOCAL)
```

세션 `SET` 이 아니라 `SET LOCAL` 인 이유: 연결은 풀에서 재사용되므로 세션에 걸면
**같은 연결의 다른 쿼리까지** 영향을 받는다. 설정 실패는 경고만 남기고 검색은 진행한다 —
속도 조정이지 정확성 조건이 아니다.

출하 경로에서 확인했다(`verify_pg_parallel_hint.py`).

```
1  트랜잭션 안에서 값이 바뀌는가        8MB→0 · 2→4        적용됨
2  반납 후 원래대로 돌아오는가          8MB · 2            새지 않는다
3  워커가 실제로 뜨는가                 2개 → 4개          기대대로
4  search_hybrid 지연                  195.5 → 127.7ms    결과 40/40 동일
```

⚠ `SET LOCAL` 은 트랜잭션 블록 밖에서는 경고만 내고 **조용히 무시된다.** "설정을 넣었다"
  가 "설정이 걸렸다" 를 뜻하지 않아 위 1·2 를 따로 확인한 것이다.

## 5. 측정 과정에서 내가 틀린 것

같은 SQL 이 195ms 와 1,415ms 로 갈리는 일이 있었고, 원인을 두 번 잘못 짚었다.

```
1차 가설   후보 수(cand) 가 다르다        → 맞췄지만 그대로였다
2차 가설   캐시 순서 - 어휘를 먼저 재서    → 워밍업을 넣었더니 오히려 늘었다(1,062→1,356ms)
실제 원인   연결 재사용
```

`diag_pg_conn_effect.py` 로 회차별 시간을 찍어 찾았다.

```
회차        1~10        11 이후
연결 재사용  187~254ms   829~2,131ms
새 연결      187~254ms   150~238ms
```

같은 연결에서 **11회차부터** PostgreSQL 이 준비구문을 범용 계획(generic plan)으로 바꾼다.
출하 경로(`search_hybrid`)는 호출마다 연결을 반납해 이 전환이 안 일어난다.

**이것 때문에 측정 스크립트 두 개가 틀린 값을 냈다.** 연결 하나로 40회를 돌려서
`profile_pg_retrieval` 은 어휘 단독을 1,356ms 로, `tune_pg_retrieval` 은 여섯 조합을
전부 1,415~1,457ms 로 재고 있었다 — 설정 차이가 범용 계획에 묻혔다. 둘 다 고쳤다.

⚠ 함께 정정: `tune_pg_parallel` 이 "쿼리 하나가 8,197MB 를 읽는다" 고 찍었는데
  **틀린 값이었다.** 실행계획 모든 노드의 블록 수를 더했는데 PostgreSQL 은 각 노드에
  자식 몫을 이미 포함해 보고한다 — 깊이만큼 곱해진 값이다. 루트에서만 읽도록 고쳤다.

## 7. 측정 과정에서 드러난 것

**GPU 가 있는데 CPU 로 돌리고 있었다.**

```
223 서버        NVIDIA L4 23GB · CUDA 13.0 · nvidia 런타임 등록됨
배포 이미지      torch 2.12.1+cpu     <- 의도된 설계(고객사 CPU 전용, 10GB->3GB)
```

측정 전용 이미지를 따로 빌드해 해결했다(`TORCH_INDEX=.../cu130`). 배포본 이미지는 안 건드렸다.

```
CPU   21.6건/분  -> 약 11시간
GPU   약 30분     (적재 포함)
```

⚠ 내가 서버 GPU 를 확인하지 않고 "CPU 전용이라 11시간" 이라고 보고했다가 지적받았다.
  `nvidia-smi` 한 번이면 됐다.

⚠ 그리고 `cu124`·`cu128` 인덱스에는 락파일이 요구하는 torch 2.12.1 이 없다(각각 최대
  2.6.0 · 2.11.0). 드라이버가 CUDA 13.0 이라 `cu130` 이 맞다.
